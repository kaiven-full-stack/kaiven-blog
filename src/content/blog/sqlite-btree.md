Redis 系列写完内存数据库，CPython 系列写完解释器，还有一类东西没碰过：**磁盘数据库**。数据比内存大、停电不能丢、百万行里查一行要毫秒级——这套约束长出来的数据结构，和内存世界的哈希表、跳表完全是两种生物。

这一篇开一个新系列，主角是最适合「读源码加做实验」写法的数据库：SQLite。理由有三：它是世界上部署最广的数据库（手机、浏览器、飞机，几十亿实例）；它的源码是一个 27 万行的 amalgamation 单文件，注释以教科书级著称；最要紧的是——**它的磁盘格式简单到可以用十六进制直接读**。这一系列的方法论就从这里立起来：每个结论，要么在文件字节里看到，要么在源码里读到，要么两者都有。

先从最小的问题开始：建一张表，插三行数据，SQLite 在磁盘上写了什么？

```
$ sqlite3 btree.db "CREATE TABLE t(a INTEGER PRIMARY KEY, b TEXT);
    INSERT INTO t VALUES (1,'听雨'), (2,'夜凉'), (3,'客舍');"
```

```text
$ ls -l btree.db
8192 bytes    # 两页，每页 4096
```

三行中文，八个字节都不到的 overhead 之外，整个数据库 8KB。下面把这 8KB 逐层拆开。实验环境：SQLite 3.53.4（2026-07-24），源码取自 sqlite.org 官方 amalgamation，函数名行号均以此版为准。

## 文件头：图书馆的门牌

`xxd` 看前 100 字节，这是数据库头，固定格式：

```text
00000000: 5351 4c69 7465 2066 6f72 6d61 7420 3300  SQLite format 3.
00000010: 1000 0101 0040 2020 0000 0002 0000 0002  .....@  ........
```

开头 16 字节是魔数 `SQLite format 3\0`——文件类型识别用的。接着的每个字段在官方文档 [Database Header](https://sqlite.org/fileformat2.html#the_database_header) 里都有编号：

- `0x1000`（偏移 16，大端 2 字节）：页大小 4096；
- `0x0002`（偏移 28）：文件里共 2 页；
- 偏移 56 的 `0x0001`：可写版本号，1 表示 legacy journal，2 表示 WAL。

这里有个贯穿全篇的约定值得先记下：**SQLite 的文件由定长的页组成，所有数字段都是大端**。页是磁盘和内存之间搬运的基本单位——读一页、写一页、锁一页。第一个问题随之而来：这两页各自是什么？

`dbstat` 虚拟表是本系列最常用的观测台（需要编译时开启 `SQLITE_ENABLE_DBSTAT_VTAB`，官方二进制和主流发行版都开了）：

```sql
SELECT name, pageno, pagetype, ncell, payload FROM dbstat;
```

```text
sqlite_schema|1|leaf|1|59
t|2|leaf|3|27
```

两页、两张「表」：第 1 页是 `sqlite_schema`（所有建表语句的家），第 2 页才是 `t`——此刻还是**叶子页**（leaf），三个 cell（三行数据）。整棵 B-tree 此刻只有一片叶子。

## 页头：每层楼都有自己的索引牌

跳过第 1 页前 100 字节的文件头，看 `t` 的页（第 2 页，文件偏移 4096）的页头：

```text
00001000: 0d 0000 0003 0fdf 00
```

五个字节，一个叶子表页的全部自我描述：

| 偏移 | 字节 | 含义 | 本例值 |
| --- | --- | --- | --- |
| 0 | `0d` | 页类型：0x0d = 叶子表页 | 叶子 |
| 1–2 | `0000` | 第一个空闲块偏移 | 无空闲块 |
| 3–4 | `0003` | cell 数量 | 3 行 |
| 5–6 | `0fdf` | cell 内容区起始 | 0xfdf，从页尾往前 |
| 7 | `00` | 碎片字节数 | 0 |

页类型一共五种，记住两个就够起步：`0x0d` 叶子表页，`0x05` 内部表页（下面马上见到）。索引页是另外两个值（`0x0a`/`0x02`），系列后面讲索引时再拆。

页头之后、从偏移 8 开始是**指针数组**：每项 2 字节，指向一个 cell 在页内的偏移。cell 本体则从页尾（`content start`）向前生长——**索引在前排由低地址向高长，数据在后排由高地址向低长，中间是自由空间**。一个页的内部布局，一句话就说完了。

## cell 与 record：一行数据的九个字节

指针数组指向的地方就是 cell——一行数据的容器。用 Python 把它解出来（后面系列会把这个解析器逐步写全）：

```python
page = data[4096:8192]           # 第 2 页
ncell = int.from_bytes(page[3:5], 'big')
ptr = int.from_bytes(page[8:10], 'big')   # 第一个 cell 的偏移
cell = page[ptr:]
```

换个只有一行的库看最短的 cell——`INSERT INTO t VALUES (42, 'rain')` 的完整字节：

```text
07 2a 03 00 15 72 61 69 6e
```

九个字节，逐段拆开：

1. `07`：**payload 长度**，varint 编码——整行记录共 7 字节；
2. `2a`：**rowid**，42。SQLite 每行都有一个 64 位整数 rowid，表按它排序；`INTEGER PRIMARY KEY` 就是 rowid 的别名，所以那格不重复存数；
3. `03`：记录头长度 3 字节；
4. `00 15`：两个 serial type。`00` 是 NULL（rowid 别名列，占 0 字节）；`0x15` 是 21，TEXT 长度公式 `(21-13)/2 = 4` 字节；
5. `72 61 69 6e`：`rain` 的 ASCII。

于是 record 格式也露面了：**头（各列的 serial type）在左，数据在右**。serial type 是个小类型系统——0 是 NULL，1 到 6 是 1/2/3/4/6/8 字节整数，7 是 float，8 和 9 是字面量 0 和 1（连一个字节都懒得给），13 起是文本和 blob，长度编码在类型里。一列值占几字节、是什么类型，全在这张表里，不用猜。

三行中文的库里同理：`听雨` 是 6 字节 UTF-8，serial type 是 `(6*2+13)=25=0x19`。语言无关，字节说话。

## 树是怎么长出来的

三行的表用不着树。现在让它长大——递归 CTE 一次灌五千行：

```sql
WITH RECURSIVE cnt(x) AS (VALUES(8) UNION ALL SELECT x+1 FROM cnt WHERE x<5000)
INSERT INTO t(a,b) SELECT x, '雨'||x FROM cnt;
```

```sql
SELECT pagetype, count(*), sum(ncell) FROM dbstat WHERE name='t' GROUP BY pagetype;
```

```text
internal|1|18
leaf|19|5000
```

一个内部页、十九个叶子页。第 2 页——原来的叶子——被改造成了**内部页**，看它的页头：

```text
00001000: 05 0000 0012 0f94 00
```

类型字节从 `0d` 变成了 `05`；18 个 cell；从偏移 8 开始的指针数组后面跟的不是 record，是**子页号数组**：

```text
00001008: 0000 0015 0ffa 0ff4 0fee 0fe8 0fe2 0fdc ...
```

每个内部页 cell 的格式是「4 字节子页号 + rowid 分隔键」。`00000015` 是 21——第一个子页是第 21 页。整个查找过程在字节层面就是：读内部页 → 二分指针数组 → 顺着子页号下沉 → 到叶子页 → 二分到 cell。**B-tree 不是索引的附属品，它就是表本身**——「表」这个概念在磁盘上就是一棵 rowid 有序的 B-tree，这是 SQLite（也是多数磁盘数据库）和内存世界最根本的分歧：内存里数据住哈希表，磁盘上数据住树，因为磁盘按页读、按范围扫，树对两者都友好。

五千行的表，树高只有两层——4096 字节的页塞得下几百个指针，乘起来很快。但叶子页塞不下一行的时候呢？

## 溢出页：一本书放不进书架，就放到别处去

cell 的 payload 大部分要留在本页（本地存储最少 `page_size - 35` 字节之类的一组公式），装不下的部分挪到**溢出页**，本页 cell 里留下 4 字节的溢出页号链头。造一个装不下的行：

```sql
CREATE TABLE t(a INTEGER PRIMARY KEY, b TEXT);
INSERT INTO t VALUES (1, printf('%.*c', 5000, 'x'));  -- 5000 个 x
```

```text
2|leaf|912|5004|4096|4096
3|overflow|4092|0|4096|4096
```

第 2 页里留下了 912 字节（cell 头 + 记录头 + 5004 字节 payload 的前一段），第 3 页是溢出页，装了 4092 字节——溢出页自身的开头 4 字节是指向下一个溢出页的链（没有下一个就是 0）。读这一行需要走两页；如果列更宽，就在这条链上继续走。这解释了一个日常经验：**SQLite 单行理论上限约 1GB，但一行跨的页越多，读它越贵**。大 blob 之所以要单表存甚至拆行存，字节层面就是这个链。

## 删掉的数据去哪了

五千行删掉三千九百行：

```sql
DELETE FROM t WHERE a > 100 AND a <= 4000;
```

```sql
PRAGMA freelist_count;   -- 13
```

删掉的三千九百行没有让文件变小——空出来的 13 个页进了**空闲页链表**（freelist，文件头里记着链头页号），下次插入优先复用。想让文件真正收缩：

```sql
VACUUM;
```

```text
page_count: 6, freelist_count: 0
```

VACUUM 是重建：新建一个临时库，把数据按序抄进去，替换原文件。13 个空闲页归零，总页数从 19 收到 6。「删除是逻辑的，收缩是物理的重写」——这个行为和 CPython 那边 pymalloc 的池不还给操作系统（CPython 篇讲过的 RSS 问题）是同一类设计：**拿空间换复用速度，把「要不要真还」做成一个显式动作**。

## 对照源码：这些格式住在哪

字节里看到的每个结构，在 amalgamation 里都有名有姓。`grep` 一下刚才用到的概念：

- `sqlite3BtreeInsert`（约 82500 行附近）——插入的主入口，本文的「cell 从页尾生长」就是它的工作；
- `btreeInitPage`（75443 行）——把磁盘页解码成内存页结构，读的就是本文拆的那 8 字节页头；
- `balance()` 家族（`balance_nonroot` 等）——分裂与再平衡，本文「叶子变内部页」那一幕的执行者，源码注释自己写着这是模块里最复杂的部分；
- 文件格式文档 [fileformat2.html](https://sqlite.org/fileformat2.html) 和源码里的 `BtreeInt.h` 注释互为镜像，官方甚至给 amalgamation 的读者留了接口文档注释。

这个系列的方法在 Redis 系列就立过规矩：**先复现行为，再读实现**。SQLite 比 Redis 更适合这个方法——因为 amalgamation 是单文件，没有构建系统、没有目录跳转，`grep` 就是地图，27 万行里任何函数 30 秒内可达。

## 系列：往后走哪几步

这一篇拆的是「表怎么住磁盘」。往后的路线，按依赖关系排：

1. **pager 与事务**——页面缓存、journal/WAL 两套日志。WAL 为什么读写不互相阻塞、checkpoint 什么时候发生——磁盘层的并发故事；
2. **索引与查询计划**——`EXPLAIN QUERY PLAN` 背后，优化器怎么在几棵 B-tree 间做选择；
3. **VDBE 虚拟机**——一条 SQL 编成什么字节码、Cursor 怎么在 B-tree 上移动（和 CPython 篇的字节码对读，趣味加倍）；
4. **锁与并发**——文件锁的五种状态、busy_timeout 的语义，「单写者」模型的全部细节；
5. 番外：**用 Zig 给 SQLite 写个绑定**——C 互操作篇的知识返场，顺便验证 cgo 没有的那些东西。

## 代价，认真地

**十六进制不是日常工作的界面。**拆字节是为了建立模型，不是建议以后拿 `xxd` 调数据库——生产里 `dbstat`、`PRAGMA`、`sqlite3_analyzer` 是正确的观测层。本文手拆字节是一次性的学费，交完就换成工具。

**格式版本是快照。**文件格式从 2004 年的 format 3 定型至今稳定，但 reserved bytes、WAL 头部这类边角在新版有过微调；本文锚定 3.53.4，换版本请对照官方 fileformat2 文档复核。

**「数据库即文件」的边界要认清。**格式可读不等于可以绕过 SQLite 直接改文件——页里有校验和链表的一致性约束，跨页事务有日志保护，手工写坏一个字节，整库都可能打不开。读是自由的，写要经过它。

回到开头那个问题：三行中文在磁盘上是什么？现在有完整答案了：一个 16 字节的魔数门牌；一页记着「这个馆里有哪些表」的目录叶子；一页从尾部向前码放三个 cell 的表叶子；每个 cell 里一行 varint 加 serial type 的紧凑记录——**没有别的了**。没有服务进程，没有网络协议，没有独立存储引擎，一个文件，自洽。

Redis 系列结束时说过，内存数据库把「数据结构住哪儿」的答案写在了内存里。SQLite 的答案写在页里：表是树，树是页的链条，页是字节的自述。接下来几篇会沿着这个文件往上走——从页到日志，从日志到事务，从事务到并发。

图书馆闭馆音乐响起的时候，管理员只是把两页书轻轻合上。没有谁会来搬走书架——明天的读者，还是从第 1 页的目录开始。
