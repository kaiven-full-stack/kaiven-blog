人间千载，地址从来不只属于机器。

它可以是长街深处的一扇门，也可以是内存里一个无声的数字。地址负责指明去处，却未必说明去处之内有什么。只给你一枚门牌，你仍不知道门后是一间屋，还是一整排相连的库房；不知道里面住了多少人，也不知道走廊尽头有没有记号。若还要继续往里走，便只能靠猜。

C 里的指针常是这样一枚门牌。`T *` 可以指向一个 `T`，可以指向数组首项，可以为空，也可以一路做算术走到别处。长度写在另一个参数里，终点藏在一个零后面，所有权与可写性散落在注释和约定中。一个星号承担了太多口供，最后几乎什么都没有说清。

Zig 的指针乍看之下很不节制：

```zig
*T
*[N]T
[*]T
[]T
[*:0]T
[:0]T
?*T
[*c]T
```

星号旁边长出了方括号、问号、数字和冒号。初见像一族面目相近的生字，叫人疑心这是否只是语法洁癖。

其实它们都在回答同一个问题：**拿到这个地址时，编译器究竟还握有多少证据？**

上一篇写整数溢出，谈的是一个值走到类型疆界以后该去哪里；这一篇换一幅地图，谈地址从哪里起、可以走多远，以及边界失落以后，谁还敢替你作保。代码照例全部在 Zig 0.16.0 上验证过。

## `*T`：门后只有一件东西

最窄的一份承诺是单项指针：

```zig
const std = @import("std");

pub fn main() void {
    var year: u16 = 2026;
    const p: *u16 = &year;

    p.* += 1;
    std.debug.print("{d}\n", .{year});
}
```

```text
2027
```

`*u16` 不是「一个地址，后面也许还有更多 `u16`」，而是「一个地址，那里恰好有一个 `u16`」。所以它用 `p.*` 解引用，却不支持 `p[1]`，也不支持 `p + 1`。若硬写：

```zig
const next = p + 1;
```

编译器回答：

```text
error: incompatible types: '*u16' and 'comptime_int'
```

这不是 Zig 不会做地址加法，而是 `*u16` 的类型里没有「这里是一串东西」这份证据。让它往后走一步，等于只凭一枚门牌便断定隔壁也归同一户。编译器不肯猜。

这里还有两个经常混在一起的 `const`：

```zig
var value: u8 = 1;
const p: *u8 = &value;
p.* = 2; // 合法
```

变量 `p` 是 `const`，只说明这枚指针不会改指向；它指向的 `u8` 仍然可写。真正禁止借此修改目标的是 `*const u8`：

```zig
const value: u8 = 1;
const p: *const u8 = &value;
```

一个管门牌能不能换，一个管门里的东西能不能动。写法挨得很近，承诺并不是一回事。

## `*[N]T`：连院子有多大也写进类型

若门后不是一件东西，而是一整个数组，地址可以带上数组的完整类型：

```zig
var rain = [_]u8{ 7, 11, 19, 23 };
const p: *[4]u8 = &rain;

std.debug.print("len={d}, third={d}\n", .{ p.len, p[2] });
```

```text
len=4, third=19
```

`*[4]u8` 仍是单项指针，只不过它指向的那「一项」恰好是 `[4]u8`。长度 4 不在运行时另存一份，而是写在类型里。于是编译器知道 `p[2]` 合法，也知道 `p[4]` 已过界。

这类数组指针是 Zig 指针家族里的枢纽。它手里的证据最齐：地址有了，元素类型有了，长度也是编译期常量。需要时，它可以把部分证据交出去：

```zig
const many: [*]u8 = p; // 放下长度，只留下「后面还有同类元素」
const slice: []u8 = p; // 把编译期长度变成运行时携带的长度
```

两次转换都不需要改动底层数据。变化的只是类型还愿意替这段地址保证什么。

反过来却没有这样从容。一个 `[*]u8` 本来就没带长度，不能凭空变回 `*[4]u8`；一份已经遗失的证词，类型系统不会替你补写。

## `[]T`：把边界随身带着

多数 Zig API 接收的不是裸指针，而是切片：

```zig
fn sum(values: []const u32) u32 {
    var total: u32 = 0;
    for (values) |value| total += value;
    return total;
}
```

`[]const u32` 的意思不是「某种更好看的指针」，而是「一段连续的 `u32`，起点和长度都在」。语言参考说得很直白：slice is a pointer and a length——切片是一枚指针，加一个长度。

在这台 x86_64 机器上实测：

```zig
const std = @import("std");

pub fn main() void {
    std.debug.print("*u8       {d}\n", .{@sizeOf(*u8)});
    std.debug.print("*[4]u8    {d}\n", .{@sizeOf(*[4]u8)});
    std.debug.print("[*]u8     {d}\n", .{@sizeOf([*]u8)});
    std.debug.print("[]u8      {d}\n", .{@sizeOf([]u8)});
}
```

```text
*u8       8
*[4]u8    8
[*]u8     8
[]u8      16
```

前三种的长度要么不存在，要么已写进编译期类型，因此运行时只需一个地址。切片多带一个运行时长度，在这里是两个机器字。

「指针加长度」是语言语义；具体两个字在内存里谁先谁后、有没有 padding，却不是可以拿去当 ABI 的承诺。可靠的入口只有 `.ptr` 和 `.len`。能在当前机器上观察到布局，不等于语言替所有目标、所有版本签了字。

那多出来的一个机器字买到了什么？最直接的是边界检查：

```zig
fn readAt(values: []const u8, index: usize) u8 {
    return values[index];
}
```

当长度为 4、`index` 是 10，Debug 与 ReleaseSafe 都会停在现场：

```text
thread panic: index out of bounds: index 10, len 4
```

ReleaseFast 与 ReleaseSmall 会移除这道安全检查；越界依旧是非法行为，只是不再有人替你当场鸣锣。和上一篇的普通溢出一样，拆掉护栏不等于另获一份合法语义。

## 看起来像切片，却未必是切片

这里有一个颇能体现 Zig 性情的细节。许多人见到 `array[a..b]`，便认定结果一定是切片。实测并非如此：

```zig
const std = @import("std");

pub fn main() void {
    const letters = [_]u8{ 'a', 'b', 'c', 'd', 'e' };
    const first = letters[0..2];

    std.debug.print("{s}\n", .{@typeName(@TypeOf(first))});
}
```

```text
*const [2]u8
```

起点 0、终点 2 都在编译期已知，长度没有必要跟到运行时。编译器保留下更强的类型：`*const [2]u8`，一枚指向两元素数组的指针。

若边界直到运行时才知道，结果才是 `[]const u8`。而两种形态还可以接在一起，写出 Zig 里很实用的「按长度切片」：

```zig
fn fourAt(input: []const u8, start: usize) *const [4]u8 {
    return input[start..][0..4];
}
```

第一刀从运行时位置 `start` 切出尾部，得到切片；第二刀的长度 4 是编译期常量，于是结果重新收紧为 `*const [4]u8`。信息不必一味流失：只要证据重新出现，类型也可以重新写得精确。

这正是数组指针与切片并存的意义。前者把长度放进类型，后者把长度带到运行时。表面都是「一段连续内存」，一个适合编译器已知的尺度，一个适合程序运行时才揭晓的尺度。

## `[*]T`：边界一旦交出去

有些底层接口确实只给起点，不给长度。Zig 用多项指针 `[*]T` 表达这种处境：

```zig
var numbers = [_]u32{ 10, 20, 30, 40 };
var p: [*]u32 = &numbers;

p += 2;
std.debug.print("{d}\n", .{p[0]});
```

```text
30
```

这是指针家族里支持 `p + n`、`p - n` 的那一支。它承认后面有一串同类元素，所以可以索引、切片、前后移动；可它没有长度，也就无法知道哪一步越过了合法对象。

最容易踩的坑，是从切片里把 `.ptr` 单独取出来：

```zig
const slice: []u8 = &numbers_as_bytes;
const raw: [*]u8 = slice.ptr;
```

`slice[100]` 有长度可查，Debug 下能报告越界；`raw[100]` 连「100 是否太大」这个问题都无从提出。实测即便在 Debug，`[*]T` 的索引也不会自动使用原切片的长度——那份长度已经留在身后了。若地址最终落到对象之外，依然是非法行为，只是类型已经没有足够证据替你布置检查。

同理，不要把推进切片写成修改 `slice.ptr`。指针向前走了，`.len` 却仍停在原地，起点与边界便互相说谎。正确做法是重新切片：

```zig
slice = slice[1..];
```

新起点和新长度一同生成，两份口供仍然对得上。

这也是 Zig 把 `[]T` 与 `[*]T` 分开的根本理由：一个地址能做算术，不代表它仍拥有边界；一个 API 只要收下 `[*]T`，便是在签名里明确放弃了自动边界检查所需的信息。

## 哨兵：在尽头立一块碑

并非所有序列都另带长度。C 字符串靠末尾的零认路，许多系统接口也沿用这种习惯。Zig 没把它假装成普通切片，而是在类型里写下哨兵：

```zig
[*:0]const u8 // 以 0 为哨兵的多项指针
[:0]const u8  // 有运行时长度，且保证 data[len] == 0 的切片
```

冒号后的 `0` 不是装饰。`[:0]const u8` 除了 `.ptr` 和 `.len`，还承诺在索引 `.len` 的位置确有一个零；因此那一格可以合法读取：

```zig
var word = [_:0]u8{ 'r', 'a', 'i', 'n' };
const z: [:0]u8 = &word;

std.debug.print("len={d}, sentinel={d}\n", .{ z.len, z[z.len] });
```

```text
len=4, sentinel=0
```

这份承诺只说终点那一格是零，不说前面绝不会提前出现零。哨兵切片不是「扫描到第一个零自动算长度」的魔法；它仍有明确的 `.len`，哨兵只是边界外再立的一块凭据。

若手里只有普通缓冲区，可以用带哨兵的切片语法当场核验：

```zig
const z: [:0]u8 = buf[0..4 :0];
```

这行会检查 `buf[4] == 0`。实测放一个 9 在那里，Debug 与 ReleaseSafe 都会报告：

```text
thread panic: sentinel mismatch: expected 0, found 9
```

ReleaseFast 会移除检查，错误承诺便可能继续流入后面的代码。哨兵写进类型，不代表事实会凭空生成；从无保证的内存收紧到有保证的类型时，总得有人核验。

反过来，若来源本就没有哨兵，编译器连门都不让进：

```zig
fn takesZ(p: [*:0]const u8) void {
    _ = p;
}

const plain: [5]u8 = .{ 'h', 'e', 'l', 'l', 'o' };
takesZ(&plain);
```

```text
error: expected type '[*:0]const u8', found '*const [5]u8'
note: destination pointer requires '0' sentinel
```

它不肯因为最后一个字节「也许碰巧是零」就替你加盖印章。类型要的是证据，不是愿望。

## 字符串字面量的真实身份

于是，一个常见误会也可以揭开了。Zig 里的字符串字面量并不是 `[]const u8`：

```zig
const std = @import("std");

pub fn main() void {
    std.debug.print("{s}\n", .{@typeName(@TypeOf("hello"))});
}
```

```text
*const [5:0]u8
```

逐字拆开：它是一个只读指针，指向长度为 5、以 0 为哨兵的 `u8` 数组。地址、长度、只读性、结尾零，四份证据都在类型里。

需要普通文本 API 时，它可以隐式变成 `[]const u8`；需要 C 风格字符串时，又可以变成 `[*:0]const u8`。不是字面量天生「就是」这些类型，而是它原本携带的证据足够多，可以按接收方需要放下一部分。

中文也不例外。源码字符串装的是 UTF-8 字节，长度和索引都按字节计算。「听雨」不是两个 `u8`；若从中间随手切一刀，完全可能切进某个汉字的多字节编码里。指针类型能替你守内存边界，不能替你把字节自动理解成文字。这条界线，也须分清。

## `?*T`：地址也可以缺席

普通 `*T` 不允许是 null。一个地址可能不存在，应写成 optional pointer：

```zig
fn find(values: []u8, needle: u8) ?*u8 {
    for (values) |*value| {
        if (value.* == needle) return value;
    }
    return null;
}
```

调用方必须显式拆开两种状态：

```zig
if (find(&data, 19)) |found| {
    found.* = 20;
} else {
    std.debug.print("没有找到\n", .{});
}
```

这里的问号不是给指针额外套一个笨重盒子。Zig 保证 optional pointer 与普通 pointer 大小相同，并保证 null 表示为地址 0。在这台机器上：

```zig
@sizeOf(*u8)  == 8
@sizeOf(?*u8) == 8
```

原因很朴素：普通 `*u8` 已经把零地址排除在合法值之外，空出来的那一种表示正好拿来写 null。没有额外标志，也没有额外机器字。

若真的在 freestanding 环境里需要把地址 0 当成有效地址，可以写 `*allowzero T`。但这会占掉原本留给 null 的空位，`?*allowzero T` 在本机便长到 16 字节。`allowzero` 是给特殊内存映射准备的窄门，不是 nullable pointer 的另一种拼法。

这种区分很 Zig：null 不是某个恰好等于零的普通地址，而是类型明确允许的一种缺席。要进门，先写问号。

## 对齐与 volatile：地址还可以附带别的约束

指针承诺的不只数量。它还可以声明地址的对齐：

```zig
*align(16) const u8
[]align(4) u32
```

更高对齐的指针可以隐式交给只要求较低对齐的地方，反过来则需要 `@alignCast`。这个 builtin 不会神奇地挪动数据，只会断言当前地址确实满足更严格的对齐。实测地址错开一字节后强行 `@alignCast`，Debug 与 ReleaseSafe 报 `incorrect alignment`；ReleaseFast 移除检查，责任又回到写下断言的人。

硬件寄存器或内存映射 I/O 还会用到：

```zig
*volatile u32
```

`volatile` 要求相关读写按程序所写保留下来，避免编译器把外设交互当作普通内存访问消掉。它与线程同步无关，也不能替代原子操作。一个词被放进指针类型，只说明这条访问路径应如何对待目标内存，不会自动附赠并发秩序。

`const`、`align`、`volatile`、`allowzero` 看似又给类型添了许多笔画，其实仍是在做同一件事：把原本散在注释里的前提，尽量收进编译器能读懂的地方。

## `[*c]T`：为旧世界保留的一块含混

最后一支最特别：C pointer，写作 `[*c]T`。

它既能 `p.*`，又能 `p[i]`；允许地址 0；可以从整数隐式转换，也能和整数比较。实测下面这段在 Zig 0.16.0 是合法的：

```zig
const p: [*c]u8 = 42;
if (p == 42) {
    // 合法，不代表值得这样写
}
```

它之所以如此宽松，不是 Zig 忽然放弃了自己的类型观，而是翻译 C 头文件时，单看一个 `T *` 根本无法知道那是单个对象、数组首项还是 nullable pointer。`[*c]T` 是为了把这份原始含混原样接住。

语言参考对此几乎没有留情：应尽可能避免这种类型，合理用途是自动翻译 C 代码。原生 Zig API 若知道参数是单项，就写 `*T`；知道是一段数据，就写 `[]T`；可能为空，就写 `?*T`；以零结尾，就写 `[*:0]T`。信息明明在手，却主动退回 `[*c]T`，等于把好不容易拆开的承诺重新揉成一团。

连空间都能看出代价。在本机：

```text
@sizeOf(?*u8)    = 8
@sizeOf(?[*c]u8) = 16
```

普通指针不允许零地址，optional 可以借零表示 null；C 指针本身已经允许零，外面再套 optional，只能另找地方记录「缺席」，于是多出一个机器字。

C pointer 不是第九种更强的指针。它是一只过境用的旧箱子，里面装着 C 没能说清的东西。接过来可以，带进自己的屋里四处摆放，就未免辜负了 Zig 前面做的所有拆分。

## 类型转换，其实是在交还证据

把这一家子重新排开，它们并没有想象中杂乱：

| 类型 | 地址 | 单项或多项 | 长度 | 终点哨兵 | 可为空 |
| --- | --- | --- | --- | --- | --- |
| `*T` | 有 | 单项 | 隐含为 1 | 无 | 否 |
| `*[N]T` | 有 | 一整个数组 | 编译期 `N` | 可由数组类型携带 | 否 |
| `[*]T` | 有 | 多项 | 无 | 无 | 否 |
| `[]T` | 有 | 多项 | 运行时 | 无 | 否 |
| `[*:x]T` | 有 | 多项 | 无 | 有 | 否 |
| `[:x]T` | 有 | 多项 | 运行时 | 有 | 否 |
| `?*T` | 可能无 | 单项 | 隐含为 1 | 无 | 是 |
| `[*c]T` | 可能为零 | 含混 | 无 | 无法表达 | C 式含混 |

因此，许多隐式转换都可以理解为「交还证据」。`*[N]T` 变成 `[]T`，把编译期长度交给运行时；变成 `[*]T`，干脆放下长度；`*T` 变成 `*const T`，放下写权限；带哨兵的数组指针变成普通切片，放下终点保证。

这条路通常只能从强承诺走向弱承诺。要逆着走，就得重新拿出证据：检查长度、核验哨兵、断言对齐，或者显式处理 null。类型系统不阻止你下山，只是不许你声称自己已经站回山顶，而手里没有路引。

从这个角度看，Zig 的指针类型并非过多。C 用一个 `T *` 装下了八种处境，Zig 只是把它们逐一倒出来，叫每一种处境写上自己的名字。

## 代价，认真地

**词汇确实变多了。** 新手不只要学星号，还要分清星号在方括号里还是外面、冒号后的值是什么、问号修饰了谁。错误信息里的 `*const [5:0]u8` 初看像一串机关。C 把复杂度藏进约定，Zig 把它移到类型；复杂度没有消失，只是从运行时事故和文档猜谜，换成了编译期的学习成本。

**证据可以被你亲手丢掉。** 从切片取 `.ptr`，边界检查便失去长度；用 `@ptrCast` 改换子类型，后续读写可能踏进不可检测的非法行为；ReleaseFast 又会移除许多安全检查。类型细，不代表语言自动安全。Zig 只是让放弃了哪一份保护尽量可见，不会锁住所有后门。

**切片要多带一个机器字。** 对绝大多数接口，这是边界信息应付的合理价钱；在 ABI、寄存器压力或极窄数据结构里，它仍是真实成本。若长度本来就是编译期常量，`*[N]T` 可以更精确；若外部协议只给裸地址，也不能凭空要求世界变成切片。类型应贴着事实长，而不是一律追求看起来最安全的写法。

**哨兵仍要扫描。** `[*:0]const u8` 只保证终点存在，不直接告诉你终点离起点多远。要算长度，仍得一路寻找零。`[:0]const u8` 同时带长度和哨兵，信息更多，也意味着调用方得先取得并维护两份一致的事实。没有哪种类型能免去问题本身的成本。

**与 C 交界时，含混会回来。** `[*c]T` 的存在就是承认：外部 ABI 未必提供 Zig 想要的证据。绑定层要检查 null、补上长度、核验 sentinel，再尽快把 C pointer 收紧成原生类型。这些胶水不是美学上的瑕疵，而是两个世界对地址的承诺不同，边界处必须有人翻译。

---

到这里，那枚孤零零的地址终于补齐了凭据。

`*T` 说门后只有一件东西；`*[N]T` 连院子的尺度都写在纸上；`[]T` 把边界随身带着；`[*]T` 只认起点，不问归途；哨兵指针在尽头立碑；optional pointer 承认地址也可能缺席；`[*c]T` 则把旧世界未说清的话原样封存。

上一篇写整数的疆界，这一篇写内存的疆界。两者看似一动一静，其实问的是同一件事：当程序向前走一步，凭什么相信这一步仍在合法范围之内？整数靠位宽作答，切片靠长度作答，哨兵靠终点作答；没有答案的地方，Zig 宁愿换一种类型，直说自己不知道。

这门语言的书生气，大约也在这里。它未必替你挡住每一次莽撞，却固执地要求名实相副：知道一项，便写一项；知道长度，便写长度；一无所知，也不要冒充胸有成竹。

夜深以后，雨终于落了下来。檐下门牌微微发亮，来路已经写清。至于门后有几重院落——这一次，类型写得明白，不必再猜。
