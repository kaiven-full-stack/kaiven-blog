```text
>>> 0.1 + 0.2 == 0.3
False
>>> 0.4 - 0.1 == 0.3
False
>>> 0.1 + 0.2 - 0.3
5.551115123125783e-17

三个看似荒谬的答案，来自同一张 64 位的表。
```

int 篇讲过 CPython 拆掉了整数的墙：30 比特一间房，数字无限延伸。float 是它的对极——**墙不但没拆，还造得极其精确**：64 个比特，符号 1 位、指数 11 位、尾数 52 位，一个比特都不能多。墙内的世界由 IEEE 754 双精度标准统治，CPython 只是这座建筑的物业管理员。

这一篇走进墙内：0.1 到底是个什么数、2**53 的悬崖为什么在那里、repr 怎么决定印多少位、`hash(1.0) == hash(1)` 是巧合还是契约，最后回到与 int 篇的对照——为什么一个选无墙、一个选精确的 64 位。实验在 CPython 3.14.7 上复核，源码以 3.14 分支为准。

## 先看结构：墙内的十六个字节

PyFloatObject 是所有内置类型里最朴素的：

```c
typedef struct {
    PyObject_HEAD        /* 16 字节：引用计数 + 类型指针 */
    double ob_fval;      /* 8 字节：C double，没有别的了 */
} PyFloatObject;         /* 共 24 字节 */
```

`sizeof(1.0)` 实测 24 字节，对比 int 的 28 字节起步——float 永远 24，因为 double 定宽，没有 digit 数组要伸缩。所有复杂度都不在结构里，在 `ob_fval` 这 8 个字节的编码规则里。

64 个比特分三段：

```text
[ 符号 1 位 | 指数 11 位 | 尾数 52 位 ]
  正还是负    2 的几次方    有效数字（隐含首位 1）
```

一个 double 的值是 `±1.尾数 × 2^指数`。指数段用「偏移码」存（真实指数 + 1023），既省一个负号位又让同号数可以按位比大小。尾数段最妙：规格化数的首位永远是 1，干脆不存——**52 位存储当 53 位用**，这就是那道著名悬崖「2 的 53 次方」的出处。

把 0.1 放进这张表，立刻看到问题所在：

```text
0.1 的真身 = 3602879701896397 / 2**55
           = 0.1000000000000000055511151231257827...
```

十进制的 0.1 是 1/10，分母含质因数 5——而二进制世界的分母只有 2。**1/10 在二进制下是无限循环小数**（就像 1/3 在十进制下无限循环），53 位尾数装不下无限循环，只能截断到最近的表示。存进去的那一刻，0.1 就已经不是 0.1，是 0.1000000000000000055…。0.2、0.3 同理各有自己的偏差。

## 一 ULP 之差：加法的账

现在 `0.1 + 0.2 == 0.3` 判 False 的机制可以精确到比特。用十六进制浮点表示（`float.hex()`）看四个数的真身：

```text
0.1      = 0x1.999999999999ap-4
0.2      = 0x1.999999999999ap-3     （0.1 的两倍，尾数相同）
0.1+0.2  = 0x1.3333333333334p-2
0.3      = 0x1.3333333333333p-2
```

两个带偏差的数相加，误差也加了进去；相加结果再舍入到最近的 float，落在了 `...334`，而字面量 0.3 直接舍入到 `...333`——**尾数末位差 1，一个 ULP（unit in the last place）**。

判定相等用的是 `==`，浮点的 `==` 是**逐位精确比较**（同值不同表示如 +0.0/-0.0 除外），不做任何容差。差一个 ULP 就是不等，哪怕差值只有 5.55e-17。

工程答案因此从来不是绕过 `==` 的技巧，而是换问题：要比较就 `abs(a-b) < epsilon`（带量纲的容差），要精确就用 `decimal` 或 `fractions`，要解释为什么——现在你能解释到比特级了。

顺带一个会计实务：**浮点误差是会累积的**。十万次 `+=` 的朴素求和与 `math.fsum`（精确补偿求和）实测差 3.9e-10；对账系统用 float 累加分账金额，账目差额不是 bug，是舍入的复利。

## 2**53 悬崖：尾数的物理边界

尾数 52 位存 53 位，意味着 double 能**精确表示所有绝对值 ≤ 2**53 的整数**——再往上，相邻整数之间的间距就会超过 1：

```text
2**53     = 9007199254740992      float 精确
2**53 + 1 = 9007199254740993      float 装不下——变成 9007199254740992.0
2**53 + 2 = 9007199254740994      又能装下（间距变成 2）
```

实测三连：

```text
int 4503599627370497 (2**52+1) → float 精确保留      （悬崖以下）
int 9007199254740993 (2**53+1) → 变成 9007199254740992
int 9007199254740995 (2**53+3) → 变成 9007199254740996  （向偶数舍入！）
```

最后一行暴露了 IEEE 754 的默认舍入规则「round to nearest, ties to even」：正中间的两个候选一样近时，选尾数为偶的那个。`+3` 距离 `+2` 和 `+4` 各 1，选了偶数的 +4。这条规则不是随意——统计上它让舍入误差无偏，一半向上一半向下。

悬崖之上间距持续翻倍：`float(10**17+1)` 实测直接丢掉那个 +1（`1e+17`）。**`float(big_int)` 再 `int()` 回来会悄悄变值**，这是 int 与 float 之间最危险的一座桥。而 `10**17+1 == float(10**17+1)` 返回 False 正是悬崖的守护——Python 不假装那个 +1 还活着。

## repr 的魔术：最短往返

墙内的数是真身，印出来给人看的却是另一回事：

```text
repr(0.1)   → '0.1'         （真身是 0.1000000000000000055511…）
repr(1/3)   → '0.3333333333333333'
'%.17g' % 0.1 → '0.10000000000000001'   （17 位全精度，不是 repr）
```

老 Python（≤3.1）用的正是 17 位全精度打印，每行代码都顶着 `0.10000000000000001` 这种数字。3.1 起 repr 换成**最短往返算法**（`float_repr` → `PyOS_double_to_string`，'r' 模式）：从 1 位到 17 位精度逐个试，**找到最短的、读回来还是同一个 double 的十进制表示**。

`'0.1'` 读回去恰好舍入到那个 `0x1.99...ap-4`，所以两位就够了。这不是四舍五入到几位——是「在能唯一往返的前提下要最短」。设计动机也干净：** repr 的契约是 eval(repr(x)) == x**，多印的每一位都在为不存在的信息付版税。实验确认 `'%.1g' % 0.3` 读回也是 0.3 本尊——最短往返不一定唯一（'0.3' 与 '.3' 都行），算法保证的是最短且有往返保证。

`str` 与 `repr` 在 float 上 3.2 起完全同款。于是调试浮点问题时，`print` 看到的是化妆品，`float.hex()` 和 `struct` 才是素颜——四段实验表格里那些 `...999a`、`...334`，就是诊断的唯一可信证据。

## 哈希的契约：hash(1.0) == hash(1)

一个意料之外却刻意的等式：

```text
hash(1) == hash(1.0) == hash(True) == 1
hash(2.0) == hash(2)
```

dict 篇讲过：键的判等是「哈希相等 + `==` 成立」两条都过。而 `1 == 1.0` 是 True（数值相等，跨类型比较）——如果哈希不同，`d[1]` 和 `d[1.0]` 就会落到不同桶里，同一个「相等的键」查出两个条目，字典的等价类就裂了。

所以 CPython 规定：**数值相等的一切对象，哈希必须相等**（连 True 也算——bool 是 int 的子类）。实现不靠巧合：`_Py_HashDouble` 把 double 分解成 `m × 2^e`，用模 2**61−1 的整数运算对尾数做数学哈希再按指数移位——**算的是「这个数的值」，不是「这串比特」**。1.0 和 1 的值相同，无论存储形态是 double 还是 digit 数组，哈希殊途同归。

实测的连带后果：

```text
d = {1: 'int key'}; d[1.0] = 'float key'
→ {1: 'float key'}           （同键覆写）
{1, 1.0, True} → {1}          （set 里只剩一个元素）
```

不是 bug，是等价类的正确执行。工程师要记的边角：**用 float 做 dict 键时，1 和 1.0 是同一把钥匙**——天上不会因为换了写法多出一格。顺带 infinities 的哈希是 ±314159（π 的前六位，源码里写死的彩蛋），nan 的哈希基于对象 id 且 `nan != nan`——所以同一个 nan 对象 `in` 列表靠的是身份捷径（实测 True），两个不同来源的 nan 连「自反」都做不到。

## 与 int 对望：两种墙壁哲学

类型三部曲到这里收口。同一台解释器里的两个数值类型，交出了两份相反的答卷：

```text
              int                float
上限          无墙，digit 无限延伸   2**1024 溢出为 inf（OverflowError 转换时）
精度          精确（整数本体）       53 位尾数，十进制约 15–17 位
加法          O(位数) 进位链        1 条 CPU 指令（近似的！）
0.1           不适用（整数）        已是 0.10000...0555…
哈希          值的数学哈希          值的数学哈希（与 int 契约一致）
sizeof        28 + 4×digit        恒 24
```

int 篇的结论在这里镜像重现：**没有哪个是更对的，只有为什么在这个场景对**。科学计算与图形学要的是速度和硬件原生支持——一条 SSE 指令加四个 double，software bignum 给不了；金融与计数要的是精确——53 位尾数给不了。CPython 的选择是把两个世界都给你，再把墙的位置写进文档。

还有一处对照值得记：int 有 -5..256 的不朽缓存，float 没有也不需要——实测 `float('1.0') is float('1.0')` 为 False（每次新对象）。原因写在上一篇的账单里：int 的小值出现频率极高（循环下标、比较哨兵）且不可变，缓存稳赚；float 的高频值没有类似的聚集模式，24 字节的分配成本也压得住。**缓存是为访问分布定制的，不是类型的标配**——set 篇的墓碑、dict 篇的共享键，同一句判词的又一次出现。

## 观测与边界

```text
float.hex() / float.fromhex()   看真身：0x1.999...ap-4
struct.pack('<d', x)            比特级检视
math.fsum / decimal / fractions 补偿求和 / 十进制精确 / 有理数精确
sys.float_info                  epsilon、max、mant_dig=53 的官方口径
```

边界照例如实：float 的 `==` 无容差，比较一律用带量纲的 epsilon；累加用 fsum 或 Kahan；跨悬崖的 `int ↔ float` 转换要 `==` 验收；`round()` 的银行家舍入与格式化的舍入是两套规则（`round(2.675, 2)` 得 2.67，因为 2.675 的真身更接近 2.67）；JSON 序列化 round-trip 由 repr 的最短算法保证安全。

## 账单，按比特再算一遍

**float 是定宽 24 字节的对象包着一个 C double。** 复杂度全在 IEEE 754 的编码里：1 符号 + 11 偏移指数 + 52 尾数，隐含首位凑成 53 位有效。

**0.1 存进去的那一刻就不是 0.1。** 十进制有限小数在二进制下无限循环，53 位截断产生固定偏差；0.1+0.2 与 0.3 差一个 ULP，`==` 逐位比较判 False——容差比较是工程正解，不是绕过 bug。

**悬崖在 2**53，间距随指数翻倍。** 悬崖上相邻整数开始合并，「向偶数舍入」处理平局；int→float→int 的往返会静默变值，悬崖之上必须 `==` 验收。

**repr 是最短往返算法，不是四舍五入。** 契约是 eval(repr(x)) == x；诊断浮点用 hex 表示，别信 print。

**hash(1.0) == hash(1) 是数值哈希的契约。** _Py_HashDouble 对「值」做数学哈希而非对「比特」，保证跨类型等价类不裂；1 和 1.0 在 dict 里是同一把钥匙。

**无墙与 64 位墙是两种场景的最优解。** int 买精确付分配，float 买速度付舍入——CPython 两个都给，墙的位置写进文档和这篇账单。

```text
0.1 想住进二进制的房子，可它的行李是五分之一。
房子只收二的幂次，行李只能舍到最近的一格。
0.2 也搬进来，两份行李合在一起又舍了一次。
0.3 独自搬进来，舍的方向偏偏相反。

三行代码里住着三次独立的妥协。
第三次妥协输给前两次的总和，一个 ULP。
```

IEEE 754 用 64 个比特给实数画了一片星空，每一颗星都是一颗真实存在的数——但星与星之间是永恒的空隙。float 的一切性格，精确、溢出、舍入、误差累积，都是「数比星星多」这个事实的推论。CPython 能做的和 int 篇一样坦率：把墙的位置、间距、舍入规则原原本本写清楚，然后把选择权交还给你。
