写一门语言的系列写到第十九篇，总有一个绕不开的问题：并发呢？线程讲过内存顺序，工具链里用过 libxev，对象模型里 spawn 过 Thread。可那套每个主流语言都在谈的 async/await，Zig 的手册里一个字都没有。

不是没写过。Zig 有过一套完整的 async/await，然后亲手删掉了。

这件事本身，比任何一套 async 语法都值得写。因为「一个语言如何决定不要某个特性」比「一个语言如何堆上某个特性」罕见得多，尤其删掉的还是这门语言曾经最重要的卖点之一。这一篇讲完整的前因后果：它曾经长什么样、为什么死、死后长出来了什么。本文 Zig 代码的验证版本是 0.16.0；历史部分的引文全部有出处，一句不造。

## 曾经的无染色协程

时间线先摆正。async/await 不是很多人以为的 0.9/0.10 时代产物，它 2018 年（0.2/0.3 时代）就在了；2019 年的 0.5.0 彻底重写，成了 Zig 那几年最响亮的名片。

0.5.0 的设计相当激进，发布说明的原话是「async functions have been completely reworked」。它的要点：

- **async 是推断的，不是声明的**。没有 `async fn`，编译器看到函数里有挂起点，就自动把它编成协程。发布说明为此专门强调：「整个程序里没有任何 async 函数」；
- 调用侧写 `async foo()`，拿到一个帧（frame）；`await` 等它完成；`suspend`/`resume` 手工挂起恢复；`@frame()` 拿到自己的帧，`@asyncCall` 在任意内存上跑一个帧；
- 帧是个普通的值，可以放栈上、堆上、静态存储里，可以传递，这叫可搬动的栈，函数的「栈帧」成了数据；
- 还有 `nosuspend` 关键字（更早叫 `noasync`，0.7.0 改的名），圈定一块「保证不挂起」的区域。

为什么这么执着于「没有 async 函数」？因为 2015 年 Bob Nystrom 写过一篇后来被引用了无数次的文章：《What Color Is Your Function?》。文章用红蓝函数的寓言批评 async 模型：函数有颜色，红色（async）只能被红色调用，红会沿调用栈向上传染；同一个语言里两套函数、两套标准库、两种写法。C# 的 async/await 缓解了「调用痛苦」，但没有消除双色世界。Nystrom 的结论盛赞 Go 的 goroutine：颜色消失了，因为颜色问题被整个换掉了。

0.5.0 的发布说明直接引用了这篇文章，然后宣布：Zig 给出的方案叫无染色（colorblind）。async 是调用方式，不是函数属性，任何函数都能被同步调用、也能被 `async` 调用。2020 年 Loris Cro 的《What is Zig's "Colorblind" Async/Await?》把这套机制讲给了大众。

听着很好。那怎么会走到删除？

## 死因：官方的四个理由

先澄清一个流传甚广的说法：网上常有人引用一个叫「Async is a mistake」的 issue 说 Andrew Kelley 承认 async 是错误。这个 issue 不存在，GitHub 上那个编号是别的 bug。真实的死因写在 0.12.0（2024-04）发布说明的「Async/Await Feature Status」一节，原文列了四条：

1. **LLVM 无法优化它们**。协程的帧拆分、挂起点恢复，走的是 LLVM 的 coroutine pass，优化效果差；
2. **调试器无法调试它们**。第三方调试工具不理解帧被搬来搬去之后的栈；
3. **取消问题**（the cancellation problem）。一个帧挂起后如果被丢弃，哪些资源已经清理、哪些还悬着，没有好答案。这个问题 0.3.0 时代（2018 年）的发布说明里就自己承认过「取消目前是不健全的」，悬了六年没解决；
4. **async 函数指针导致栈大小不可知**。拿到一个函数指针，没法知道调用它需要多大的栈，而 Zig 连 `main` 的栈怎么安排都要讲究。

发布说明接着说：这些问题可以解决，但需要时间，Zig 团队当前优先级在别处。

时间线的后半段是这样的：2022 年 12 月《Goodbye to the C++ Implementation of Zig》移除了老编译器 stage1；async 当时只存在于 stage1 里，于是 0.11.0（2023-08）起 async 整体退化（发布说明原话：「async functions regressed with the release of 0.11.0」）；2025 年 7 月，PR #24362 把 `async`/`await` 关键字和 `usingnamespace` 一起删除，合并时的原话很硬：「语言里不会有 async/await 关键字，这一点已经定了」；0.15.1（2025-08）随版发布。另外值得一记：`@frameSize` 也删了，注释里写明它们的去处：标准库的 Io 接口。

本机 0.16.0 现场验证一下「删除」的实际手感：

```zig
async fn foo() void {}
```

```text
error: expected ',' after field
```

`async fn` 已经不是「未实现」，解析器根本不认识它了，把它当 struct 字段解析。`await`、`async foo()` 同样直接是语法错误。但有两个活化石：`suspend {}` 报的是「async has not been implemented in the self-hosted compiler yet」，关键字还在，语义等一个永远不会来的实现；`nosuspend` 则被静默接受，圈一块「保证不挂起」的地，只是如今没有函数能挂起了。

## 死后：Io 接口，第二个 Allocator

如果故事到删除为止，那只是「砍特性」。但 Zig 在同一个 PR 里已经说了去处：标准库的 Io 接口。0.16.0 发布说明的路线图把 Io 称为「async/await 复活的先导」。

Io 长什么样？打开标准库看一眼它的字段：

```zig
userdata: ?*anyopaque,
vtable: *const VTable,
```

这套结构你见过，它就是 Allocator 的形状。分配器那篇看过：一个指向状态的指针，一张函数表。对象模型那篇说过 vtable 是 Zig 接口的官方答案；Io 是同一个模式在 IO 上的实例，而且规格对齐 Allocator：分配器回答「内存从哪来」，Io 回答「阻塞怎么处理」。发布说明的原话是：从 0.16.0 起，所有输入输出功能都要求传入一个 Io 实例，「任何可能阻塞控制流或引入非确定性的东西，都归 Io 接口管」。

用起来是这样的（0.16.0 实测）：

```zig
fn work(n: u32) u32 {
    var sum: u32 = 0;
    for (0..n) |i| sum +%= @intCast(i);
    return sum;
}

var threaded = std.Io.Threaded.init(gpa.allocator(), .{});
defer threaded.deinit();
const io = threaded.io();

var f = io.async(work, .{100});
const result = f.await(io);
```

```text
io.async 结果: 4950
```

注意 `work`：它是个普通函数。没有 async 标注、没有颜色、不知道自己会被并发调用。然后是无染色最直接的证据：

```zig
const direct = work(10);          // 直接调用
var f = io.async(work, .{10});    // 同一个函数，交给 io
const concurrent_result = f.await(io);
```

```text
直接调用: 45, io.async: 45（同一个函数，同一份代码）
```

同一个 `work`，直接调是一次加法，交给 `io.async` 是一次并发执行。颜色不在函数上，在调用上。这正是 0.5.0 没做到位的事，如今由库接口完成。

Io 是个可插拔的实现族，0.16.0 标准库里躺着这些：

- **`Io.Threaded`**，默认实现，每个 async 一个线程池里的线程，功能完整含取消（实测就是用它跑的上面那些例子）；
- **`Io.Evented`**，实验性的 M:N 绿线程，基于用户态栈切换（标准库里那 60 行手写汇编的 `fiber.zig` 就是干这个的，`contextSwitch` 在 aarch64/x86_64/riscv64 之间切换整组寄存器）；
- **`Io.Uring` / `Io.Kqueue`**，Linux io_uring 与 BSD kqueue 的封装（分别 6000+ 和 1500+ 行，PoC 阶段）。

关键的机制在这：调用方代码不变，换个 Io 实现就换个并发模型。你的函数从头到尾不知道自己跑在线程上、绿线程上还是 io_uring 上，那是 `io` 参数的事。和 Allocator 同一个哲学：分配策略是参数，并发策略也是参数。

两个动词的分工也值得记：`io.async` 是优化，意思是「你帮我并发跑」，实现甚至可以直接同步调用完再返回（发布说明明说这是合法的）；`io.concurrent` 是正确性要求，意思是「我需要这件事真正并发」，环境不支持时返回 `error.ConcurrencyUnavailable`。想清楚你要的是「快点」还是「必须同时」，选不同的词。批量的活用 `Group`：

```zig
var g: std.Io.Group = .init;
defer g.cancel(io);

g.async(io, work, .{100});
g.async(io, work, .{200});
try g.await(io);
```

```text
两个任务完成
```

（`Group` 版的 `work` 返回 `Cancelable!void`，涉及取消传播的边界，这里不展开。）

## 函数染色，再答一次

现在可以回到 Nystrom 那篇寓言，看看 Zig 的两次作答。

第一次作答是语言级的：把 async 做成推断，消灭「async 函数」。代价是四个死因：帧可搬动意味着调试器和优化器都得理解「栈是值」，取消语义悬而不决，函数指针的栈大小失去意义。问题的根源在于，为了消灭颜色，它把并发语义塞进了每一个函数的编译产物里。

第二次作答是库级的：颜色既不在函数上，也不在语言里，在那个传来传去的 Io 值上。`work` 永远是普通函数；想同步就同步调，想异步就把 `io` 传下去。函数不携带任何并发信息，调试器看到的就是普通栈，取消是 Io 实现的职责（`Io.Threaded` 连取消都做完了），栈大小由实现自己安排。四个死因逐条对着解。

对照一下别的答案：Go 把颜色问题换成 goroutine，代价是运行时和调度器住进每个二进制；Rust 接受颜色，用 async fn 和生态把红蓝两套世界制度化，代价是 `Send`/`Sync`/`Pin` 一整层类型系统负担；Erlang/BEAM 从对象模型上就为并发而设，代价是别的一切。Zig 的第二次作答是这几种之外的一条：不内置运行时、不区分函数颜色、把并发模型做成一个可以换来换去的库参数。LWN 在 2025 年 12 月的报道里评价这个新设计「承诺解决函数染色问题，并允许同一份代码用同步或异步 IO 正确执行」。

## 尾声：故事还没有写完

如实交代现状：这个故事没有到大结局。`Io.Threaded` 完整可用，`Io.Evented` 和 `Io.Uring` 标着实验性；未来还有两条演化路线在并行讨论：有栈协程（Evented 已经在用）和无栈协程（issue #23446，作为底层原语的提案，仍开着）。Andrew Kelley 自己在 2025 年 10 月的文章里说得很谨慎：「这些 API 还没有定稿，可能要迭代几次才能做对。」

但有一件事 PR #24362 已经一锤定音：语言层面不会再有 async/await 关键字。要回来，也是以库的形态、以 Io 参数的形态。

## 这段历史的代价

「删特性」的代价由生态承担。0.11 到 0.15 那几年，依赖 async 的库（包括当时的事件循环标准库设施）全部报废重写。这是 1.0 之前语言的常态，工具链篇聊过版本焦虑，这里是它最疼的一次兑现。

Io 接口是新的，还在长。0.16.0 是它第一个正式版本，API 会动（连 `Future.await` 要不要传 `io` 这种细节都在演化）。今天的示例代码不代表明天的写法；写这篇文章时我实测的每一行，都注明了 0.16.0。

无染色不是免费的。把并发决策推迟到调用点，意味着读代码时不能从函数签名判断它会不会被并发执行：`work` 在谁手里、以什么方式跑，要看调用链顶端传的是什么 Io。这比「看一眼有没有 async」多了一跳。换取的是同一份函数在同步、线程、io_uring 世界里原样复用。这个代价 Nystrom 十年前就算过：颜色问题从来不是要不要付出，是选择在哪一层付。

四个死因解了三个半。调试（普通栈）、栈大小（实现自理）、LLVM（不经过）都解了；取消是 Io 接口的核心设计之一（连 Threaded 都支持，通过信号打断阻塞调用），但「取消之后的语义」在任何语言里都是深水区。那半个，留给时间。

---

这一系列写到这里，Zig 给我最大的震动始终是同一种：它对「删」的坦然。`usingnamespace` 删了，安全模式那篇讲的 Illegal Behavior 收编了未定义行为，async/await 七年家业一纸删除。每一次都不是失败，是设计判断：当一个特性需要其他一切为它变形，就把它请出去，用已经证明过的原语（参数、接口、vtable）重新长出来。

Allocator 教会这个系列「能力做成参数」；Io 是同一课在并发上的重修，发布说明自己都点破了这层关系，把 Io 称为「Allocator 模式的延伸」。函数颜色这道题，Nystrom 2015 年出的，Go、Rust、Kotlin 交过卷，Zig 删掉第一份答卷之后，用第二个 Allocator 又答了一遍。答卷还没交完，但答题的方式，已经和第一次不一样了。
