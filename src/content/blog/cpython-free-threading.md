```text
GIL 构建，4 线程跑 4 份独立工作    1.5063 秒（单线程 0.3390 的 4.44 倍）
free-threaded 构建，同一份代码      0.4300 秒（单线程 0.4136 的 1.04 倍）
```

同一段纯 CPU 代码，四个线程各自处理互不相干的数据。GIL 构建把并行变成了排队，还搭上切换开销；free-threaded（下称 FT）构建下四个核真的同时在跑。

这个差别值得整篇文章：**CPython 为拆掉 GIL 付出了什么，你用 FT 构建时又要接受什么**。

先把系列里欠的账摆出来。第一篇讲引用计数时说过 `del` 只删名字；讲 pymalloc 时看过“三十九座楼”；讲特化时提过一句 thread-local bytecode；讲 asyncio 时留了钩子“当 GIL 不再替这些状态提供全局串行背景”。这一篇就是那些伏笔的收束——GIL 拆掉后，引用计数、内存分配、字节码特化、事件循环依赖的每个全局不变量，都要重新发明。

本文实验以 **CPython 3.14.7 free-threaded 构建**（`--disable-gil`，x86_64 Linux，非 debug）为主，与同版本默认 GIL 构建对照，并核对本地 **CPython 3.16.0a0** 开发源码快照。PEP 703 的机制、字段布局与阈值是实现事实；3.14 起 FT 构建已按 PEP 779 进入 phase II——官方支持、仍然可选。

## 先看价目表

FT 构建不是免费的。同一组单线程基准（5 轮取最优，秒）：

| 负载 | GIL 3.14.7 | FT 3.14.7 | FT 开销 |
| --- | --- | --- | --- |
| count_1M（纯整数循环） | 2.09 | 2.79 | +33% |
| fib27（递归调用） | 0.24 | 0.35 | +44% |
| sieve100k（分支+列表） | 0.15 | 0.24 | +57% |

三个来源：对象头变大（下一节）、容器操作要过临界区（后文）、偏向引用计数仍比对单线程的普通计数多做属主检查。3.16 快照上同样负载的开销已经收窄（count 2.46、fib 0.28、sieve 0.18），这是持续优化的方向，不能写成固定比例。

所以 FT 构建的价值公式很清楚：**单线程慢一些，多线程真并行**。只在单线程跑的程序没有任何理由用它；有并行需求的程序才有得谈。

## `getrefcount` 的两个惊讶值

在 FT 构建下做两个观察（GIL 构建的结果放在注释里）：

```python
import sys

sys.getrefcount(-1)     # 3221225472（GIL 构建同为 3221225472）

def f(): pass
sys.getrefcount(f)      # 1152921504606846977（GIL 构建是 2）
```

第一个值两种构建相同：`0xC0000000`，immortal 对象的标记性引用计数，第一篇讲过。

第二个值是 FT 独有的：`1152921504606846977 = 2^60 + 1`。它不是“这个函数被引用了两百多亿亿次”，而是**两个成分的合成**：真实的引用计数是 1，再加上 `_Py_REF_DEFERRED`——`PY_SSIZE_T_MAX / 8`，一个巨大的偏置量。函数对象被标记为**延迟引用计数**（deferred reference counting）：它的引用计数不再精确维护，交给 GC 兜底。

为什么是函数对象？因为它是天然的共享热点：每个调用点、每个帧都可能握着它，跨线程引用极其频繁。如果每次 `CALL` 都要原子操作共享计数，调用就贵了。标记为 deferred 后，跨线程的 incref/decref 直接跳过（`_Py_REF_DEFERRED` 保证计数不为零），存活判断交给循环 GC。

这不是新发明。老 Python 手会想起 Python 1.x 到 3.11 之间模块、类型等对象用“永久引用”回避的同类问题；FT 把这套思路工程化了：模块、方法描述符、classmethod/staticmethod 实例、`type.__new__` 的内建包装在创建时就打上 `_PyGC_BITS_DEFERRED`，`ob_ref_shared` 初始化为 `_Py_REF_DEFERRED`；顶层函数同样标记，但嵌套函数除外——它们常捕获自由变量，及时释放更重要，源码注释写明了这个取舍。第三方类型还能用 `PyUnstable_Object_EnableDeferredRefcount()` 主动加入。

于是一个直接的边界：**FT 构建下，`sys.getrefcount` 对这些对象返回的数值失去了“精确计数”的解读**。它仍是合法的诊断窗口，但读数里混进了标记位。

## 对象头：从 16 字节到 32 字节

两个构建的 `PyObject` 头部放在一起看（`Include/object.h`）：

```text
GIL 构建（3.14.7）
struct _object {
    uint32_t  ob_refcnt;      // 8 字节（联合体，含 overflow/flags）
    PyTypeObject *ob_type;
};

FT 构建（3.14.7）
struct _object {
    uintptr_t ob_tid;         // 属主线程 id（0 = 无属主/已合并）
    uint16_t  ob_flags;
    PyMutex   ob_mutex;       // 单字节锁
    uint8_t   ob_gc_bits;
    uint32_t  ob_ref_local;   // 本地引用计数
    Py_ssize_t ob_ref_shared; // 共享引用计数（含标志位）
    PyTypeObject *ob_type;
};
```

一个 `object()` 的尺寸从 16 字节变成 32 字节，`int` 从 28 变 44，`float` 从 24 变 40。本机实测：

| 对象 | GIL | FT | 差 |
| --- | --- | --- | --- |
| `object()` | 16 | 32 | +16 |
| `int`（小整数） | 28 | 44 | +16 |
| `10**100` | 72 | 88 | +16 |
| `str 'a'` | 42 | 58 | +16 |
| `()` / `[]` / `{}` / `set()` | 48/56/64/216 | 48/56/64/216 | 0 |

注意最后一行：容器完全没变大。头部的增量被容器条目本来就按 8 字节对齐的布局吸收了；GC 头也一样——GIL 构建的 `PyGC_Head` 16 字节前置元数据在 FT 构建里整体消失，`ob_gc_bits` 一字节就够（后文讲 GC 时展开）。所以“FT 让所有对象翻倍”是错误印象：**增量集中在小标量对象上**，而小对象恰恰是分配最频繁的那批。

三个新字段各自回答一个并发问题：

- `ob_tid`——**谁拥有这个对象？**
- `ob_ref_local`——**属主线程手里有几份引用？**
- `ob_ref_shared`——**其他线程手里有几份？**

## 偏向引用计数：属主走快路

GIL 构建的 `Py_INCREF` 是一条普通内存写。FT 构建的同一行代码变成了**偏向锁的引用计数**（biased reference counting）：

```text
Py_INCREF(op):
    属主是自己？  -> ob_ref_local++         （普通读改写，无原子）
    不是          -> ob_ref_shared += 1<<2  （原子 fetch-add）

Py_DECREF(op):
    属主是自己？  -> ob_ref_local--
                    减到 0：尝试合并/释放（_Py_MergeZeroLocalRefcount）
    不是          -> _Py_DecRefShared(op)   （原子 CAS，可能入队）
```

对象的“属主”就是创建它的线程：`ob_tid` 记下线程 id，此后该线程的 incref/decref 全部走 `ob_ref_local`——不加锁、不原子、就是一条普通指令。其他线程的引用才落入 `ob_ref_shared`，用原子操作维护。

设计依据是现实的访问模式：绝大多数对象从生到死只被创建线程碰过（第一篇的结论在这里派上用场——局部性主导对象生命周期）。偏向方案让常见情形保持 GIL 时代的速度，把同步成本留给真正的跨线程共享。

`ob_ref_shared` 的低两位是标志位：`_Py_REF_MERGED`（本地与共享计数已合并，此后无属主）和 `_Py_REF_QUEUED`（对象已进入待合并队列）。真正的计数在高位。

### 属主放手：合并与入队

本地计数减到零时，属主线程调用 `_Py_MergeZeroLocalRefcount()`。两条路：

```text
共享计数也是 0        -> 直接 _Py_Dealloc（对象确实死了）
共享计数非 0          -> 把 ob_tid 清零（放弃属主），
                        标志位置成 MERGED，
                        之后所有线程都走共享计数
```

反方向更微妙：**非属主线程的 decref 把共享计数减到零时，对象不能立刻释放**——属主线程的本地计数可能非零，而且释放内存时可能有线程正读着这个对象。此时 `_Py_DecRefSharedIsDead()` 不做减法，而是把标志位 CAS 成 `_Py_REF_QUEUED`，把对象挂进属主线程的**待处理队列**（队列自身持有引用）。属主线程在下一个安全点取出队列里的对象，合并计数，再决定生死。

一句话总结这套设计：**死掉的判定权始终收归属主线程，非属主只负责投票**。没有全局锁，也没有跨线程的释放竞争。

## 单字节锁与临界区

引用计数之外，对象自身的操作（改字典、改列表、改类型）也需要互斥。FT 的答案让对象头只付出 1 字节：`PyMutex` 是一个 `uint8_t`。

```text
0b00 未锁定
0b01 已锁定，无等待者
0b11 已锁定，有等待者
```

无争用时上锁解锁是两条原子指令；有争用时才陷入内核等待（Linux 上走 futex）。锁藏在 `ob_mutex` 里，跟着对象走。

使用侧的入口是**临界区**（critical section）：

```c
Py_BEGIN_CRITICAL_SECTION(op);
    /* 读写 op 的内部状态 */
Py_END_CRITICAL_SECTION();
```

它不只是一把锁：进入时记录到线程的临界区栈，持有期间**阻塞停世界**（后文 GC 需要）、按固定顺序获取避免死锁、离开时恢复。对嵌套对象（改 A 时也要看 B）有 `PyCriticalSection2` 变体，靠编译期排序保证全进程一致的加锁顺序。

这解释了一个实测结果。四线程各自往**私有** list 里 append 50 万次，FT 构建 0.052 秒——比 GIL 构建（0.094）还快，因为私有容器无争用，临界区就是两条指令，而 FT 的真并行让四个线程各吃一个核。换成**共享**一个 list，FT 掉到 0.255 秒：每次 append 都是真实的锁竞争。GIL 构建从 0.094 到 0.100，几乎无感——GIL 本来就把一切串行了。

```text
                    GIL 构建         FT 构建
私有 list x4        0.094            0.052
共享 list x4        0.100            0.255
```

所以 FT 没有把“容器操作变慢”当成统一命运：**专属容器更快了，共享容器才付锁钱**。程序怎么写数据所有权，直接决定 FT 是赚是赔。

## `i += 1` 终于丢失更新了

GIL 时代有一句入门警告：“多线程改共享变量要加锁，否则结果不可预期”——但 GIL 构建里 `i += 1` 这种纯 Python 语句实际上被字节码粒度的串行化保护着，小实验里几乎从不出错，警告显得像走过场。

FT 构建下警告变成现实。四个线程各做 20 万次 `i += 1`（闭包共享 `i`）：

```text
GIL 3.14.7      800000   OK
FT 3.14.7       510977   丢失 289023（另一次运行 549549）
FT 3.16.0a0     460059   丢失 339941
```

`i += 1` 是三步：读 `i`、算 `i+1`、写回。两次读改写可以交错，后写覆盖先写。丢失量随调度抖动，每次运行都不同。

同一个实验里的另一组值得对照：四线程往共享 list 里 `append` 各 20 万次——**结果精确等于 80 万，一次不丢**。`list.append` 是容器操作，内部被临界区完整包裹，对外呈现原子性。

于是 FT 时代的边界要重新表述：

```text
单个容器操作（append/setitem）     原子
复合语句（i += 1、check-then-act）  非原子，与任何语言一样
多个操作的组合                     非原子，需要锁
```

GIL 曾经意外提供的“字节码级伪原子”消失了。这是语义上最需要向读者强调的变化：**不是 FT 引入了数据竞争，是 GIL 一直在替你掩盖它**。PEP 703 把这归为“受支持的语义变化”——依赖旧偶然行为的代码本来就该修。

## 字节码也变成每线程一份

特化篇末尾提过一句“thread-local bytecode 允许不同线程拥有自己的专门化副本”。实测（`_testinternalcapi.get_tlbc_id`）：

```python
def work(n):
    total = 0
    for i in range(n):
        total += i
    return total

work(50_000)        # 主线程热身，BINARY_OP 学会 ADD_INT

# 三个子线程各自热身后，查询它们看到的字节码数组：
主线程      4780070496744
线程 0      4780131287232
线程 1      4780198527168
线程 2      4780131287232
```

三个 id 各不相同——**每个线程持有 code object 字节码的独立副本**（TLBC，thread-local bytecode），各自的特化状态互不干扰。线程 0 与 2 地址相同是分配器复用，不代表共享。

为什么必须如此：特化篇讲过，`BINARY_OP_ADD_INT` 是把类型假设**写进字节码数组**。两个线程同时执行同一函数、喂不同类型时，如果共享一个数组，一个线程的特化会被另一个线程的 guard miss 冲掉——退化成持续的互相反特化。每线程一份副本，写冲突就消失了；code object 里的 `co_code` 保持逻辑视图，不随副本变化（这层设计与特化篇看到的“`co_code` 与 adaptive 数组分离”完全同构）。

副作用：禁用 TLBC 会连带禁用特化——没有独立副本，就不敢原地改写。这也是 FT 构建的内存开销来源之一：热函数的字节码在每个活跃线程里都有一份。

## 分配器与 GC：换地基

讲 pymalloc 那篇的整个世界观——block、pool、arena、size class——在 FT 构建里**整体缺席**：

```python
import _testinternalcapi
_testinternalcapi.pymem_getallocatorsname()
# GIL 构建:  'pymalloc'
# FT 构建:   'mimalloc'
```

FT 构建把分配器换成了 mimalloc。原因直白：pymalloc 的设计充满单线程假设（per-size-class 的 freelist 无锁操作、arena 归还的“整层清空”）；逐项加锁会把它仅有的速度优势也磨掉。mimalloc 从第一天就是为多线程设计的：每线程本地 heap、免锁快路径、shard 化的 page。

GC 也换了形态，差异在 `InternalDocs/garbage_collector.md` 里列得明白：

```text
                   GIL 构建              FT 构建
追踪结构           PyGC_Head 双向链表     mimalloc 扫堆找到被追踪对象
分代               三代                   不分代，每次全堆
线程协调           GIL 顺带解决           两次停世界（stop the world）
不可达对象表       PyGC_Head 链表         复用 ob_tid 当链表指针
标志位             _gc_prev 里            ob_gc_bits（头部的 1 字节）
```

最反直觉的是**放弃分代**。分代的收益依赖“多数对象朝生夕死、活过童年的会活很久”的假设——这个假设在 FT 下依然成立，但 mimalloc 的堆组织不按年龄分段，为了分代就得另维护一层跨线程的结构，成本盖过收益。于是 FT 的 GC 每次都全堆扫描。这是**用吞吐换实现简单**的取舍：停世界两次（一次找根、一次清不可达），停的世界越小、越短越好。

停世界本身靠 QSBR（quiescent state-based reclamation）实现——`Python/qsbr.c`。它不立刻冻结所有线程，而是等每个线程走到**静止点**（分配、进入解释器循环等安全位置）才生效；要释放的内存推迟到“所有读者都走过静止点”之后。同一机制还保护着无锁读的场景：类型缓存、字典查找的 fast path 都靠 QSBR 保证读到的指针不会在眼皮底下被释放。

顺带回收第一篇的一个伏笔：GIL 构建里 `PyGC_Head` 是对象前方 16 字节的“前置元数据”；FT 里这 16 字节没了，标志位住进 `ob_gc_bits`。所以 FT 的 `object()` 头部虽从 16 涨到 32，但对 GC 追踪的对象而言，**净增量是 32 − 16 − 16 = 0 字节**——头部膨胀与 GC 头消失恰好抵消。

## 还能开回来：GIL 是运行时选项

FT 构建里 GIL 没有被物理删除，只是默认关闭：

```text
默认           sys._is_gil_enabled() -> False
PYTHON_GIL=1   sys._is_gil_enabled() -> True
-X gil=1       sys._is_gil_enabled() -> True
```

用 `PYTHON_GIL=1` 重跑并行实验：4 线程 1.578 秒（单线程的 4.43 倍），`i += 1` 恢复 80 万不丢——GIL 的行为完整回来了。这给迁移留了退路：同一份二进制，可以先带 GIL 跑着，逐模块验证，再摘掉。反过来，GIL 构建用 `PYTHON_GIL=0` 开不出真并行——那个构建里根本没有 FT 的机器。

一个工程细节：PEP 703 给多阶段初始化的模块加了 `Py_mod_gil` 槽位（3.13 起），C 扩展用它声明“我不用 GIL”或“我需要”；未声明的旧扩展在 FT 构建里默认触发警告，防止它们破坏新的并发不变量。

## 三层承诺的最终版本

### Python 语言语义

`i += 1` 在线程间本来就不保证原子——GIL 构建的偶然行为不是语言承诺，PEP 703 只是让它回到本来的样子。FT 构建下：

- 容器单操作原子性不变；
- 内存可见性与普通多线程语言一致；
- `sys.getrefcount` 的读数对 deferred 对象失去直观解释。

### 构建与支持状态

PEP 779：3.14 起 FT 进入 phase II——官方支持、仍然可选、不会被无声移除。单线程开销、包生态（C 扩展逐个适配中）是现实约束。phase III（默认或唯一构建）没有时间表。

### 内部实现

```text
ob_tid / ob_ref_local / ob_ref_shared
_Py_MergeZeroLocalRefcount / _Py_DecRefSharedIsDead
_Py_REF_DEFERRED / _PyGC_BITS_DEFERRED
PyMutex（uint8_t）/ Py_BEGIN_CRITICAL_SECTION
qsbr.c / mimalloc / TLBC
```

3.16 快照的对应布局已见变化苗头（如 `ob_tid` 对齐属性的引入、解释器结构的持续调整）。字段名与机制归属版本实现，不构成跨版本契约。

## 拆掉的是天花板，不是护栏

**FT 构建买到了真并行。** 四线程独立负载 1.04 倍于单线程；GIL 构建同一场景 4.44 倍。

**单线程付了过路费。** 本机 3.14.7 上 +33% 到 +57%，来源是对象头、临界区与偏向计数；3.16 开发版已明显收窄。

**引用计数靠“偏向”活下来。** 属主线程走无锁本地计数，跨线程引用进共享计数；死亡判定收归属主，非属主只投票；函数与模块干脆延迟计数，交给 GC。

**每个对象自带一把单字节锁。** 争用时才付代价；私有容器在 FT 下反而更快，共享容器才见锁竞争。

**GIL 掩盖的数据竞争现形了。** `i += 1` 大量丢失更新；`list.append` 因临界区保持原子。边界回到多线程语言的常识。

**分配器与 GC 换了地基。** pymalloc 让位 mimalloc，分代 GC 让位全堆扫描加两次 QSBR 停世界；PyGC_Head 消失，净头增量对 GC 对象恰好为零。

**字节码按线程分家。** TLBC 让特化状态互不干扰，代价是热代码的多份副本。

**GIL 还能开回来。** `PYTHON_GIL=1` 完整恢复旧行为，迁移可以渐进。
