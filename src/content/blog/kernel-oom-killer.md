这是内存系列的最后一篇。前六篇讲的都是「分配」：页表、缺页、伙伴系统、slab、VMA、page cache，内存从各个口子流出去。这一篇讲出口：内存真的见底时，内核怎么收场，按什么顺序做哪几件事、oom_score 的分数怎么算出来、`oom_score_adj` 如何改命、Redis 该怎么用它自保。它和 Redis 系列那篇[淘汰策略](/posts/redis-eviction-policy/)正好凑成一对：应用层的淘汰是「丢数据保服务」，内核层的淘汰是「丢进程保机器」，同一道题，两个层级。（前置概念见[《第 0 篇》](/posts/kernel-primer/)。）

先交代本篇实验的特殊性：OOM killer 的完整行为（真杀进程）在真实机器上复现有天然风险，杀错一个桌面进程，整个会话陪葬。我准备了容器级的安全方案（cgroup memory.max），但它在本环境折戟了；折戟的过程和原因，本身就是「我踩的坑」一节的主角。正文因此以源码与真实配置的实测为骨架。值得先说明的是，骨架反而更扎实：打分公式、牺牲顺位、水位顺序，全部来自 v7.2 源码和这台日用机器的真实状态，没有一个数字是编的。

## 内存见底的四级响应

内核不是一缺内存就拔刀。短缺的响应分四级，一级比一级狠：

**第一级：水位回收。** 第三篇提过每个 zone 有 min/low/high 三道水位。分配路径越过 low 水位时，唤醒 `kswapd` 后台线程，在进程继续跑的同时回收内存：丢干净页缓存（第六篇的 page cache，可丢可重建）、收缩 slab 缓存（第四篇的 shrinker 与 SReclaimable）、把匿名页换出到 swap。这一级的目标是让水位回到 high，进程几乎无感。

**第二级：direct reclaim。** kswapd 追不上分配速度时，分配进程自己被拉去回收：`__alloc_pages_slowpath` 里，申请者停下来等内存腾出来。表现为分配延迟暴涨，进程没死，但 `malloc`/缺页开始卡。`/proc/pressure/memory`（PSI）的 `some`/`full` 两行计的就是这种压力，本机 `total=40357019` 微秒的累计值说明这台日用机也常在第二级门口徘徊。

**第三级：全局 OOM。** 回收也挤不出水了：没有干净页可丢、没有冷页可换、swap 满或不存在。此时 `out_of_memory()` 被调用，进入本篇主角的流程。

**第四级：memcg OOM。** 另一条独立触发线：cgroup 的 `memory.max` 顶到头。容器里一个进程把配额吃光，OOM 只在**这个容器内部**选人。这是 Docker/K8s 容器被 OOMKill 的机制，宿主机其他进程毫发无损。源码里四种约束有各自的标记：`CONSTRAINT_MEMCG` 与全局的 `CONSTRAINT_NONE` 是其中最常见的两种。

值得强调的顺序问题：**杀进程是内核最后才做的事**。第一、二级的存在就是为了永远别走到第三级：丢缓存、换冷页、拖慢分配，都是比杀进程便宜的选项。OOM killer 的触发条件不是「内存满了」这么简单，是「便宜的选项全用完了」。

## oom_badness：打分公式

走到第三级，问题变成：杀谁。v7.2 `mm/oom_kill.c` 的 `oom_badness()` 给出打分公式，简化后是：

```c
adj = (long)p->signal->oom_score_adj;
if (adj == OOM_SCORE_ADJ_MIN)     /* -1000：免死金牌 */
        return LONG_MIN;          /* 连候选都不进 */

points = get_mm_rss_sum(p->mm)                          /* RSS：真实占的页 */
        + get_mm_counter_sum(p->mm, MM_SWAPENTS)        /* 换出到 swap 的页 */
        + mm_pgtables_bytes(p->mm) / PAGE_SIZE;         /* 页表（第一篇的账）*/

adj *= totalpages / 1000;
points += adj;                                         /* adj 直接加成分 */
```

三件事值得逐条拆：

**基线是「占用了多少」。** RSS 是第三篇以来反复用的「真实到货」；swap 条目也算，换出去不代表赖掉了账，换回来还得占；连页表都算，第一篇量过页表 512:1 的增长率，杀掉一个大进程连页表一起解放。基线天然偏向杀大户：吃 2GiB 的进程比吃 20MiB 的贵 100 倍，回收效率至上。

**`oom_score_adj` 的参与方式是直接加成分。** ±1000 的范围按 `totalpages/1000` 折算成页数直接加在点上，不参与乘法。本机 15.5GiB 内存下，1 个 adj 点 ≈ 15.5MiB 占用的分。所以 `+200` 的 adj 相当于白送约 3GiB 的占用分，对占几百 MiB 的桌面进程是压倒性的；而 `+1000` 意味着无条件必杀（分数直接溢出为最大），`-1000` 意味着连候选名单都进不了。

**分数换算成 `/proc/<pid>/oom_score`（0~1000 的整数）供人读。** 写 `oom_score_adj` 是进程唯一的自保/自荐通道。内核不提供「别杀我但也不保证」之外更细的语义，粗粒度正是设计：紧急时刻不需要精细权衡，需要的是明确顺位。

### 本机实测：桌面早已排好牺牲顺位

公式说得再多，不如看一眼自己机器的真实配置。本机（KDE 桌面）抽查：

```text
kwin_wayland   oom_score=800  oom_score_adj=+200
plasmashell    oom_score=810  oom_score_adj=+200
zsh（我的终端） oom_score=800  oom_score_adj=+200
```

**整个用户会话的进程，oom_score_adj 全是 +200。** 这是 systemd 的设计（`systemd-oomd` 生态的默认策略）：桌面会话统一调高牺牲级。用意是，真到全局 OOM 那天，窗口管理器、桌面壳、终端这些「挂了能重启」的用户态进程先走，把存活机会让给系统服务和关键守护进程（它们的 adj 是 0 甚至负值）。也就是说：**你每天登录桌面时，牺牲顺位表就已经签好了**，窗口管理器排在你看不见的系统服务前面。这是 `oom_score_adj` 在真实生产环境的一次完整落地，比任何构造的实验都直白。

（注意打分的相对性：800 分在「整个会话都是 +200」的背景下互相抵消，会话内部仍按真实占用排先后，plasmashell 的 810 比 kwin 的 800 高，因为它真的多吃了几十 MiB。**adj 决定组间顺位，基线分决定组内顺位**，两层叠加才是完整顺序。）

## overcommit：承诺的边界

打分之前还有一道更早的闸：分配被允许吗。`/proc/sys/vm/overcommit_memory` 三种模式：

- **0（启发式，本机模式）**：明显荒唐的申请拒绝（比如超过 RSS+swap+page cache 总量），其余放行。Redis 官方建议的 `vm.overcommit_memory=1` 针对的就是它，fork 那篇详细拆过：BGSAVE 的子进程瞬间让「承诺总量」翻倍，启发式可能误杀正常 fork。
- **1（always）**：来者不拒，地址空间随便画（VMA 篇的 256TiB 上限），真不够时靠 OOM 兜底。Redis 的建议本质：**宁可事后 OOM，不要事前误拒 fork**。
- **2（strict）**：承诺总量硬上限 = swap + `overcommit_ratio%` × RAM（本机 ratio=50），超限的 malloc 直接失败。数据库、要强隔离的服务偏好它，**失败发生在 malloc 而不是三天后的凌晨四点**。

三档没有免费午餐：0 可能误拒、1 把矛盾推迟到 OOM、2 让程序必须处理 malloc 失败。选择本质是「你想在哪里收到坏消息」。

## 两套淘汰：内核与应用

现在兑现与 Redis 淘汰策略的对照。两套系统在资源见底时做同一件事，按某种打分丢弃占用者，但取舍几乎处处相反：

| 维度 | Redis 淘汰（应用层） | OOM killer（内核层） |
| --- | --- | --- |
| 丢弃单位 | 键/缓存条目 | 整个进程 |
| 打分依据 | LRU/LFU/TTL 等八种策略，可选 | RSS+swap+页表 + adj，固定 |
| 精细控制 | `maxmemory-policy` 全局切换 | `oom_score_adj` 逐进程微调 |
| 丢弃成本 | 低：删键即完事 | 高：进程状态蒸发，需重启恢复 |
| 预警信号 | `INFO memory` 的内存比 | PSI 压力计数、水位事件 |
| 兜底哲学 | 丢数据保服务 | 丢进程保机器 |

最深的一行是最后的哲学差异。Redis 的淘汰是**日常机制**：它假设丢数据是业务的正常成本，八种策略是八种「谁该被丢」的业务判断。OOM killer 是**异常机制**：它假设杀进程是灾难，整套四级响应（回收→换页→direct reclaim→杀）都是为了把这一刻推到永不来临；真来临时，决策要快（持有锁、禁止递归进 OOM），顺位要提前排好（systemd 的 +200），事后要留全尸检报告（`dmesg` 的 dump 输出，`sysctl_oom_dump_tasks` 默认开）。**应用层把丢弃做成参数，内核层把丢弃做成伤疤。** 这是层级不同带来的分工，不是谁更高级。

## 我踩的坑

本篇原计划的核心实验是「容器内安全复现 memcg OOM」：cgroup v2 的 memory 控制器已委托到用户会话（探测确认），`systemd-run --user --scope -p MemoryMax=64M` 一切就绪。然后实验翻车，翻得很有教育意义，全程记录如下。

**翻车现场。** 64M 限制的容器里，吃内存程序安安稳稳吃满 512MiB 退出。`memory.max=67108864` 确认写入成功，`memory.events` 的 `oom`/`oom_kill` 全零。限制在，触发没发生。

**排查第一层：进程归属。** 怀疑进程根本不在 scope 里。程序自己打印 `/proc/self/cgroup`：在的，路径分毫不差。

**排查第二层：记账。** 采样 `memory.current`：全进程吃入过程中**恒定 155648 字节**，`memory.stat` 的 `anon=98304`、`pgfault=70`。512MiB 的 memset 换来七十次缺页计数，记账根本没发生。手动建 cgroup 目录、直接迁入进程重试：一样。

**排查第三层：横切验证。** 换一把完全独立的尺子：`/proc/self/status` 的 VmRSS。程序吃 512MiB，RSS 报 **2000kB**，全程不动。再试 `/proc/self/oom_score_adj` 写入：`权限不够`，而 `ls -la` 显示它明明是 `-rw-r--r--` 属主可写。

**谜底。** 三把尺子（cgroup 记账、RSS、score）说同一句话：**这个会话的执行环境（我运行命令所在的沙箱）在拦截内存驻留与部分 /proc 写入**。malloc 返回的页被触碰后并未按正常路径驻留记账，64M 的容器限制因此永远等不到它的触发条件。答案不在内核 7.2.3，不在 CachyOS 的补丁，也不在 cgroup 的用法：是我的实验环境本身有一层我没假设过的行为。

四个教训，按疼的程度排序：**其一，多把独立的尺子早该同时上。** 我先怀疑 systemd、再怀疑内核、再怀疑发行版，每一步都只拿一把尺子量；三把尺子（cgroup/current、VmRSS、oom_score）第一次同时读数，谜底三十秒就出来了。**其二，「实验失败」先量环境再怪系统。** 排查顺序应该从最近的假设（我的环境）开始，我却从最远的（内核 bug）开始。**其三，负结果要留全尸。** 如果第一轮翻车就放弃，这篇文章会少掉一节最有价值的内容。**其四，沙箱里做系统实验，先跑一次「吃 100MiB 看 RSS 涨不涨」的环境自检。** 这个自检脚本我现在留在了实验目录里，以后每个系列开工前先跑它。

排查路上还有几样副产品，全都进了正文：桌面会话 adj=+200 的发现、zram swap 的配置（15G 配额、当下用了 4.8G，第一级响应里「换出匿名页」的主力正是它，压缩换出而非磁盘换出）、PSI 的累计压力。

## 内存系列的最后几条规矩

内核对内存短缺的响应有四级，杀进程是最后一级：水位回收（kswapd 后台丢缓存）、direct reclaim（申请者自己停下来等）、全局 OOM、memcg OOM（容器内独立触发）。OOM killer 的触发条件，是便宜的选项全部用完。打分公式是基线分加直接加成分：基线 = RSS + swap 条目 + 页表页数，天然偏向杀大户；`oom_score_adj`（±1000）按内存总量折算直接加分，+1000 必杀、-1000 免死；adj 决定组间顺位，基线分决定组内顺位，本机桌面会话的 +200 是这套两层机制的活教材。overcommit 三档是「坏消息送达时机」的选择：启发式可能误拒 fork，这是 Redis 建议 1 的由来；always 把矛盾推迟给 OOM；strict 让 malloc 当场失败。没有免费午餐，只有提前挨刀和延后挨刀。Redis 的淘汰与这套机制是两层分工：应用层把丢弃做成参数，八种策略、丢数据保服务；内核层四级缓冲、固定公式、丢进程保机器。两级叠加才是完整的生存设计，所以 Redis 在容器里既配 `maxmemory` 做应用层淘汰，也该配 `oom_score_adj=-500` 一类自保，别把命运全交给任何一级。最后一条留给实验方法：本篇最大的翻车发生在沙箱里，谜底不在内核也不在 cgroup，在「吃内存」这个动作被环境拦截而 RSS 不动。多把独立尺子同时上、从最近的假设开始查、负结果留全尸，这三条比任何一次成功的复现都更接近「实验方法」本身。

系列七篇到这里收束。从第 0 篇的三样东西出发：页表画好了地图，缺页与 COW 搬完了东西，伙伴系统与 slab 盘清了仓库和柜台，VMA 与 page cache 记完了地址和文件的账，最后这道保险丝也拆了。内存从申请到占用到回收到牺牲，一条线走到底。

那张牺牲顺位表，在你登录桌面的那一刻就签好了；下一次真的 OOM，`dmesg` 里能读到它。
