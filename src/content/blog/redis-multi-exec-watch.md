```text
MULTI
SET k1 v1          → QUEUED
INCRBY k1 ten      → QUEUED        （入队时合法：k1 还不存在）
SET k2 v2          → QUEUED
EXEC               → OK / ERR / OK

第三条照样执行了。没有回滚，没有半途弃单。
```

用过关系型数据库的人到这里都会愣一下：一条失败，其余照常提交，这也叫事务？

Redis 的回答是：**它从来没承诺过你熟悉的那种事务**。MULTI/EXEC 提供的是「打包」和「隔离」——队列里的命令连续执行，中间不插入其他客户端的操作；它不提供「要么全成功要么全失败」的原子提交，更没有 ROLLBACK。官方文档对此毫不讳讳：不支持回滚是因为错误应当由开发进程解决，而不是留给运行时兜底——语法错误在入队时就被拦下，类型错误是程序 bug，靠回滚掩盖只会让 bug 藏得更深。

这一篇把这套协议拆开：命令排队时发生了什么、两道检查门各自的职责、WATCH 怎么用「弃单」替代锁、过期键上的特例，以及官方那句「用 Lua 脚本更好」到底好在哪。实验在官方 Redis 7.4.11 容器中完成，源码名称以该版本为准。

## 排队：QUEUED 不是执行，只是登记

MULTI 之后的画风突变。普通命令会立刻执行并返回结果，MULTI 上下文里的命令却只回一个 `QUEUED`：

```text
127.0.0.1:6379> MULTI
OK
127.0.0.1:6379> SET k1 v1
QUEUED
127.0.0.1:6379> INCR k1
QUEUED
127.0.0.1:6379> EXEC
1) OK
2) (error) ERR value is not an integer or out of range
```

源码里这一步很朴素：`processCommand` 发现客户端带着 `CLIENT_MULTI` 标志，就不调用命令的实现，而是 `queueMultiCommand()` 把 argv 整个搬进 `mstate.commands` 数组——参数对象连引用计数一起转交，客户端结构体上则清空。命令数组按 2 起步、倍增扩容，和多打了一场交道的只有内存，不碰数据。

入队的资格也有边界：`MULTI`、`EXEC`、`DISCARD`、`WATCH`、`RESET` 不排队（各自管理事务本身），阻塞命令（BLPOP 等）被显式拒绝——队列一旦执行就是一口气，中间停下来等数据会把「连续执行」的承诺撕开一个口子。

## 两道门：入队时拦语法，执行时报类型

事务的错误处理之所以显得拧巴，是因为检查分在两道门上，行为完全不同。

**第一道门在入队时**：命令名存不存在、参数数量对不对、内存够不够。任何一条不通过，客户端被打上 `CLIENT_DIRTY_EXEC` 标记，此后继续排队的命令直接被忽略（省内存），EXEC 一到就是终审：

```text
127.0.0.1:6379> MULTI
OK
127.0.0.1:6379> SET onlyonearg
(error) ERR wrong number of arguments for 'set' command
127.0.0.1:6379> SET k3 v3
QUEUED
127.0.0.1:6379> EXEC
(error) EXECABORT Transaction discarded because of previous errors.
```

`EXECABORT`，整单弃掉，`GET k3` 确认什么都没发生。**语法错误是全有全无的**——这是事务里唯一「像事务」的部分。

**第二道门在执行时**：命令合法，但对不上数据。开头的实验就是这一类：`SET k1 v1` 先把 k1 变成了字符串，轮到 `INCR k1` 时类型错误——但 EXEC 的循环不因此停摆，下一条 `SET k2 v2` 照常执行。实测确认：

```text
执行前  k1 = "v1"     k2 = "v2"
EXEC 返回  1) OK  2) (error) ...  3) OK
执行后  k1 = "hello"  k2 = "world"
```

k1 被 SET 成功改写，错误只属于 INCR 那一条。**Redis 在这里选择的是「报告，不收拾」**：每条命令的回复按原顺序放回一个数组，对错由客户端自己看。理由值得原味转述：能通过第一道门的命令，执行期错误只剩「逻辑错误对错误的数据类型」（编程错误）和「内存不足」两类；前者该在开发期修，后者回滚也救不了——Redis 5.0 起内存不足时连实例都会拒绝写入。为这两种场景维护一套撤销日志，官方的判断是不值得。

## 隔离：串行柜台送来的免费午餐

「事务执行期间没有其他客户端插队」——这个性质听起来昂贵，实际上没花一分钱。

事件循环篇讲过那个核心事实：**键空间命令由主线程串行执行**。EXEC 收到后，`execCommand` 把队列里的命令逐条送进同一个 `call()`，中间不回到事件循环——对这个客户端来说是原子批处理，对其他客户端来说，这批命令和一条命令没有区别。隔离不是事务机制实现的，是单线程执行模型的副产品。

一个容易被忽略的细节是传播。EXEC 期间每条命令的 AOF/副本传播被延迟到整个执行单元结束，由 `propagatePendingCommands()` 统一发送——所以**副本看到的事务也是完整的一批**，不会出现主库 EXEC 了一半、副本只重放半批的窗口。AOF 篇讲过的命令流水，在这里以「批」为单位落账。

还有 ACL 的一层：入队时检查过权限，EXEC 时会**再查一遍**——管理员可能在你排队和执行之间改了权限。这类错误同样只作废当前条目并回复 NOPERM，不影响批的其余部分。

## WATCH：用弃单替代锁

到目前为主，事务还只是「打包」；真正的并发控制由 WATCH 补上，而它的思路是乐观锁：

```text
WATCH key [key ...]
……（读旧值、本地计算新值）……
MULTI
……（写命令入队）……
EXEC
```

`watchForKey` 把键登记进数据库的 `watched_keys` 字典。此后**任何客户端**修改这些键——SET、DEL、过期删除、甚至另一个事务——`touchWatchedKey` 都会顺着字典找到所有观察者，打上 `CLIENT_DIRTY_CAS`。EXEC 开头验标记：脏了就返回空数组（不是错误，是 nil 多批量回复），整单作废；干净才执行。

完整走一遍经典的「读-算-写」竞争：

```text
客户端 A                          客户端 B（插队者）
WATCH bal
GET bal → 100
                                  SET bal 75
MULTI
SET bal 300        （基于过期值 100 算出）
EXEC → (nil)  ← 整单作废
GET bal → 75                       ← 300 从未落盘
```

关键在最后一步：A 基于陈旧的 100 算出的 300 **没有写入**，余额保持在 B 写入的 75。这就是 CHECK-AND-SET 的完整闭环——不是防住别人改，而是**别人改了我就放弃**。客户端拿到 nil 后重新读值、重新计算、重新提交，循环直到成功。高竞争下这套协议会反复重试，但 Redis 的负载画像（短命令、低冲突）让它比悲观锁便宜：不用维护等待队列，不用处理死锁，冲突的代价只是一次重试。

被修改污染是单向的：一旦 DIRTY_CAS，`touchWatchedKey` 顺手把该客户端的所有观察注销——反正 EXEC 必弃，留着观察只浪费内存。UNWATCH 和 DISCARD 也会清空；EXEC 结束（无论成败）事务状态一律复位。

## 过期键的特例：WATCH 一个「本来就不存在」的键

WATCH 与 TTL 交互时有个精细的特例，值得单独看。

`watchForKey` 登记时记下一个快照：这个键**在 WATCH 时刻是否已经过期**（`wk->expired` 标志）。两种情形走向完全不同：

**WATCH 时键活着，之后才到期**：EXEC 开头 `isWatchedKeyExpired` 检查当前状态，发现它已过期——打 DIRTY_CAS，弃单。逻辑很直：你观察的是一个会消失的值，它消失了当然算「被改过」。

**WATCH 时键就已经过期**：这个键在逻辑上等于不存在，你观察的本来就是「无」。之后它被惰性删除或主动过期回收，都不算变化——键空间通知、副本传播里它也表现为 `del`，但对这个观察者而言，「不存在」到「不存在」没有状态转移。实测确认：

```text
SET gone v PX 100 ；等待过期
WATCH gone        （此刻 gone 已经过期）
MULTI / SET gone resurrect / EXEC
→ 事务成功执行，gone = resurrect
```

不是 bug，是「逻辑不存在」与「物理删除」分离的又一次出现——过期篇里为 TTL 讲过的那对概念，在 WATCH 的语义里原样重现。

## 与 Lua 对质：官方为什么说脚本更好

Redis 官方文档在 MULTI/EXEC 一节的末尾放了段不那么客气的建议：除了历史原因，**用 Lua 脚本更简单更快**。拆完两边机制，可以给这句判词一个结构性解释。

MULTI 事务的根本限制：**命令入队时不能读**。`QUEUED` 只是登记，事务里没有「看一眼再决定」的分支——SET 的值必须在 MULTI 之前就算好。所以「读旧值、算新值、条件写入」只能靠 WATCH 在外面搭脚手架：WATCH、GET、MULTI、SET、EXEC 五步，外加冲突重试循环。

Lua 脚本把这套逻辑搬进了服务端：

```text
EVAL "if redis.call('GET', KEYS[1]) == '100' then
        return redis.call('SET', KEYS[1], ARGV[1])
      else return 0 end" 1 bal 300
```

脚本整体和一条命令同权：主线程执行期间不插队，读和算发生在服务端本地，不存在「读算之间被插队」的窗口，也就**不需要 WATCH、不需要重试**。网络往返也从五次坍缩成一次。

代价在别处：脚本是排他资源（同一时刻只有一个脚本在跑），长脚本会把串行柜台堵成事件循环篇里那条队；EVAL 的文本每次都要传输，缓存 EVALSHA 又引入脚本丢失的边角；调试也远不如客户端代码方便。所以那句官方判词的完整版应该是：**短小、读算写交织的逻辑用 Lua；纯粹想把一批写打包、或需要配合 WATCH 做乐观锁的，MULTI/EXEC 仍然是对的工具**。

## 成本：MULTI 不是性能工具

最后一个常见误会值得当场拆掉：MULTI 不是为性能设计的。

实测对照，500 条 SET 三种发送方式：

```text
逐条发送（等每条回复）            慢      （往返主导）
流水线直发（一次性发送 500 条）    0.1 毫秒
MULTI + 队列 + EXEC（同样流水线）  0.4 毫秒
```

流水线化之后，MULTI 比裸 pipeline 慢——队列拷贝、EXEC 的调度都是真实开销。MULTI 买到的是语义（打包、隔离、CAS），不是吞吐；批量写的吞吐工具是 pipeline，两者解决的问题不同。顺带一个内存提醒：队列在服务端按参数原样持有，`multi-mem` 在 CLIENT LIST 里可观——百万级参数的事务会把这份拷贝放大到不容忽视。

## 账单，按承诺范围再算一遍

**MULTI/EXEC 是打包与隔离，不是原子提交。** 队列里的命令连续执行、不插队，这是单线程模型的免费副产品；但没有回滚——执行期错误只报错那一条，其余照常。

**两道门的分工要记牢。** 入队期错误（语法、参数数量）→ EXECABORT 整单弃；执行期错误（类型、权限变更）→ 逐条报告，批不散。写代码时应该只依赖第一道门。

**WATCH 是乐观锁，弃单替代锁。** 任何客户端的修改都会弄脏观察者，EXEC 返回 nil；客户端重读重算重试。WATCH 时已过期的键视同不存在，其后的物理删除不算修改。

**Lua 脚本是「读了再写」的正解。** 事务里不能读，是 MULTI 一切别扭的根源；脚本把读算写搬进服务端单命令边界内，WATCH 和重试都可以省掉——代价是脚本要短。

**别用 MULTI 提吞吐。** 流水线才是批量工具；MULTI 的队列拷贝和执行调度是净开销，买的是语义不是速度。

---

```text
QUEUE  QUEUE  QUEUE
门一：参数齐吗？齐。
门二：类型对吗？——到执行时再问。
EXEC：一条条过闸，错了记一笔，队伍不停。
```

Redis 的事务像一列不回头的火车：检票口（入队检查）拦得住写错站名的旅客，上了车才发现坐错方向的（类型错误），只能在广播里通报一声，车照样往前开。想中途改道？那不是列车的能力，是你出发前就该想清楚的事。

对「事务」这个词的预期越像关系型数据库，这套协议就越显得简陋；把它看成「一批命令的免插队通道 + 一枚版本探针」，每个设计选择就都对上了。
