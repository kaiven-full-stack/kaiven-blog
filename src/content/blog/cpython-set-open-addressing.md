```text
同样 170 个 int 元素：
dict（带值）  4,688 字节     27.6 B/条目
set（只有键）  8,408 字节     49.5 B/条目

只存一半的数据，占了双倍的内存。
```

dict 篇拆过那张「索引表 + 条目表」的分层哈希表——条目表紧凑连续，索引表只存小整数下标，删除不挖洞只标灰。这是 3.6 时代 dict 的革命。可同一个解释器里还有另一张哈希表：set。它没有跟着改造，仍守着最古典的开放寻址——单张表、槽内直接存键和哈希、碰撞了就地往后探。

于是出现了开头的账单：set 每存一个键的成本，接近 dict 存一个键值对的两倍。这不是 set 被遗忘，而是一次坦诚的取舍——**分层设计的收益属于「插入序 + 共享键 + 紧凑条目」这些 dict 独有的需求，set 都用不上**。这一篇把 set 的古典方案拆开，看它贵在哪、又换来什么，最后实测它的死穴。实验在 CPython 3.14.7 上复核，源码以 3.14 分支为准。

## 先看结构：一张表，两种账

PySetObject 没有分层，只有一槌子买卖：

```c
typedef struct {
    PyObject *key;       /* 8 字节：元素指针 */
    Py_hash_t hash;      /* 8 字节：缓存的哈希值 */
} setentry;

typedef struct {
    ...
    setentry *table;         /* 槽位数组本体 */
    Py_ssize_t fill;         /* 占用 + 墓碑 */
    Py_ssize_t used;         /* 实际元素 */
    setentry smalltable[8];  /* 前 8 槽内嵌，免 malloc */
} PySetObject;
```

对照 dict 的方案，差异一目了然：

```text
dict：索引表（1/2/4 字节下标）→ 条目表（key+value+hash 连续存放）
set ：槽位直接是 {key, hash} 二元组，16 字节一槽
```

每槽 16 字节 vs dict 索引项的 1–4 字节，这就是账单悬殊的主因。**dict 把「表」和「数据」分离后，表可以缩到极致；set 的表和数据焊在一起**，哈希值还得每个槽存一份（它没有第二张表可以挪去）。

`fill` 与 `used` 的差值是墓碑（dummy）数——被删元素的槽。dict 篇见过同款概念，但 set 的墓碑直接占着活动槽位，参与探测链的成本，这在后面要专门算账。

还有一处古典遗风：`smalltable[8]` 内嵌。小 set 的前 8 个槽直接长在对象体里，连 malloc 都省了。dict 的 64 字节空表也来自同款设计，但 set 起步就带 8 槽（216 字节 vs dict 的 64 字节）——**空 set 比空 dict 贵三倍多**，小对象极多的场景里这不是零头。

## 探测：九连探再跳跃

碰撞处理是开放寻址的灵魂。hash 落到槽 i，若被占，往哪找下一个？set 的答案是混合式两段舞（`set_add_entry`）：

```c
i = hash & mask;
perturb = hash;
while (1) {
    /* 第一段：从 i 开始的 LINEAR_PROBES=9 次线性探测 */
    probes = (i + LINEAR_PROBES <= mask) ? 9 : 0;
    do { 检查 entry++; } while (probes--);
    /* 第二段：换阵地，重新散列 */
    perturb >>= 5;
    i = (i * 5 + 1 + perturb) & mask;
}
```

**第一段九连探**：从落点开始一口气看接下来 9 个槽。线性探测的毛病是聚集（clustering），但小范围内的聚集几乎是免费的——9 个连续槽大概率同在一两个缓存行里，一次内存总线取数全带上。**第二段跳跃**：九连探落空说明这一带满了，`i*5 + 1 + perturb` 跳到表的另一头重来，`perturb` 每轮右移 5 位，把哈希值的高位比特逐步搅进探测位置——保证最坏情况下所有槽都会被访问到。

这套「先扫描后跳跃」的编舞是缓存时代的产物。纯线性探测聚集严重，纯双重散列每次探测都是一次缓存 miss；九连探用 9 次换 1 次 miss 的汇率，在两者之间买平衡。dict 篇的 `perturb >>= 5` 递推在这里原样出现——**dict 的索引表探测抄的就是 set 的作业，只是 dict 从来不需要 LINEAR_PROBES**（它的索引表小到整表都在缓存里）。

## 扩容：五分之三就搬家

`set_add_entry` 的收尾处写着扩容条件：

```c
if ((size_t)so->fill*5 < mask*3)
    return 0;                              /* 还够用 */
return set_table_resize(so, so->used>50000 ? so->used*2 : so->used*4);
```

**fill 超过槽位的 3/5 就扩**，新尺寸取 used 的 4 倍（大表 2 倍）。注意分子是 fill 不是 used——墓碑也算压力，因为它们参与探测成本。实测的容量跳变点与公式严丝合缝：

```text
n=17   728 字节（32 槽）      n=21   2,264 字节（128 槽）
n=85  8,408 字节（512 槽）    n=171 33,064 字节（2048 槽）
```

8、32、128、512、2048——每个跳变点都在 fill 触及 3/5 时。对比 dict 的 2/3 负载上限：set 收得更紧，因为它没有索引表可以分摊探测成本，聚集在单表结构里加倍致命。

而 `used > 50000 ? ×2 : ×4` 这个分支是 2008 年 Guido 亲自改的（commit 注释还在源码里）：大 set 翻 4 倍太浪费内存，翻 2 倍；小表多翻点，减少 rehash 频率。**负载因子与扩容倍率的每个数字，都是「探测成本 × 内存空转 × rehash 频率」三方的停战线**。

## 墓碑：删除不搬家，只立碑

删除是开放寻址最麻烦的操作。直接把槽清空，会截断经过它的探测链——后面同哈希的元素就「找不到了」：

```text
槽 10: A（hash→10）
槽 11: B（hash→10，被 A 挤过来的）
清空槽 10 后查 B：从槽 10 开始探，槽 10 空 → 判定不存在 ✗
```

set 的解法是墓碑（dummy）：删 A 时槽 10 换成一个特殊标记对象，**占位但不等于任何键**。探测链经过墓碑不停下（继续往后找），但插入遇到墓碑可以复用。于是：

```text
查找：空槽 → 停（不存在）；墓碑 → 跳过；匹配 → 命中
插入：记住第一个墓碑，找一圈没找到就复用它
```

实测的墓碑残留：一千个元素的 set 全部 discard 后，**len=0 但 sizeof 纹丝不动**（33 KB 的表原封不动）——空了 99% 的表不会自动收缩。再往里 add，新元素住进墓碑的槽位，表也不涨。只有扩容 rehash 或显式重建（`set(s)`、`s |= set()`）才清走墓碑、归还内存。

dict 篇的对应设计是「索引表标灰」——同款思想，但 dict 的灰标记只占索引项 1 个比特，set 的墓碑占满 16 字节一槽。**又一处单表结构的税**。长时间「增删循环」的 set（比如滑动窗口的 id 集合），实际内存由峰值决定而非当前规模，这是容量评估必须带的一笔。

## 顺带的红利：set 的快

贵有贵的道理，set 也拿回了 dict 拿不到的东西。

**成员检查与 dict 同速甚至更快。** 一百万元素的容器里查一万次：set 2.60 ms、dict 3.53 ms。dict 的 `in` 走完索引表还要跳到条目表核对，set 命中槽位即得键——单表结构少一次间接寻址。

**frozenset 免费。** dict 无法整体哈希（可变），frozenset 可以缓存整表的哈希值做 dict 的键。set 和 frozenset 共享同一套布局（`sizeof` 完全相同），一个 `__hash__` 和一组不可变约束就是全部区别——这是「set 只有键没有值」送的设计福利。

## 死穴实测：全部同哈希

开放寻址的命运系在哈希分布上。构造恶意键——哈希函数全部返回同一个值——古典方案立刻原形毕露：

```python
class Bad:
    def __hash__(self): return 42      # 所有人挤在同一个槽
    def __eq__(self, o): return self.v == o.v
```

实测往 set 里逐个插入：

```text
n=500    10.8 ms
n=1,000  43.3 ms     （2 倍规模 → 4 倍耗时）
n=2,000  162.8 ms    （2 倍规模 → 3.8 倍耗时）
```

漂亮的二次方曲线。九连探在这里帮不了忙（同一落点，探完 9 个还是这群人），perturb 跳跃也只是换一群同样的人——**每次插入都要 O(n) 次比较才能找到空槽**。dict 面对同样的攻击退化得更狠（它连 LINEAR_PROBES 都没有），这也是 str 的哈希默认加盐（PYTHONHASHSEED）的原因之一——不让外部输入预测哈希分布。

日常代码里的「意外同哈希」没这么极端，但方向相同：自定义类忘了写 `__hash__`（默认用 id，分布尚可）、或写了糟糕的 `__hash__`（比如 `return 1` 的老代码），set 的性能就悄悄滑向这张表。**重写 `__eq__` 必须同时重写 `__hash__`**，不单是语义正确（相等对象必须同哈希），也是这张表的性能契约。

## 为什么 dict 改了，set 没改

回到开头的悬案。3.6 的 dict 改分层时，set 明显是候选，为什么没动？

分层设计的红利逐项对账：**紧凑条目表**——set 的条目本来就只有 key+hash，再分层要多一次间接寻址，白付；**共享键配额**——dict 实例的键可与对象属性共享（attribute 篇的那套），set 无此场景；**插入序**——set 语义上无序，白送也不要。而分层把「表」和「数据」拆开后，单次访问从一次寻址变两次——恰好是 set 成员检查现在的优势，拆了反而丢。

于是答案变成：**dict 的分层是为 dict 的需求定制的，set 的需求清单几乎全不重合**。保持古典单表，set 拿到了更快的命中路径和更简单的结构；付出的是每槽 16 字节、墓碑全额占位、更低的负载上限。两种哈希表活在同一个解释器里，是「按需选型」而不是「历史欠账」——虽然 216 字节的空 set 起步价，确实有历史遗风的成分（smalltable 的 8 槽内嵌）。

## 观测与边界

```text
sys.getsizeof(s)             216 + 16 × 槽数（超出内嵌 8 槽后）
len(s) vs 容量跳变            8→32→128→512→2048（fill 3/5 触发）
sys.hash_info                哈希宽度、算法、PYTHONHASHSEED 的语义
s = set(s)                   清墓碑重建：长寿命高删除 set 的保养动作
```

容量估算的经验值：int 元素的 set 约 16 × n / 0.6 ≈ **27 字节/元素**（不含元素本体；小 int 免费，见 int 篇），对比 dict 键值对的约 50 字节——**set 贵的是「每键」，dict 贵的是「每条目」，键值各半时 dict 反而更省**，这是选型时最容易弄反的一处。

边界照例如实：3.14 的 set 没有插入序保证（dict 有，3.7+）；迭代中修改 set 会 RuntimeError（dict 同样）；墓碑表不自动收缩，峰值内存要按 fill 的历史最高点算。

## 账单，按槽再算一遍

**set 是单表开放寻址，每槽 16 字节存 {key, hash}。** 与 dict 的索引表+条目表分层相对：贵约一倍每键，换来命中路径少一次间接寻址。

**探测是「九连探 + perturb 跳跃」的混合编舞。** 9 次线性探测吃缓存红利，`i*5+1+perturb`、`perturb >>= 5` 保证全覆盖；dict 的探测递推同源，但没有九连探。

**fill 过 3/5 就扩容，小表 ×4 大表 ×2。** 跳变序列 8/32/128/512/2048 实测吻合；墓碑计入 fill——删除也在给扩容施压。

**删除立墓碑，探测链不断。** 空表不自动收缩：一千元素删光，33 KB 原样保留；长寿命 set 用 `set(s)` 重建清碑。

**同哈希是命门，二次方退化实测在案。** 全同哈希键 2 倍规模 4 倍耗时；`__eq__` 与 `__hash__` 的配套重写既是语义也是性能契约。

**dict 不改 set 不是欠账，是选型。** 分层的三项红利（紧凑条目、共享键、插入序）set 全用不上；单表换来的命中速度和 frozenset 福利，是它自己的账。

```text
hash(A) → 槽 10。

查 C：槽 10、碑 11、命中 12。
墓碑不说话，但链子没断。
```

三张哈希表的旅程到这里齐了：CPython 的 dict 把索引和数据分层，CPython 的 set 坚守古典开放寻址，Redis 的 dict 用链地址加渐进式搬家。同一位作者的两个作品在同一个解释器里并存，各自对「探测、扩容、删除」三道必答题交出不同答卷——数据结构没有标准答案，只有出题时的场景。
