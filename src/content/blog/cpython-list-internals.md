```text
append 一百万次：realloc 只发生约 60 次
insert(0) 一百万次：内存搬运了约五千亿次

同一个动态数组，同样一百万个元素，
一个把搬摊成了零头，一个把搬全数照付。
```

list 是 Python 里被使用得最不经意的容器。它看起来是链表——随长随加、随处插删——但 CPython 的 list 是一块**连续的指针数组**：每次扩容是一次真正的内存搬家，只是搬得足够聪明。开头的两组数字是同一枚硬币的两面：聪明的时候（append），一百万次增长只需六十次搬迁；用错姿势的时候（insert(0)），每一次插入都是一场全队平移。

对象布局篇看过 PyObject 的头，dict 篇看过「索引表 + 条目表」的分层，这一篇看最后一个大头：PyListObject。实验在 CPython 3.14.7 上复核，源码以 3.14 分支为准。

## 先看本体：一排指针，不是一排对象

PyListObject 只有三样东西：

```c
typedef struct {
    PyObject_VAR_HEAD          // 引用计数、类型、长度 ob_size
    PyObject **ob_item;        // 指向指针数组的开头
    Py_ssize_t allocated;      // 实际分配的槽数
} PyListObject;
```

关键在 `ob_item` 指的那块内存：**数组里存的是 PyObject 指针，不是对象本身**。`[1, "a", [2]]` 的三个元素住在全国各地，list 里只有三个 8 字节的门牌。所以 `sys.getsizeof(lst)` 量的是「门牌架」的尺寸，元素本身另算——这是容量评估最常见的漏项：一个百万元素的 list 本体 8MB，但元素如果是百万个独立 int，还得再加上每个 28 字节的对象本体（对象布局篇的账单）。

`ob_size` 是在册的元素数（`len()` 直接读它），`allocated` 是架子上的实际槽数。两者之间的差，就是这一篇的主角：**过度分配**。

## append 的账本：12.5% 的余量

append 遇到架子满了要扩容。CPython 的扩容公式（`list_resize`）是：

```c
new_allocated = (newsize + (newsize >> 3) + 6) & ~3;
```

多租 `newsize/8 + 6` 字节再对齐到 4：大约 **12.5% 的余量，外加一点起步补贴**。源码注释里直接给出了增长序列：

```text
0, 4, 8, 16, 24, 32, 40, 52, 64, 76, ...
```

实测逐个 append 并跟踪 `sys.getsizeof`，容量跳变的序列完全对上：

```text
len   1   5   9  17  25  33  41  53  65  77  93
cap   4   8  16  24  32  40  52  64  76  92 108
```

为什么要多租？纯粹的成本摊销。如果每次满员都恰好扩一格，一百万次 append 就要一百万次 realloc——每次都是「申请新内存、拷贝全部指针、释放旧内存」。多租 12.5% 后，第 n 次扩容只需在 n 增长 12.5% 时发生：**搬家的总成本被摊薄成每次 append 的常数级零头**，这就是「均摊 O(1)」四个字的物理含义。代价是平均约 6% 的内存空转（多租 12.5% 的均值），以及地址不连续——每次 realloc 后整个数组搬到新家。

公式里还有个贴心的细节：`+6` 是给小 list 的起步补贴（前几次扩容不至于 1 格 1 格地抠），`& ~3` 对齐到 4 槽减少 realloc 次数。而 3.14 新增的判断「新尺寸更接近过度分配尺寸时取消过度分配」堵了另一头的浪费：`lst[1000:2000]` 这种一步到位的大扩展，不再先算出一个巨大的余量。

## 3.13/3.14 的新面貌：构造器精确分配

上面的增长序列在 3.13 之前是 list 的唯一性格。3.13/3.14 起分裂成了两种：

```text
list(range(100))   →  sizeof 精确 = 56 + 100*8   （容量 == 长度）
[...] 逐个 append  →  容量按增长序列跳变（4, 8, 16, 24…）
```

实测对照（同一长度、不同出生方式）：

```text
list(range(n))   cap = n        （list_preallocate_exact）
append 构造      cap = 增长序列
```

源码里是 `list_preallocate_exact`：**知道最终尺寸的构造路径不再多租**。`list(range(n))`、`list(iterable)` 这类「一次性到货」的场景，直接精确分配——反正马上就要用满，余量只会浪费。而逐个 append 无法预知未来，仍走 12.5% 的老路。

这个分裂给性能测量添了个坑：`sys.getsizeof(list(range(n)))` 在新旧版本里数字不同（3.12 还会过度分配）。容量评估的脚本如果拿构造器造样本，会严重低估 append 场景的内存——**测量过度分配，必须用 append 路径构造样本**。

## 收缩：跌到一半才还地

扩容有公式，收缩也有对称的规矩：`list_resize` 开头有一条快速通道——新尺寸不小于已分配容量的一半时，只改 `ob_size`，不动内存；**跌到一半以下才 realloc 缩小**。

实测从 cap=1100 的 list 逐个 pop，精确捕捉到收缩点：

```text
cap 1100 → pop 到 len 550：缩到 620
cap  620 → pop 到 len 310：缩到 352
cap  352 → pop 到 len 176：缩到 200
```

每次都是「半数触发、缩到下一个增长序列档位」。这套对称设计让 pop 也获得均摊 O(1)：不至于每 pop 一次就 realloc 一次（那会把抖动列表变成 realloc 风暴），也不至于删到只剩一个元素还占着千座仓库。

值得留意的副作用：一个从百万元素 pop 到十个的 list，中间要经历约二十次半数收缩，每次都是全量指针搬运。**从尾部消费列表是健康的；消费完立刻丢弃也是健康的；半途而废的 pop 链是最贵的**——反正架子迟早要还，不如切片一次到位（`del lst[:k]` 一次 resize）。

## insert(0)：O(n) 不是理论，是五百倍

指针数组的代价在头部操作上全额兑现。`insert(0, x)` 要把现有全部元素向后挪一格——memmove 一整个指针数组：

```text
n=1,000     insert(0)×n   0.2 ms     append×n   0.03 ms
n=10,000    insert(0)×n  18.1 ms     append×n   0.30 ms
n=100,000   insert(0)×n  1806 ms     append×n   3.39 ms
```

十万元素时差五百倍，而且差距随 n 线性拉大——这正是开头的第二组数字：一百万次 `insert(0)` 是约五千亿次指针搬运的总和，1806ms 里几乎全是 memmove。`pop(0)` 同理对称。

把元素「倒序塞进 list」的正确姿势是 `append` 完再 `reverse()`（O(n) 一次），或者干脆用 `collections.deque`——它是分块链表，两端操作都是 O(1)。**list 的形态决定了它适合「尾部增长、随机访问」**，这两件事它比任何容器都快（下标访问就是一次指针数组的寻址）。

## sort：动态数组的意外福利

顺带说一件指针数组结构送的事：`list.sort()` 的 Timsort 之所以高效，一部分根基就在这里。排序挪动的只是指针（8 字节一次），比较才调用元素自己的 `__lt__`——**搬运和数据访问解耦**。对大对象排序时，这个解耦让 Timsort 的归并搬移几乎免费，成本集中在真正的比较上。

3.14 的 sort 实现仍是 Timsort 的加强版（小段二分插入、识别既有顺序的 run、galloping mode），配合上篇特化篇讲的比较操作自适应特化，`sort` 已经把「解释器里排序」的极限压得很低。同数据的排序在 C 层和 Python 层的差距，远小于想象。

## 一次到齐，一次装订

把三段行为并排，list 的性格就完整了：

```text
append / pop        均摊 O(1)：12.5% 余量摊薄搬家
insert(0) / pop(0)  O(n)：每一次都是全队平移
sort                O(n log n)：挪指针不挪对象
list(range(n))      精确分配：3.13+ 的「一次性到货」优化
```

同一个指针数组，四种操作四种价格。性能问题的答案不在「list 快不快」，在「你把它当什么用」。

## 观测与边界

```text
sys.getsizeof(lst)          门牌架尺寸；56 + 8*allocated
len(lst)                    在册数 ob_size
lst.__sizeof__()            同上（不含对象本体的提醒依然成立）
tracemalloc / pymalloc 篇   元素本体的账单归属
```

评估 list 内存的一条经验公式：`56 + 8 × capacity`（架子）加上每个元素对象本体的总和。元素是小整数（-5..256 缓存，见下一篇）时本体免费；元素是独立字符串或对象时，本体通常比架子贵一个数量级。

边界也要如实：过度分配的余量在 3.12 与 3.14 之间经历了精确分配改造，网上的旧数字（如「list(range(8)) 占 120 字节」）多半对应旧版本；`getsizeof` 从不递归，嵌套结构的总量要自己乘。

## 账单，按操作再算一遍

**list 是指针数组，不是链表。** `ob_item` 指向连续的 PyObject 指针，`ob_size` 在册、`allocated` 实租。随机访问是寻址，头部插删是全队平移——先看操作再看容器。

**append 均摊 O(1) 的物理含义是六十次搬家。** 12.5% + 6 的过度分配，让一百万次 append 只触发约六十次 realloc，增长序列 4, 8, 16, 24, 32…实测与源码公式逐项吻合。

**收缩对称：跌到一半才还地。** pop 到一半容量才缩到下一档，同样均摊 O(1)；「pop 到一半就停」是最贵的消费姿势。

**3.13+ 的构造器精确分配改变了老数字。** `list(range(n))` 不再多租，append 路径不变；测量过度分配必须用 append 构造样本。

**insert(0) 慢五百倍不是缺陷是几何。** 需要「往头部加」的场景，答案从第一天起就是 deque 或 append+reverse。

---

```text
第 1 次 append：租 4 格，用 1 格。
第 5 次 append：搬去 8 格的家，留下 3 格余量。
第 9 次 append：搬去 16 格。
……
第 1,000,001 次 append：这是一路上的第六十次搬家。
```

过度分配的本质是一场对未来谦逊的赌博：多租一点，赌你会继续来。赌注小（12.5%），赔率高（搬场次数除以八），而 Python 押注的场景——「list 会继续增长」——在真实代码里几乎总是成立。
