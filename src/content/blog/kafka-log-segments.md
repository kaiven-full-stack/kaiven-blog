```text
$ kafka-dump-log.sh --files kseg-0/00000000000000000000.log
baseOffset: 0 lastOffset: 4 count: 5 baseSequence: 0 lastSequence: 4
producerId: -1 partitionLeaderEpoch: 0 position: 0
CreateTime: 1789143164710 size: 296 magic: 2
compresscodec: none crc: 4059270002 isvalid: true
```

这不是一段日志，这是一条消息的户口本。上一篇一条消息的旅程只走到「落进某个分区、拿到一个 offset」的表层；这一篇下到磁盘现场，看它到底以什么形态存在、凭什么被找到、又凭什么「被删除」。MySQL 系列第一篇从 B+ 树开始——为了找到一页数据要层层下降、随机 I/O；这个系列的存储篇从反面开始：**Kafka 连「找」这个动作都省了，因为它是追加的，队尾永远在文件的末尾**。同一块 NVMe，两种命运。

工具是 Kafka 自带的 `kafka-dump-log`，直接把二进制翻译成人话。实验环境一个 1MB 滚动的小段 topic（细节在实验笔记里），先把每一站挖出来的东西按顺序摆出来。

## 一、batch：落盘的最小单位

生产者发消息不是一条一条写的。`producer.send` 会在客户端攒一小撮——逗留几毫秒（`linger.ms`）、攒够一小批（`batch.size`）就打包发走。实测最直观：一个 `send` 带五条消息，dump 出来是**一行**：

```text
baseOffset: 0 lastOffset: 4 count: 5 ... position: 0 size: 296
compresscodec: none crc: 4059270002 isvalid: true
```

`count: 5`——五条消息挤在同一个 batch 里，共享一个批次头。这个头就是上面那行户口本，逐个字段过一遍，每个都是伏笔：

- **baseOffset / lastOffset**：这批消息占的 offset 区间，[0, 4]。区间的存在意味着 offset 的分配单位其实是 batch——leader 给整个 batch 一个起点，区间内的每条顺次编号。
- **position**：这个 batch 在日志**文件**里的字节偏移——0，因为它是第一条。这个字段马上是主角。
- **size**：整批 296 字节，含消息体和批次头的全部开销。
- **crc**：整批的校验和，broker 写入时算一遍，消费端读出时再算一遍——对不上就是传输/磁盘损坏，`isvalid: true` 是 dump 工具替你比过之后的结论。数据库读者眼熟：binlog 事件也有 CRC32（MySQL 系列第六篇拆过），日志型存储的标配保险。
- **producerId: -1**：生产者还没有身份。它变成正整数的那天，幂等生产者就开了——那是第六篇的故事，先记下这个 -1。
- **partitionLeaderEpoch: 0**：这批写入时的分区领袖任期。副本篇的主角之一，此刻只是户口本上安静的一栏。
- **compresscodec: none**：这批没压缩。生产者可以在客户端把 batch 整体压缩，broker 原样落盘——注意压缩的单位是 batch 不是消息，这也是攒批的又一个理由。

**消息在磁盘上的真实形态：不是一条条的记录，是一批批的压缩包**。这解释了上一篇灌压实验里 20000 条 1.7 秒的一个侧面——攒批不只是减少请求次数，还把每条的元数据开销摊薄到了批次头里。

## 二、日志段：文件名就是座标

一批 296 字节不足以看清存储的骨架。往同一个分区灌 1.2MB（20 条 60KB 的大消息，每条独占一个 batch），然后看日志目录：

```text
00000000000000000000.log    296 B
00000000000000000005.log    1,046,018 B
00000000000000000022.log    184,593 B
```

三个文件，三个**日志段（segment）**。规则一目了然：段写满 1MB（我们配的 `segment.bytes`）就滚动，开新段；**文件名是 20 位零填充的数字，就是这个段的起始 offset**——`...005` 段从 offset 5 开始，装到 21；`...022` 从 22 开始，是当前正在写的活跃段（active segment）。

为什么要把一根连续的日志切成段？三个理由，每个都对应后面的一节：

1. **删除需要单位**。retention 到期删的是段文件，不是记录——第五节展开。
2. **索引需要粒度**。稀疏索引挂在段上，一段一套——下一节的主角。
3. **活跃写热点隔离**。正在写的只有 active 段，旧段从此只读、可被页缓存温柔对待、可被整体搬走。

一个对照给 MySQL 读者：InnoDB 的表空间里也有「段」（segment）——叶子段、非叶子段、回滚段，段下面是区（extent）、区下面是页。同一个字，两种命运：**InnoDB 用段把随机写聚成连续分配，Kafka 用段把顺序写切成可删除的单元**。一边为「找到」服务，一边为「扔掉」服务。

## 三、稀疏索引：二分，然后短扫

消息都在段文件里了，消费时要按 offset 找——总不能从 position 0 顺序扫到天荒地老。答案在每个段旁边的 `.index` 文件，dump 出来：

```text
Dumping kseg-0/00000000000000000005.index
offset: 6  position: 61530
offset: 7  position: 123060
offset: 8  position: 184590
...
offset: 21 position: 984487
```

十六行，每行 8 字节：4 字节 offset，4 字节 position。这就是稀疏索引——**不是每条消息都有索引条目**。我们配了 `index.interval.bytes=64`（每写 64 字节日志记一条）加 60KB 大消息，所以每条都显影出来；生产默认是 4096 字节，同样这批消息大约每十五条才一行，大部分消息在索引里**没有户口**。

查找一条 offset=9 的消息怎么走？三步：①目标段——文件名二分（`...005` ≤ 9 < `...022`）；②段内——`offset: 9 position: 246120`，索引二分找到；③**从 position 246120 开始顺序扫描**，在下一条索引条目覆盖的范围内找到精确的 offset。第三步是稀疏索引的精髓：允许索引不精确，因为日志本身有序且连续——**扫几条消息的代价是常数，换来索引体积缩小一个数量级**。

给这个结构找一个镜像：B+ 树是「为随机点查造的多级目录」，三层下降三次随机 I/O；稀疏索引是「为有序追加造的一级路标」——因为数据物理上已经排好序，索引只需要偶尔立块牌子。MySQL 读者会想起索引的另一种形态：InnoDB 的 change buffer（第八篇的缓冲池篇）在为「不必现在找」打时间差，而 Kafka 干脆取消了「找」。**数据结构是访问模式的镜像**——这句话是这一篇最想留下的。

两个边角素材顺手记下。其一：`.index` 文件 `ls -la` 显示 10MB，`du` 实占 0 磁盘块——**预分配的稀疏文件**，滚动关闭时才 truncate 到实际内容（活跃段索引 10MB、老段索引 0~128B，都见过实物了）。避免频繁扩文件，也顺手给了「索引有上限、稀疏是必需品」一个注脚。其二：段的第一条消息（baseOffset）不占索引条目——position 0 是隐含的起点，户口从第二条开始记，这也是 5 号段索引从 offset 6 开始的原因。

## 四、timeindex：时间旅行

每个段还有第三个文件 `.timeindex`，dump 出来是另一种映射：

```text
Dumping kseg-0/00000000000000000005.timeindex
timestamp: 1789143192614  offset: 6
timestamp: 1789143192622  offset: 7
...
```

timestamp ↔ offset。它服务的查询是：**「给我昨天 14:00 之后的消息」**。官方 CLI 一行验证——按某个历史时刻要位点：

```text
$ kafka-get-offsets.sh --topic kseg --time 1789143192614
kseg:0:6
```

返回 offset 6：那个时刻的第一条消息。时间旅行的工程形态就是它——「把消费组重置到事故发生前」，在 RabbitMQ 的世界观里根本没有对应物（消息送走就没了，哪来的历史），在 Kafka 里是一次 timeindex 查询加一次位移重置。日志不只是存消息，它存的是**带时间轴的历史**——这也是上一节稀疏索引不焦虑的深层原因：这段历史反正会被按时间窗截断，索引不必比档案活得精细。

## 五、删除：按段，而且不着急

retention 配了 60 秒。灌完消息等 60 秒、80 秒、100 秒……段文件纹丝不动。为什么？**过期和删除是两件事，中间隔着一个周期任务**：broker 的清理线程默认每 5 分钟（`log.retention.check.interval.ms`）巡一遍日志目录，发现段的整体时间戳过了保留期，才把它标记删除——改名 `.deleted`，再等一个删除延迟（默认 60 秒），才真正 unlink。60 秒的 retention 撞上 5 分钟的巡逻周期，被删的时辰完全由巡逻说了算。这不是缺陷是设计：删除本身要和读写竞争磁盘 IO，Kafka 把它安排成了不慌不忙的后台事务。

真正想看清的是删除的**单位**。等清理周期过去再对账（实测等了 400 秒）：

```text
$ ls kseg-0/
00000000000000000025.log   0 B     ← 只剩它：滚动产生的新活跃段

$ kafka-get-offsets.sh --topic kseg --time earliest
kseg:0:25                          ← earliest 从 0 跳到 25

$ kafka-get-offsets.sh --topic kseg --time 1789143192614
（空）                              ← 那段历史已经不存在了
```

`...000`、`...005`、`...022` 三个段连同索引整体消失，没有中间商。earliest 跳到 25 是消费者能感知到的全部变化——试图从更早的 offset 读会收到「越界」而非数据。最后那个空返回值得多看一眼：**时间旅行是保留期内的特权**，timeindex 再精妙也救不回已经被 unlink 的段——「重放历史」的服务等级协议，写在你配置的 retention 里。

没有「删除 offset 7 那条消息」这回事——**记录级删除在日志世界观里不存在，删除的粒度是文件**。这解释了一个上一篇留下的悬案：为什么毒消息不能从队列里摘掉、只能抄送进 DLQ topic？因为「队列里的那条消息」物理上是某个段文件中间的几十个字节，动它等于重写整个段——日志只追加、不回改，这是它的宪法。想要「删」，要么整段陪葬，要么用消费者视角的「跳过」（DLQ 就是制度化的跳过）。

MySQL 读者此刻应该有既视感：**binlog 的purge 也是整文件**（`bin.000004` 过期整体删除），redo 的 checkpoint 之外部分也按块废弃——日志型存储的 GC 单位从来不是记录。B+ 树表格才能 `DELETE FROM t WHERE id=7`，因为页内本来就在原地改。删除语义跟着存储结构走，不跟着 SQL 走。

## 六、顺序写的账单

最后把 position 排一排，这是今天最安静也最有力的一列数字：

```text
batch 1  position: 0
batch 2  position: 61530
batch 3  position: 123060
batch 4  position: 184590
...（等差，一路加到底）
```

每个 batch 的起点 = 上一个的起点 + 上一个的 size。**没有空洞，没有跳跃，没有「找」**。对比 MySQL 写路径的账：一笔 INSERT 要先按 B+ 树找到页（三次随机读）、改页、写 redo、可能还要 change buffer 兜着——那是第一篇和第八篇拆过的、为点查和原地改付出的全部税。Kafka 的写路径只有一句：**把这一批字节 append 到活跃段末尾**。位置计算是加法，磁头不动，页缓存顺序刷。百万级条/秒的吞吐不是魔法，是访问模式的胜利。

两笔尾账留给后面的篇章。其一：**fsync 的纪律**。`log.flush.interval.messages` 默认无限大——Kafka 默认**不等每条 fsync**，落盘节奏交给 OS 页缓存，持久性靠副本来兜（多台机器同时灰飞烟灭的概率，比一台机器掉电小几个量级）。MySQL 读者会立刻想起双 1 的纪律和那篇《提交的那一停》——两个系统对同一块磁盘的掉电风险，给出了完全不同的保险方案。为什么 Kafka 敢？答案在副本与 ISR，第五篇展开。其二：**读老数据走页缓存**，活跃段在缓存里烫着、老段被逐渐挤到冷的区域——冷热分层没写一行代码就发生了。MySQL 那边为了这个分级造了整个 LRU 变体（young/old 子链、中点插入）。缓冲池篇的镜像，第九篇消费者组再回来对。

---

一条消息的完整履历到这里拼齐了：它属于一个 batch、batch 落在一个段、段挂在它那个 offset 的文件名下、旁边站着稀疏索引和 timeindex、到期时整段陪葬。但今天的一切都发生在**单个分区**里——三段文件、一套索引，都是一个分区的私产。

分区自己是从哪来的？上一篇说过一句话没展开：分区器对 key 做 murmur2 哈希再对分区数取模。这个除法里藏着整个系列的下一个深水区：**分区数凭什么定、加一个分区会发生什么、同 key 的承诺在那一刻怎么碎的**。下一篇：分区与键。

（实验环境：apache/kafka:4.3.1 KRaft 单容器；工具 kafka-dump-log / kafka-get-offsets，全在镜像里。有个量具坑值得抄给读者：4.3 的 dump-log 已经不认 `--index`/`--timeindex` 这些老 flag，直接 `--files xxx.index` 它按文件类型自己认。另外，segment.bytes 的合法下限是 1MB，别像我一样想用 512B 的小段偷懒被 broker 一口回绝。）
