四行记录全部来自本机一次 384MiB 的实验，发生在同一秒内。

> 读完这一篇，你应该能回答三个问题：**内存明明还剩很多，大页申请为什么失败？`/proc/buddyinfo` 的每一列在数什么？「碎片」饿死的到底是什么？**（前置概念见[《第 0 篇》](/posts/kernel-primer/)：页、/proc 账本。）

申请大页为什么不是「给就是了」？第一篇页表实验留下过一笔账：`MADV_HUGEPAGE` 申请 1GiB，大页达成率只有 88%，再跑一次 91%，系统默认（THP=always）只有 69%——「凑齐物理连续的 2MiB 有多难，要等讲到伙伴系统才有完整答案」。第二篇结尾又欠了一笔：写时复制说要「分配一页新内存」，fork 说要「分配页表」，分配、分配、分配——页从哪里来。

这一篇进仓库。内核管理物理页的底层机构叫伙伴系统（buddy allocator），`/proc/buddyinfo` 是它的货架台账，本文两个实验都在这本账上做。它值得单独一篇，不仅因为大页的成败系于它，还因为它和 pymalloc 是同一道题的两种解法——这篇会不断回到这个对照上。

实验环境沿用系列前例：Linux 7.2.3，AMD Zen 2，源码对照 vanilla v7.2 tag。本篇的实验机器已连续运行多日、swap 用着 4.9GiB——这不是干扰，这本身就是素材：一台真实机器的碎片现场，比新装的虚拟机诚实得多。

## 十一层货架

先看台账长什么样。这张表第一次看会眼晕，可以先只盯 **Normal 行的最后三列**（o8/o9/o10），那是主力内存区的大块库存；其余等读完解读再回来对照：

```text
Node 0, zone      DMA      0      0      0      0      0      0      0      0      1      2      2
Node 0, zone    DMA32  16605   8786   3665   1526    767    359    148     71     25     62     61
Node 0, zone   Normal  34029  24739   1734   1610    300     71     59     26      2      1      0
```

每行一个区（zone），每列一个「阶」（order）——阶就是块的大小档位，像货币的面额：第 0 列是 order-0（4KiB 单页）的空闲块数，第 1 列是 order-1（8KiB，两页连续），依此翻倍直到第 10 列 order-10（4MiB，1024 页连续）。十一列不是随便排的——`include/linux/mmzone.h`：

```c
#define MAX_PAGE_ORDER 10
#define NR_PAGE_ORDERS (MAX_PAGE_ORDER + 1)
```

阶数到 10 为止，最大连续块 4MiB。这正是本机 buddyinfo 的列数，与源码对上了。

读这本账有三个要领。**第一，每列数的是「整块」，不是页数。** DMA32 那行的 62 不是 62 页，而是 62 个完整的 2MiB 连续块。**第二，低阶块随时可以拼成高阶的需求吗？不能。** 第 0 列的 16605 个散页再多，也凑不出一个新的 order-9 块——连续性是物理的，不是算术的。**第三，看静态结构。** Normal 区是这台机器 8GiB 的主力内存区，它 order-10 那列是 **0**，order-9 只有 2——运行多日的系统，4MiB 的整块已经一块不剩。而旁边的 DMA32 区（低 4GiB）还有 61 块。碎片不是理论威胁，是这台笔记本的日常。

三行 zone 各有各的历史使命：DMA 是远古 ISA 设备的 16MiB 特区，DMA32 是 32 位设备能摸到的 4GiB，Normal 是其余全部。每个区还配有 min/low/high 三道水位（`/proc/zoneinfo` 里 DMA 区是 16/20/24 页），低于水位的内存要留给内核自己——用户态分配越过 low 水位会触发回收，这是后面 OOM 篇的伏笔，这里先记账。

## 分配：从最低够用的阶层摘

伙伴系统的分配规则，源码 `mm/page_alloc.c` 的 `__rmqueue_smallest()` 一层循环写尽：

```c
for (current_order = order; current_order < NR_PAGE_ORDERS; ++current_order) {
        area = &(zone->free_area[current_order]);
        page = get_page_from_free_area(area, migratetype);
        if (!page)
                continue;
        page_del_and_expand(zone, page, order, current_order, migratetype);
        return page;
}
```

从请求的阶开始往上找，找到第一个有货的阶层，摘下一块；如果摘的块比请求大，`expand` 把它逐层劈半，劈出来的另一半挂回对应阶的空闲链表，一直劈到恰好满足。请求 order-9 而货架只有 order-10 时：劈一个 4MiB，一半成交，另一半成了新的 order-9 空闲块——**下一个同样的请求就不用再劈了**。

反过来不成立：order-9 缺货时，order-8 及以下再富裕也帮不上忙。碎片问题从数据结构上就是「高阶饿死、低阶过剩」，不是总量不足。

顺带把前两篇的线头接上：第一篇说每触碰 2MiB 内存、页表多一张 4KiB 的 PTE 页——那张 PTE 页本身就是一次 order-0 分配；第二篇写时复制抄的那一页、零页转正分的那一页，也都是 order-0。order-0 是全系统出货量最大的规格，也永远是最好拿的——这条特性后面要用对照实验验证。

## 释放：找到伙伴，成对升级

分配是劈，释放是合。伙伴系统之名，来自每个块都有一个由物理地址决定的「伙伴」：同一个 order 里，和它地址相邻、大小相等、合成后恰好对齐到更高阶的那一块。计算方式是异或，v7.2 `mm/internal.h`：

```c
__find_buddy_pfn(unsigned long page_pfn, unsigned int order)
{
        return page_pfn ^ (1 << order);
}
```

地址按 `2^order` 对齐分组，伙伴就是同组里和它配对的那一半——把 order 那一位翻过来就是它的页帧号。释放时 `__free_one_page()` 拿着这个公式找伙伴：

```c
while (order < MAX_PAGE_ORDER) {
        buddy = find_buddy_page_pfn(page, pfn, order, &buddy_pfn);
        if (!buddy)
                goto done_merging;      /* 伙伴不自由，到此为止 */
        __del_page_from_free_list(buddy, zone, order, buddy_mt);
        combined_pfn = buddy_pfn & pfn;
        pfn = combined_pfn;
        order++;                        /* 合并，升一阶，继续找下一层伙伴 */
}
```

伙伴也空闲，两块合成一块升一阶，继续向更高阶找伙伴，直到伙伴被占或到顶。这是伙伴系统对抗碎片的自愈机制：**只要成对的自由凑齐，零散就能自动归拢成大块。**

而碎片的定义也随之清楚了：伙伴被占，合并链条断在半路。下面两个实验，一个测「合不上」，一个测「合不上时申请大页会怎样」。

## 棋盘实验：回得去原阶，升不上高阶

第一个实验做棋盘。铺 384MiB——192 个独立的 2MiB 大页（`mmap` 后取 2MiB 对齐区间，`MADV_HUGEPAGE`，逐页触碰），然后**隔一块释放一块**：奇数块 munmap，偶数块留住。如果物理上这 192 块大致连续排布，棋盘化之后每个被释放块的伙伴都在被占的那一半里——合并链条应该全部断裂。

实测数据（只列 DMA32 和 Normal 两区的高阶列）：

```text
          DMA32 o9  o10      Normal o9  o10      vmstat
S0 基线        61   60            0    0      alloc=22081
S1 铺满         0    0            0    0      alloc=22273 (+192, 无回退)
S2 释放 96 块  89    0            3    0      计数器无变化
```

S1 的账很干净：alloc 精确 +192，DMA32 的 order-9 从 61 清零、order-10 从 60 清零——61 块直接成交，60 个 4MiB 块被劈半凑数，零头由压实补齐（compact_stall +9）。Normal 区从头到尾没出货，因为它的 order-9/10 本来就是空的。

S2 是实验核心。释放了 96 个 2MiB 块（192MiB），台账上回来了 92 块 order-9（89+3，±4 是系统噪声）——**释放的块精确回到了自己原来的阶层**，一块都没有升阶：order-10 那列从 0 到 0，纹丝不动。192MiB 完整归还，却连一个 4MiB 整块都凑不出来。每一个被释放的块，物理伙伴都还压在偶数块手里；合并循环的第一步就 `goto done_merging`。

对照 pymalloc（CPython 的分配器，没读过那篇只需知道：它把内存组织成一兆字节的「arena」大块，块内所有小对象都释放后整块才能归还）：arena 里只要还有一个在用 block，整座楼退不掉——同一个「差一点就全部自由」的结构性浪费。区别在账本粒度：pymalloc 卡的是 1MiB 的楼，伙伴系统卡的是 2MiB/4MiB 的块。

## 钉子实验：饿死 order-9

棋盘证明了「合不上」，但没饿死谁——92 个 order-9 空闲块仍然够新的大页申请吃好几轮（对照实验里，碎片状态下新的 64MiB 大页申请照样 100% 成交，因为隔块释放归还的就是 order-9 本身）。

第二个实验换更细的刀：还是铺 384MiB 大页，然后**对每个 2MiB 窗口 `MADV_DONTNEED` 掉它的第一个 4KiB 页**——每个窗口钉一颗钉子。这一下有双重效果，实测全部显形：

```text
          DMA32 o9  o10     主区 AnonHugePages     thp_split_pmd
S1 铺满         0    0        393216kB (384MiB)        3079
S2 敲钉子       0    0              0kB              3271 (+192)
```

第一重：PMD 映射全部拆散。`thp_split_pmd` 精确 +192，主区 `AnonHugePages` 从 393216kB 归零——第二篇讲过拆分：不能只 zap 大页的一部分，只能把 PMD 映射整个拆成 512 个 PTE。页没少（它们仍以 PTE 粒度映射着），变的只是地图的画法。

第二重才是本篇的主菜：每个 2MiB 窗口里都有一颗 4KiB 的钉子，order-9 那层**一块空闲块都没有**。释放的 192 个钉子页也没在 buddyinfo 的 order-0 列露面（19334→19334）——它们被 per-CPU 页缓存（pcp lists）吸收了，那是不进伙伴链表的零钱抽屉，又一个 buddyinfo 看不见的角落。

现在碎片现场布置完毕：高阶三个区全部空仓（DMA32 o9=0、Normal o9=0、DMA 只有区区 2 块），而内存总量充足。做两组对照申请：

**order-0 申请 64MiB（`MADV_NOHUGEPAGE`）**：0.03 秒完成，Normal 区 order-0 列从 3011 掉到 641——照常供货。**碎片不是内存不足，是「连续」这个规格断货。** 零钱再多，换不出整钞。

**大页申请 64MiB（`MADV_HUGEPAGE`）**：0.06 秒内完成，结果 43008kB / 65536kB——**32 块只成交 21 块**。vmstat 的差分给出了全部剧情：

```text
thp_fault_alloc     +21     成交
thp_fault_fallback  +11     回退成 4KiB
compact_stall       +37     压实发起 37 次
compact_success     +16     其中 16 次凑出了大页
compact_fail        +21     21 次失败
compact_migrate_scanned  +136636   扫过 13 万多个可迁移候选页
```

这就是第一篇那 88% 的完整答案：**大页申请失败不是当场回绝，而是先尝试搬迁救场**。本机 THP defrag 模式是 `defer+madvise`，`MADV_HUGEPAGE` 的缺页在拿不到 order-9 时发起直接压实（direct compaction）——把可移动页搬到别处，腾出连续空间，再重试分配。37 次尝试救回 16 块，救不回的 11 块回退成 512 个 order-0。达成率 88%、91%、69%——就是「成交 + 压实拯救 + 回退」三种结局的混合比例，每次运行随碎片分布浮动。

而「搬迁」二字，正是伙伴系统对 pymalloc 做不到的事。

## 迁移类型：钉子分两种

为什么内核能搬页、pymalloc 不能搬对象？因为内核把「能不能搬」做成了货架的分类维度。每个 2MiB 的 pageblock 带一个迁移类型标记，匿名页是 `MIGRATE_MOVABLE`——没有外部指针指向物理地址（对进程完全透明），随时可搬；内核自己的数据结构是 `MIGRATE_UNMOVABLE`——到处都是指向它的指针，动了就全乱。还有 `MIGRATE_RECLAIMABLE`（可回收，如缓存页）。分配时优先找同类型的块，`__rmqueue_smallest` 循环里那个 `migratetype` 参数就是分类索引。

不同类型可以互相借用，但优先级是单向的，`page_alloc.c` 的回退表写得很直白：

```c
static int fallbacks[MIGRATE_PCPTYPES][MIGRATE_PCPTYPES - 1] = {
        [MIGRATE_UNMOVABLE]   = { MIGRATE_RECLAIMABLE, MIGRATE_MOVABLE   },
        [MIGRATE_MOVABLE]     = { MIGRATE_RECLAIMABLE, MIGRATE_UNMOVABLE },
        [MIGRATE_RECLAIMABLE] = { MIGRATE_UNMOVABLE,   MIGRATE_MOVABLE   },
};
```

UNMOVABLE 缺货时可以偷 MOVABLE 的整块用，被偷的 pageblock 从此变性为 UNMOVABLE——**不可移动的钉子就这样钉进了原本干净的连续区域**。这正是长期运行的系统 Normal 区高阶归零的主要成因：不是内存不够，是几十年的内核分配（页表页、slab、各种结构体——它们全是 UNMOVABLE 的 order-0/order-1）像撒钉子一样撒满了各处，order-9/10 的连续窗口被零星钉死。运行越久、越满，钉子越难拔。压实能搬走的只有 MOVABLE 的页，UNMOVABLE 的钉子是搬不动的——所以 compaction 有 21 次失败，不是它不努力，是有些钉子真的焊死了。

对照收束：pymalloc 的 arena 和伙伴系统的块面对同一道题——「差一个没自由，整块退不掉」。pymalloc 无解，因为 C API 承诺了对象地址稳定，它不能搬；内核有解的一半，因为对进程隐藏物理地址，MOVABLE 的页随便搬（第二篇的棋盘拆分也演示过：物理位置从来不是承诺）。而另一半无解——UNMOVABLE 搬不了，所以碎片只能缓解，不能根治。**分配器的「不搬」是设计，不是偷懒；能搬的部分，才是内核相对用户态分配器真正的特权。**

## 我踩的坑

**第一个实验的设计是错的，数据反而是对的。** 棋盘实验的原始目的就是饿死大页申请——结果 S3b 对照组 100% 成交，实验「失败」。原因：隔块 munmap 归还的就是 order-9 整块，它们本身就是合格的大页货源，何须合并升级。但这次失败留下了更干净的数据：释放精确回到原阶（92/96）、高阶一格不升（o10 始终 0）——「合并需要伙伴也自由」的直接证据。于是把「失败」的实验保留成上半场，真正的饿杀改成逐窗钉钉子。**实验设计错出来的数据别扔，先看它证明了什么。**

**buddyinfo 是慢账本加盲区。** 它只反映伙伴链表本体：pcp 里的零钱（S2 释放 192 页、order-0 列一动不动）、以及被别的进程瞬息吞吐的块，都看不见或看不准。做差分时把 ±5 块当噪声处理，别把系统的一次 page cache 回收读成自己的实验效果。

**全局计数器人人有份。** `thp_fault_alloc`、`compact_stall` 是全系统累计值，桌面环境里 Chrome 一动它们就动。本文所有计数都做实验前后差分，并且容忍个位数漂移——+192、+21、+11 这种量级才敢下结论。

**对照实验要同时做。** 只看 S3b 的 66% 达成率，无法区分「碎片饿死」还是「机器本来就拿不出大页」。S3a 的 order-0 照常供货钉死了因果：同一时刻、同一货架，零钱管够、整钞断货——碎片这个诊断才立得住。

## 合上货架以前

**物理页的家底按「阶」记账。** 十一层货架从 4KiB 到 4MiB，每层数的是整块；低阶再富裕，凑不出高阶的连续——碎片从数据结构上就不是总量问题。

**分配从最低够用的阶层摘，释放靠伙伴成对升级。** 伙伴是物理地址异或出来的另一半；合并链条能走多远，取决于最不自由的那对伙伴。释放的块回原阶、升不了阶，是碎片的第一现场。

**碎片饿死的是「连续」，不是容量。** 钉子实验里 order-0 照常 0.03 秒拿 64MiB，大页申请 32 块只成交 21 块——同一货架两种命运。第一篇的 88% 之谜至此还清：成交、压实拯救、回退的三方混合。

**压实是内核独有的解药，且只解一半。** MOVABLE 的页可以搬，UNMOVABLE 的钉子焊死。这也是长寿命系统高阶货架逐渐清零的机制：不可移动的小分配撒进连续区域，时间越长钉子越密。

**pymalloc 与伙伴系统是同一道题的两种解。** 「差一个没自由整块退不掉」的结构相同；差别在能否搬迁——内核对进程隐藏物理地址，换来了搬家的自由。这一篇也把系列前三篇的线头收拢：页表页是 order-0，COW 的新页是 order-0，大页是 order-9——你写下的每一笔内存，背后都是伙伴系统的一次摘货架。

```text
12:53:10  货架上，order-10 还有六十几个整块。
12:53:10  一次铺货，高阶清空；两分钟前，它们还叫「空闲」。
12:53:10  钉子敲下，连续成为稀缺品；零钱照旧，整钞绝迹。
12:53:11  全部释放，成对的自由逐层归拢，货架复原。
```

伙伴系统管的是页，最小的出货规格也是一整页 4KiB。但内核自己也有海量比页更小的需求：inode、dentry、task_struct、各种哈希节点……总不能每存一个 200 字节的结构体就撕一页。第一篇提过的 slab，就是内核为小对象另开的柜台——它和 pymalloc 长得像到可以互相验证。
