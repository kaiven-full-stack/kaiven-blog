先放两个实测数字：`sys.getsizeof(2**100)` 是 40 字节，`sys.getsizeof(2**10000)` 是 1360 字节。再大的数也照存不误。Zig 系列里讲过另一种世界观：整数溢出是 bug，语言要么 panic，要么要求你显式绕过（wrapping、saturating）。CPython 给了完全相反的答案：int 没有上限，你写 `2**10000`，它就真的把这个数完整地造出来，一个比特都不缩写。

没有上限不等于没有代价。这一篇看代价怎么付：数字怎么按 30 比特一个 digit 存放、符号和位数怎么打包进一个 `lv_tag`、为什么 -5 到 256 的整数常驻内存、以及大数乘法在什么规模上换了算法。以下实验在 CPython 3.14.7 上完成，引用的源码来自 3.14 分支。

## 数字住进 30 比特的房间

PyLongObject 的本体是一串 32 位无符号整数（`digit`），每个 digit 存 30 个比特：

```c
typedef struct _PyLongValue {
    uintptr_t lv_tag;    /* 位数、符号、标志打包在一个字里 */
    digit ob_digit[1];   /* digit = uint32_t，实际用 30 位 */
} _PyLongValue;
```

一个数的值就是各 digit 的加权和：

```text
value = digit[0] + digit[1]×2³⁰ + digit[2]×2⁶⁰ + ...
```

拿 2**100 + 12345 实测：

```text
v = 1267650600228229401496703217721
sizeof(v) = 40            （24 字节头部 + 4 个 digit × 4 字节）
digit = [12345, 0, 0, 1024]
```

digit[0] 是 12345（低 30 位放不下 2 的任何高次幂），中间两个 digit 是 0，digit[3] = 1024：2**100 = 2**90 × 2**10，第 4 个 digit（覆盖第 90–119 比特）里存的就是 2**10。按四个 digit 重构：12345 + 0 + 0 + 1024×2**90，分毫不差。

每个 digit 用 30 位而不是满打满算的 32 位，是给进位留余量。两个 digit 相加最大可到 2**31，相乘最大 2**60，都要装进更大的临时类型（`twodigits` = uint64_t）里完成进位；空出 2 个比特，进位运算就永远不会溢出临时变量。这是手写多精度算术的经典取舍：每个 digit 牺牲一点存储密度，换来加法乘法的进位链全程无溢出。

于是 sizeof 的阶梯每 30 比特一级：

```text
2**30-1 → 28 字节（1 间房）    2**60-1 → 32 字节（2 间房）
2**90-1 → 36 字节（3 间房）    2**120-1 → 40 字节（4 间房）
```

一个只存小值的 int 总共 28 字节，其中数据只占 4 字节，对象头和 lv_tag 占 24：元数据比数据贵。后面的小整数缓存，省的就是这笔开销。

## 符号藏在标签里

3.12 之前 sign 和 ob_size 是两个分开的字段；3.12 起合并成一个 `lv_tag`：低 2 位存符号（正、负、零），高位存位数。这个改动来自 free-threading 的需要：引用计数篇和 free-threading 篇讲过，多字段的原地更新需要多把锁，打包成一个字就能用单条原子指令维护。

顺带的好处是 `_PyLong_IsNonNegativeCompact` 这类判断：一个比较就能同时回答「是几位的、正的还是负的」，热路径上的分支更少。GIL 时代的结构布局，已经在为无 GIL 的时代做准备。

## -5 到 256：常驻的小整数

int 是不可变对象，`a = a + 1` 就是造一个新对象、扔一个旧对象。但循环一百万次并不会带来两百万次分配：-5 到 256 的全部整数在解释器启动时就造好了，永不释放。

```text
#define _PY_NSMALLPOSINTS  257    /* 0..256 */
#define _PY_NSMALLNEGINTS   5     /* -5..-1 */
```

这段范围不是拍脑袋。0 和 1 是最常用的值（bool 还是 int 的子类，True/False 就是 1/0）；ASCII 码、月天数、常见循环界都落在几十到二百五十六之间；下限取 -5 是给倒序索引、负数哨兵留的余量。所有这些数的创建一律返回缓存里那个对象的引用，分配、释放、引用计数增减全省。

验证要用运行时计算的值，编译期常量会被折叠成同一个对象干扰判断：

```python
def fresh(n): return int(str(n))   # 强制运行时解析

fresh(256) is fresh(256)   # True  —— 256 在缓存里，两次拿到同一个对象
fresh(257) is fresh(257)   # False —— 257 在缓存外，两次各造各的
fresh(-5) is fresh(-5)     # True
fresh(-6)  is fresh(-6)    # False
```

四行输出把缓存边界画清楚了。工程上的提醒也跟着来：`is` 只该用来判 None 和哨兵，永远不要判整数相等。256 行得通、257 就出错，这种 bug 在测试环境的小数值里根本不复现。

缓存还解释了上一篇 list 留下的一个数字：百万元素的 list 如果装的是 0..256 的小整数，元素本体几乎不占内存，它们共享这 257 个缓存对象。`list(range(1000000))` 的真实内存远小于「百万 × 28 字节」的直觉，原因就在这里。

## 小整数的快路径

缓存解决的是「创建贵」，还有「运算贵」要解决。两个 int 相加，如果都只有一个 digit，CPython 不走通用大数例程，走的是特化快路径：`x_add`/`x_mul` 之外有一层单 digit 的快捷分支，加法就是一条 C 加法指令加一次进位判断。字节码篇和特化篇讲过的 `BINARY_OP_ADD_INT`，落到底层就是这条快路径。

大数没有这等待遇。digit 数组的逐位加法是 O(n)，乘法朴素实现 O(n²)，但实测的成本曲线在某个规模后明显变缓：

```text
平方运算 ×100 次的耗时：
 3k 比特    0.44 ms
30k 比特   19.8 ms    （10 倍位数，45 倍耗时 ≈ 平方律）
300k 比特  726 ms     （10 倍位数，37 倍耗时 < 平方律）
3M 比特   29,024 ms   （10 倍位数，40 倍耗时 < 平方律）
```

十倍位数本该带来百倍耗时，300k 比特之后只有 37–40 倍，因为 Karatsuba 乘法接管了。它把两位数乘法拆成三次一半规模的子乘法（朴素做法是四次），递归下去复杂度降到约 O(n^1.585)。CPython 的切换门槛不高（几十个 digit），中等规模的密码学运算、大数阶乘都已经落在 Karatsuba 区间里。

拆分在 digit 层面进行：Karatsuba 要求等长的两半，30 比特的 digit 正好提供整齐的切分单位。当年为进位留下的 2 比特余量，在这里又派上一次用场。

## 与 Zig 的对照

把两个系列放在一起看。

Zig 的立场是溢出属于程序错误。`a + b` 默认在安全模式下 panic（ReleaseFast 除外），要绕过必须显式声明 `+%`（wrapping）或 `|%|`（saturating）。理由是性能：CPU 的加法器就是定宽的，语言不该为极少数大数场景让所有整数运算付税。

CPython 的立场是溢出不存在，所以也无需处理。定宽加法器之上盖了一层 digit 数组，加法链条溢出一位就进位到下一个 digit。两边的成本都能算清：

```text
Zig u64 加法：1 条指令
CPython 小 int 加法：1 条指令 + 对象头维护 + 缓存查找
CPython 大 int 加法：O(位数) 的逐 digit 进位链
```

选择背后是对使用场景的判断：系统语言假设你在写操作系统和协议栈，每一位都要计入成本；脚本语言假设你在写业务逻辑和算法原型，`2**64` 溢出一个 hash 计算是不可接受的意外。两种答案各自适合自己的场景。

边界也要说清：任意精度不等于任意免费。`10**1000000` 的幂运算、`math.factorial(100000)` 会在毫秒到秒级制造可观的延迟与内存；乘法的 Karatsuba 门槛救不了除法（仍是 O(n²) 级的 Newton 迭代或长除法）；`float(int)` 超过 2**53 会丢精度，int 没有上限，float 有。

## 观测手段

```text
sys.getsizeof(n)           24 + 4 × digit 数（小整数缓存里的对象除外）
int.bit_length()           有效比特数 ≈ 30 × (digit 数 - 1) + 最高位比特
sys.int_info               bits_per_digit=30, sizeof_digit=4
```

`sys.int_info` 值得看一眼：它把「30 比特一个 digit」从实现细节变成了可直接查询的接口，类似 str 篇里 PEP 393 对内部布局的说明。

## 回看这套结构

int 的本体是 digit 数组的加权和，每个 digit 存 30 比特、留 2 比特给进位链，sizeof 每 30 比特上一级台阶。符号和位数打包在 lv_tag 一个字里，3.12 的这次布局改造让一个原子操作就能维护两个字段的信息，结构在给 free-threading 让路。

-5 到 256 在解释器启动时造好、永不释放，运行时验证要用 `int(str(n))` 绕开常量折叠；`is` 不要用来比较整数；小整数 list 的元素本体因此几乎免费。运算上，单 digit 的小数走快路径，大数乘法在几十个 digit 后切到 Karatsuba，300k 比特起平方律明显放缓，除法没有同等待遇。

回到开头的问题：Python 为什么没有整数溢出。因为 int 的位数是变量，放不下了就再加一个 digit。程序员少了一类 bug，代价摊进每条整数运算的对象开销和内存里，而其中最重的一块，又被 257 个常驻小整数和 Karatsuba 分治压了回去。

28 字节的最小 int 与对象头构成见《一只 Python 对象到底有多重》，lv_tag 打包的动机见《拆掉 GIL 之后，引用计数先要活下来》，上一篇《每次搬家只多租一成》里小整数让 list 元素本体免费的那笔内存，出处就是这里的缓存。Zig 对同一问题的另一种回答见《255 + 1 等于什么：Zig 怎么处理整数溢出》。
