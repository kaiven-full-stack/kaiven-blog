```text
sizeof(2**100) = 40 字节
sizeof(2**10000) = 420 字节

一万位的十进制数字，住进了一栋 420 字节的楼。
房间里没有「最大整数」这堵墙——因为墙被拆掉了。
```

Zig 系列里讲过另一种世界观：整数溢出是 bug，语言要么 panic 要么要求你显式绕过（wrapping、saturating）。CPython 选择了完全相反的答案：**int 没有上限**，你写 `2**10000`，它就真的把这个数完整地造出来。开头的 420 字节不是科学计数法的缩写，是那 33220 个比特的真实住址。

没有上限不等于没有代价。这一篇把这笔账拆开：数字怎么按 30 比特一间地住进 digit 数组、符号和位数怎么打包进一个 `lv_tag`、为什么 -5 到 256 的整数是不朽的、以及大数乘法在什么规模上悄悄换了算法。实验在 CPython 3.14.7 上复核，源码以 3.14 分支为准。

## 数字住进 30 比特的房间

PyLongObject 的本体是一串 32 位无符号整数（`digit`），每间房住 30 个比特：

```c
typedef struct _PyLongValue {
    uintptr_t lv_tag;    /* 位数、符号、标志打包在一个字里 */
    digit ob_digit[1];   /* digit = uint32_t，实际用 30 位 */
} _PyLongValue;
```

一个数的值就是房间内容的加权和：

```text
value = digit[0] + digit[1]×2³⁰ + digit[2]×2⁶⁰ + ...
```

拿 2**100 + 12345 实测：

```text
v = 1267650600228229401496703217721
sizeof(v) = 40            （28 字节对象头 + 4 间房 × 4 字节）
digit = [12345, 0, 0, 1024]
```

digit[0] 是 12345（低 30 位放不下 2 的任何高次幂），中间两间空着，digit[3] = 1024 —— 2**100 = 2**90 × 2**10，第 4 间房（第 90–119 比特）里住着 2**10。四间房重构：12345 + 0 + 0 + 1024×2**90，分毫不差。

为什么是 30 不是满打满算的 32？**进位的余量**。两个 digit 相加最大可到 2**31，两个 digit 相乘最大 2**60——都必须装进更大的临时类型（`twodigits` = uint64_t）里完成进位。留 2 个比特的空，是为了让进位运算永远不会溢出临时变量。这是手写多精度算术的经典取舍：每间房牺牲一点存储密度，换来加法乘法的进位链全程无溢出。

于是 sizeof 的阶梯每 30 比特一级：

```text
2**30-1 → 28 字节（1 间房）    2**60-1 → 32 字节（2 间房）
2**90-1 → 36 字节（3 间房）    2**120-1 → 40 字节（4 间房）
```

值得注意的是：28 字节的对象头（引用计数 + 类型指针）意味着**一个小 int 的元数据比数据还贵**——数据只占 4 字节，头占 24。这为后面的缓存埋下伏笔。

## 符号藏在标签里

3.12 之前 sign 和 ob_size 是两个分开的字段；3.12 起合并成一个 `lv_tag`：低 2 位存符号（正、负、零），高位存位数。这个改动来自 free-threading 的需要——引用计数篇和 free-threading 篇讲过，多字段的原地更新需要多把锁，打包成一个字就能用单条原子指令维护。

顺带的福利还有 `_PyLong_IsNonNegativeCompact` 这类判断：一个比较就能同时回答「是几位的、正的还是负的」，热路径上的分支更少。GIL 时代的结构布局，正在为无 GIL 时代悄悄让路。

## -5 到 256：不朽的整数

int 是不可变对象，于是 `a = a + 1` 就是造一个新对象、扔一个旧对象。循环一百万次就是两百万次分配？小整数早就免了这笔账——**-5 到 256 的全部整数在解释器启动时就造好了，永不释放**：

```text
#define _PY_NSMALLPOSINTS  257    /* 0..256 */
#define _PY_NSMALLNEGINTS   5     /* -5..-1 */
```

这段范围不是拍脑袋。0 和 1 是最常用的值（bool 还是 int 的子类，True/False 就是 1/0）；ASCII 码、月天数、常见循环界都落在几十到二百五十六之间；下限取 -5 是给「倒序索引、负数哨兵」留的余量。所有这些数的创建一律返回缓存里那个对象的引用——分配、释放、引用计数增减，全省。

验证要用**运行时计算的值**，编译期常量会被折叠成同一个对象干扰判断：

```python
def fresh(n): return int(str(n))   # 强制运行时解析

fresh(256) is fresh(256)   # True  —— 256 在缓存里，两次拿到同一个对象
fresh(257) is fresh(257)   # False —— 257 在缓存外，两次各造各的
fresh(-5) is fresh(-5)     # True
fresh(-6)  is fresh(-6)    # False
```

四行输出把边界画得干干净净。工程上的提醒也就跟着来了：**`is` 只能用来判 None 和哨兵，永远不要判整数相等**——256 行得通、257 就翻车，这种 bug 在测试环境（小数值）里根本不复现。

缓存的另一面是它解释了前一篇留下的账：**百万个元素的 list 里如果装的是 0..256 的小整数，元素本体是零字节**——它们全都共享 257 个不朽对象。这也是为什么 `list(range(1000000))` 的真实内存远小于「百万 × 28 字节」的直觉。

## 单机器字的美梦：小整数的快路径

缓存解决「创建贵」，还有一个「运算贵」要解决。两个 int 相加，如果都只有一间房，CPython 不走通用大数例程，走的是特化快路径——`x_add`/`x_mul` 之外有一层单 digit 的快捷分支，加法就是一条 C 加法指令加一次进位判断。字节码篇和特化篇讲过的 `BINARY_OP_ADD_INT`，落到底层就是这条快路径。

大数则没有这等待遇。digit 数组的逐位加法是 O(n)，乘法朴素实现 O(n²)——但实测的成本曲线在某个规模后明显「变缓」：

```text
平方运算 ×100 次的耗时：
 3k 比特    0.44 ms
30k 比特   19.8 ms    （10 倍位数，45 倍耗时 ≈ 平方律）
300k 比特  726 ms     （10 倍位数，37 倍耗时 < 平方律）
3M 比特   29,024 ms   （10 倍位数，40 倍耗时 < 平方律）
```

十倍位数本该带来百倍耗时（平方律），300k 比特之后只有 37–40 倍——**Karatsuba 乘法接管了**。它把两位数乘法拆成三次一半规模的子乘法（而不是朴素的四次），递归下去复杂度降到约 O(n^1.585)。CPython 的门槛不高（几十个 digit 就切换），所以中等规模的密码学运算、大数阶乘都已经活在 Karatsuba 的区间里。

拆分在 limb 层面进行——Karatsuba 要求等长的两半，而 30 比特的 digit 正好提供了整齐的切分单位。设计者当年留的那 2 个比特余量，在这里又收了一次利息。

## 一切皆对象的账单：与 Zig 的对望

现在可以把两个系列放在一起对望了。

Zig 的立场：**溢出是程序错误**。`a + b` 默认在安全模式下 panic（ReleaseFast 除外），要绕过必须显式声明 `+%`（wrapping）或 `|%|`（saturating）。理由是性能：CPU 的加法器就是定宽的，语言不该为极少数大数场景让所有整数运算付税。integer-overflow 篇把这套设计称为「把 UB 关进四个笼子」。

CPython 的立场：**溢出不存在，所以也无需处理**。定宽加法器之上盖了一层 digit 数组，加法链条溢出一位就进位开新房。代价明码标价：

```text
Zig u64 加法：1 条指令
CPython 小 int 加法：1 条指令 + 对象头维护 + 缓存查找
CPython 大 int 加法：O(位数) 的逐 digit 进位链
```

选择背后是对使用场景的判断：系统语言假设你在写操作系统和协议栈，每一位都要过账；脚本语言假设你在写业务逻辑和算法原型，`2**64` 溢出一个 hash 计算是不可接受的意外。**没有哪个是「更对」的，只有「为什么在这个场景里对」**——两个系列写到这里，这句话差不多成了所有设计取舍的通配结论。

边界也照例要说：任意精度不等于任意免费。`10**1000000` 的幂运算、`math.factorial(100000)` 会在毫秒到秒级制造可观的延迟与内存；乘法的 Karatsuba 门槛救不了除法（仍是 O(n²) 级的 Newton 迭代或长除法）；`float(int)` 超过 2**53 会丢精度——int 世界没有墙，但 float 世界有。

## 观测与边界

```text
sys.getsizeof(n)           28 + 4 × digit 数（不含小整数缓存的特殊性）
int.bit_length()           有效比特数 ≈ 30 × (digit 数 - 1) + 末房比特
sys.int_info               bits_per_digit=30, sizeof_digit=4
```

`sys.int_info` 值得亲眼一看：它把「30 比特一间房」从实现细节升格为受承诺的接口——PEP 393 时代对 str 的承诺（str 篇的灵活字符串表示），在 int 这里同样成立。

## 账单，按位再算一遍

**int 是 30 比特 digit 数组的加权和。** digit 留 2 位余量供进位链使用；sizeof 阶梯每 30 比特一级，2**100 占 4 间房 40 字节。

**符号与位数打包在 lv_tag 一个字里。** 3.12 的布局改造，一个原子操作维护两个字段的信息——结构在为 free-threading 让路。

**-5..256 是启动时造好的不朽对象。** 运行时验证要用 `int(str(n))` 绕开常量折叠；工程守则是永远不用 `is` 比较整数；小整数 list 的元素本体因此免费。

**小数走单 digit 快路径，大数走 Karatsuba。** 300k 比特起平方律明显放缓（实测 10 倍位数只带来 37–40 倍耗时）；除法没有这等待遇。

**没有溢出是用每条指令的税换来的。** 与 Zig 的显式溢出哲学互为镜像：一个为每一位记账，一个把墙拆掉——各自对得起自己的使用场景。

```text
1 住在缓存里，第 257 号房。
257 在缓存外，每次见面都是新造的。
2**100 住在四间房里：[12345, 0, 0, 1024]。
2**10000 住在 334 间房里，账单 1364 字节。

从 1 到 2**10000，没有一道门写着「到此为止」。
只有账单，随位数增长。
```

Python 的 int 用一个结构回答了「溢出怎么办」：不怎么办。数字住进 30 比特的房间，满了就开新房，符号和位数写在门口的标签上。墙拆掉之后，程序员少了一类 bug，多了一份账单——而账单的大头，早被 257 个不朽的小数字和 Karatsuba 的分治法悄悄垫付了。
