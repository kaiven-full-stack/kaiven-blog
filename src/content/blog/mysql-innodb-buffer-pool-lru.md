
第一篇结尾埋了一句话没还：回表 40 万页读 vs 覆盖 233 页读、耗时却只差 4 倍，因为「buffer pool 兜住了随机读——表大于内存时才现形」。这一篇就来把 buffer pool 本身拆开：**一页从磁盘进内存住在哪、凭什么留下、又被谁赶走**。它是页、区、段、表空间这套磁盘四层结构之外的内存层，也是前六篇每个「页读」计数器背后的那只手。

朴素 LRU（最近最少使用）人人都懂：新页进队首，被访问就挪回队首，队尾淘汰。它有个致命软肋——**一次全表扫描等于一场洗劫**。1000 万行的 big10m 有 6.4 万个叶子页，扫描会把它们鱼贯塞进 128MiB 的池子（8192 页），每页只被碰一次、之后再无访问，却把常驻热页从队尾一路挤出去。扫描结束，缓存空了，热点查询集体撞磁盘。

InnoDB 的对策是把这条链劈成两段：**young/old 子链 + 中点插入**。听起来简单，但每条规则都值得抠——比如你以为「隔 1 秒重访一个 old 页，它该升 young 了吧」？在 8.4 里大概率不会，而且原因就写在 `buf_page_peek_if_too_old` 开头那几行里。本篇照旧用 docker 里的 MySQL 8.4.11 逐条实测，所有数字当场跑出来，源码逐行对上。

> 读完这一篇，你应该能回答四个问题：**young/old 子链怎么分工，新页从哪里进链？为什么全表扫描冲不掉热页，又是哪个计数器在拒绝？表大于内存时回表到底多付多少物理读？8.4 为什么把 change buffer 和自适应哈希的默认值都改掉了？**

## 一条链劈两段：young/old 子链

先看家底。池子 128MiB = 8192 个 16KiB 页，单实例。链表方向以 `INNODB_BUFFER_PAGE_LRU` 的 `LRU_POSITION` 为准：**0 是队尾（最旧，淘汰从这端开始），最大值是队首（最新）**。表里还有一列 `IS_OLD`，就是每个页的身份牌。

冷启动后不跑任何业务查询，池里已经有 1400 多页——系统表空间、undo 表空间的账本页。源码里链长不足 512 页（`BUF_LRU_OLD_MIN_LEN`）时 old 边界指针不启用（`buf_LRU_old_init`：链长一到 512，先把整条链标成 old，再把边界挪到目标比例处）；我这个实例启动即越过 512，边界早就就位。落定后的格局由 `innodb_old_blocks_pct`（默认 37）决定：**old 子链是队尾侧的约 3/8，young 子链是队首侧的约 5/8**——实测任何时刻数一遍 `IS_OLD`，都是链长的 37% 上下，比如 547/1430、3043/8192。「中点」就是这两个子链的接缝：磁盘新页从这里进链。

这条 5/8 分割线不是摆设，它把两种「新来的页」分流：

- **磁盘读入的页，一律插进 old 子链的头部（中点）**。源码 `buf_page_init_for_read` 里就一行：`buf_LRU_add_block(bpage, true /* to old blocks */)`。新页从磁盘进来，不管多重要，先站中点——它身后是整个 old 子链当炮灰。
- **B+ 树分裂新建的页，直接插队首（young）**：`buf_LRU_add_block(&block->page, false)`。新页是刚写出来的，大概率马上还要被写，没必要让它去过 old 子链的安检。

实测把这条规则拍得清清楚楚。冷启动后先点查一次 `id=700000`（读入根 4、中间页 40、叶子页 2437），再查三个相距很远的主键（100000、400000、900000），树上各层的落点：

```text
LRU_POSITION  PAGE_NUMBER  IS_OLD  记录数  身份
543           40           YES     928     中间页（700000 的路径，上一轮）
545           38           YES     928     中间页 ←本轮新读入
546           3125         YES     292     叶子页（id=400000）←本轮新读入
547           1406         NO      290     叶子页（id=100000）←本轮新读入*
548           376          NO      292     叶子页（id=900000）←本轮新读入*
549           37           NO      464     中间页（另一段范围）←本轮新读入*
550           2437         NO      291     叶子页（id=700000，上一轮）
551           4            NO      5       根页（上一轮）
```

本轮新读入的五个页全落在 545-549——正是 old 子链头部（当时 old 区从 543 延伸到 546 一带）。「叶子在 old、根在 young」不是巧合，但根和中间页站在 young 区的原因**不是被晋升**（预热期根本不晋升，见下节），而是边界滑动：新页不断从中点塞进 old 头部，old 区超长越过容差，边界指针就向队首让一步、把最靠上的几个 old 页顺手翻成 young——**没有再访问也能「集体转正」**。（带 \* 的三个页就是这么翻的。）这也是拿 `IS_OLD` 做观测时的一条纪律：**不是每个 NO 都代表晋升，也不是每个 YES 都代表冷**——边界 ±20 页以内的身份牌，看边界滑动，别看页本身。

### 边界不是一条线，是一条带

`buf_LRU_old_adjust_len` 里有个 `BUF_LRU_OLD_TOLERANCE`：边界指针不是每插一页就挪一步，而是**攒够容差再动**。源码是个双向循环：

```cpp
if (old_len + BUF_LRU_OLD_TOLERANCE < new_len) {
  buf_pool->LRU_old = UT_LIST_GET_PREV(LRU, LRU_old);  // 边界向队首推
  buf_page_set_old(LRU_old, true);                     // 页被划进 old
} else if (old_len > new_len + BUF_LRU_OLD_TOLERANCE) {
  buf_pool->LRU_old = UT_LIST_GET_NEXT(LRU, LRU_old);  // 边界向队尾退
  buf_page_set_old(LRU_old, false);                    // 页被划回 young
}
```

所以边界附近的页，身份会因「指针滑动」翻动而非「被重新访问」。上面 1406 号页的 NO 就是这么来的——它明明刚从中点进来。这也是为什么拿 `IS_OLD` 做观测时，别对边界 ±20 页的页较真。

## 升 young 的三道闸

old 页想升入 young 区（挪到队首），要过三道闸，**每道都能独立否决**：

**第一道：淘汰还没开始。** `buf_page_peek_if_too_old` 的第一行：

```cpp
if (buf_pool->freed_page_clock == 0) {
  /* If eviction has not started yet, do not update the
    statistics or move blocks in the LRU list.  This is
    either the warm-up phase or an in-memory workload. */
  return false;
}
```

池子从没满过、一个页都没淘汰过（`freed_page_clock == 0`）时，**所有升 young 请求直接拒绝，连计数器都不走**。我在这上面踩了个大坑：冷启动后点查几个页、隔 2 秒再点一次，`made young` 纹丝不动——不是时间窗不够，是**预热期根本不挪页**。InnoDB 的逻辑是：池子还有的是空位，谁也别折腾。要看到升 young，先得让淘汰发生（把池子灌满）。这个冷知识网上几乎没人提，因为文档只写「young/old 子链」，不写预热豁免。

**第二道：时间窗。** 老过 `innodb_old_blocks_time`（默认 1000ms）才准升。源码：`(now - access_time) >= old_threshold` 才放行，否则 `n_pages_not_made_young++`。注意 `access_time` **只在首次访问时置位**（`buf_page_set_accessed` 里明写 "Make this the time of the first access"），之后访问都不刷新——所以「快速访问两次」凑不出资格，从首次访问起要真满 1000ms。这就是防扫描的核心：扫描的页从磁盘读入、落进 old 区（首次访问被记下），顺序读和预读会让它**在几百毫秒内又被碰到几次**，但那几次都翻不过时间窗。实测里 127589 次拒绝就是这么来的：**扫描洪水的页几乎每个都被访问了两遍以上，一次也升不了 young**。

**第三道：访问模式。** `Page_fetch::SCAN` 模式的访问**跳过升 young**，连随机预读都不做。`buf0buf.cc` 里明写：

```cpp
if (m_mode != Page_fetch::PEEK_IF_IN_POOL && m_mode != Page_fetch::SCAN) {
  buf_page_make_young_if_needed(&block->page);
}
```

枚举注释也直白：*"Same as NORMAL, but hint that the fetch is part of a large scan. Try not to flood the buffer pool with pages that may not be accessed again any time soon."* 但这里有个反直觉的事实：全库 grep 下来，`Page_fetch::SCAN` 的使用者**只有 row0pread.cc（并行读取器，8.0.14 的并行聚簇索引扫描）**。普通 `SELECT *` 的全表扫描（row0sel.cc 走 `Page_fetch::NORMAL`）**不享受这个标记**——也就是说，**单线程顺序扫描的防污染，全靠 midpoint + 时间窗这两道闸硬扛**，SCAN 标记只是并行扫描的额外保险。你以为的「扫描模式」在 8.4 里其实不覆盖最常见的场景。

### 三道闸的实测账本

把三道闸串成一次完整实验。冷启动 → 先访问 users 表 4 个热页（400000/700000/900000/100000 的叶子页）→ 全表扫描 big10m 把池子灌满并触发淘汰 → 立刻重访 4 个热页 → 隔 3 秒再重访：

```text
扫描刚结束（洪水期重访）  made young 0     not young 127662
隔 3 秒重访              made young 8     not young 127663
```

8 = 一次 IN 查询触碰的 8 个页：共享的根页 1 + 中间页 3 + 叶子页 4（百万行的 users 树中间层共 5 页，4 个 id 跨了 3 页）。**洪水期那次重访一个也没升上去，隔 3 秒后同一批访问放行 8 个**——两次之间没有别的变量，差的只是那道 1000ms 的时间窗：洪水把页搅进搅出，被重新读入的页资格从进池起算，不满 1000ms 的访问全部拒绝。重访之后再看这 8 个页的位置：

```text
首次访问（插中点一带）     LRU_POSITION 543-553，old 区头部
3 秒后重访升 young        LRU_POSITION 8184-8191，IS_OLD=NO   ← 队首
```

而这一切发生在 65460 页的扫描洪水之后——百万行扫描冲进来又流出去，**8 个热页一个都没被逐出**：扫描结束的快照里，5 个已在 young 区的页待在队首附近（8187-8191），3 个 old 页守在 old 区中段（3038-3040）等这轮重访接应。扫描自己的页呢？`Old database pages = 3043`，洪水全被圈在 old 子链里，淘汰从队尾（old 的末端）开始，牺牲的永远是扫描自己的炮灰。

## 时间窗拧到 0 会怎样

`innodb_old_blocks_time = 0` 意味着第二道闸拆掉：old 页一被访问就升 young。同样跑一遍 1000 万行全表扫描：

| old_blocks_time | made young | not young | 扫描后池内 |
| --- | --- | --- | --- |
| 0 ms | 56078 | 0 | old 区被反复访问的页洗成 young |
| 1000 ms（默认） | **0** | 127589 | 洪水圈死在 old 区 |

拧到 0 时扫描页里的「双次访问者」（顺序读 + 预读回访）全部升 young，56078 页挤进 young 区——**扫描把热页冲走的经典事故就是这么制造的**。默认 1000ms 时同一个扫描，升 young 数恰好是 0。这一个旋钮的开关，就是「LRU 洗劫」的有与无。

顺带一提「扫描速度」：读 6.5 万物理页用了 26 秒（2581 reads/s），不是磁盘慢（NVMe），是**淘汰跟不上流入**——每秒约 2500 页流入、同样要逐页从队尾淘汰腾位子。表大于内存的扫描，慢在换页不在读盘。

## 还第一篇的债：表大于内存时的回表

热身完成、中点插入和时间窗都验完了，现在还债。搭一个「表大于内存」的场景：big_k 表 1000 万行，聚簇树 1044MiB + 二级索引 idx_k 193MiB，池子 128MiB（约 5 万页 ≈ 表的 7%）。idx_k 的键是 id 乘大素数取模的双射——**k 与物理页序完全打散，每 31 个相邻的 k 才落同一个索引叶**，回表时的聚簇页也是纯随机访问。

流程：灌满池子（big10m 全表扫描）→ 300 个散列 k 的覆盖式探测两轮（只碰 idx_k，把索引页焐热并升 young）→ 分组计时。同一批 k 值，只换 SELECT 的列：

```sql
SELECT COUNT(*)              FROM ks JOIN big_k FORCE INDEX (idx_k) ON k ...  -- 覆盖
SELECT SUM(LENGTH(pad))      FROM ks JOIN big_k FORCE INDEX (idx_k) ON k ...  -- 要回表取 pad
```

| 量具 | 覆盖（COUNT） | 回表（取 pad） |
| --- | --- | --- |
| EXPLAIN ANALYZE 实测耗时 | 0.72 ms | **57.1 ms** |
| 物理读（Innodb_buffer_pool_reads） | **0** | **377** |
| 每行均摊物理读 | 0 | 1.26 页 |

第一篇在内存放得下时量到的是「耗时 4 倍、页读 1717 倍」；表大于内存后变成「**耗时 80 倍、物理读 ∞ 倍（0 → 377）**」。377 次物理读里：idx_k 树 3 页焐在池里没掉，300 次回表拆成约 300 个聚簇叶页 + 树上层若干次重读（页刚进池又被页赶走，同一棵树的中间层被反复拉入又逐出）。**预言兑现：4 倍变 40 倍量级（实测 80 倍）——因为「耗时 4 倍」里藏的全部是逻辑读，物理读一露头就是另一个数量级的单价。**

还有个细账：回表拉进来的 300 多个聚簇叶页，事后查 `IS_OLD`——**350 个是 YES**。它们随回表流进来，落点是 old 子链头部，因为只有一次访问、凑不满时间窗，静静等着被下一波访问淘汰。**这解释了「随机回表为什么是缓存杀手」的机制闭环：不仅页是冷的，连升 young 的资格都拿不到。** 反过来，覆盖查询焐热的 idx_k 页（探测三轮后）全部站在 young 区——热索引的「热」，是时间窗盖的章。

## 8.4 的两个新默认：change buffer 与自适应哈希

缓冲池不只装数据页，还有两位寄居的房客，8.4 正好都改了默认值——各自实测一遍。

### change buffer：默认从 all 改成 none

change buffer 解决的是**写二级索引的随机读**：往 idx_k 插一个键、目标索引页不在池里时，不读盘，把这笔修改先记进缓冲（旧名 insert buffer），等哪天这页因别的查询进池，再把积压的修改一次性合并（merge）上去。经典受益场景是「二级索引散、页不在内存」的写入负载——正是我的 big_k 形状。同一套场景各插 2 万行散列 k：

| 组 | 物理读 | 插入耗时 | Ibuf 状态 |
| --- | --- | --- | --- |
| `innodb_change_buffering = none`（8.4 默认） | 20472 | 4.35 s | 空 |
| `innodb_change_buffering = all` | **~200** | **0.23 s** | 2 万条修改排队，Ibuf 树 149 页 |

百倍差距，教科书式收益。读回 5 个刚写入的 k 值，后台合并风暴跟着启动：`merged insert 19998`，但物理读只涨了约 1600——**合并是「同页多笔修改一次性落账 + 已在池里的页不重读」**，2 万条排队修改摊到数千个目标索引页、其中大半还留在池里，所以总账 ~1800 次物理读对 none 组的 20472 次，同时插入快了近 20 倍。变更缓冲的本质不是消灭读，是**推迟 + 合并 + 去重**，把随机写的账单折成批发的。

那为什么 8.4 反而把它默认关了？因为代价同样真实：**合并把修改落回页的时刻，该页必须被读入、修改、刷出——合并风暴会跟业务 IO 抢带宽**；SSD 的随机写又已经足够快（none 组 4.35 秒完成 2 万次随机读入，HDD 时代这是分钟级的事）。受益场景（HDD、索引远大于内存、写多读少）在今天的硬件上越来越窄，Oracle 干脆把默认值从 `all` 翻成 `none`，把选择权还给用户。（9.x 里它已被正式弃用，8.4 LTS 是它最后一代可选功能。）另有一个硬限制值得一提：**唯一索引不能缓冲**——插入唯一键必须立刻读页查重，冲突判断没法推迟，所以 idx_k 若是 UNIQUE，上面的实验根本不会发生。

### 自适应哈希（AHI）：默认从 ON 改成 OFF

AHI 是另一路思路：**页在池里也可能慢**——B+ 树点查要走「根→中间→叶」三次页内二分。InnoDB 观察到某些页被以相同模式反复点查（`INDEX_NAME = 0, ...` 的检索模式），就给这页建个哈希索引，下次一步到位。它住在缓冲池里（`btr0sea.cc` 的 hash 表，8.4 分 8 个分区），完全自动、无法指定索引。

实测它的门槛：灌满池子后跑 2 万次随机主键点查（join 形式），五轮共 10 万次之后，`adaptive_hash_searches` 才爬到 3460；再五轮共 20 万次，`IS_HASHED='YES'` 的页才攒到 1214——**页要被同一模式反复访问成千上万次，才够建哈希的分数**。攒够了再看收益：AHI 开关各跑五轮同样的 2 万点查，耗时 3.4-4.2 s vs 3.4-3.9 s——**没有可测差异**。两三层树高、页全在池内的点查，B+ 树降为哈希一步的节省，被哈希分区的 latch 争用和普通路径的页命中率摊平了。

这轮实验没能复现「AHI 关掉会疼」的故事（我的池子装得下热区、树只有三层），但它反过来解释了 8.4 的默认翻转：**AHI 的历史问题是 latch 争用与维护开销在争用激烈的并发负载下会反噬吞吐**（社区大量高并发 case 关掉 AHI 反而更快），而它救场的前提（点查热区远小于池、树高、模式重复）在如今的大内存机器上越来越少成立。默认 OFF，需要时 `SET GLOBAL innodb_adaptive_hash_index=ON` 一句话打开——实测打开后它立刻从 0 页开始重新攒分数，关掉则**立刻清空哈希表**，都无感切换。

> 观测提示：`INNODB_BUFFER_PAGE_LRU`/`INNODB_BUFFER_PAGE` 虽是重量级视图（全池加锁扫描，生产慎用），8.4 里未弃用，本篇的 `IS_OLD`、`LRU_POSITION`、`IS_HASHED` 都来自它。日常监控请用轻量的计数器与 `SHOW ENGINE INNODB STATUS`。

## 页的生死账本

**一条链，两段身份。** young 子链 5/8、old 子链 3/8，边界指针带容差滑动。磁盘新页一律插 old 头（中点），B+ 树新建页直插队首；old 页要升 young 得过三道闸：淘汰已开始（预热豁免）、首次访问老过 1000ms、访问不是 SCAN 模式。8.4 的 SCAN 模式只保护并行扫描——**单线程全表扫描全靠中点插入 + 时间窗硬扛**。

**扫描洪水冲不掉热页，是三道闸的合力。** 6.5 万页的扫描只放行 0 个升 young、拒绝 127589 次；热页隔 3 秒重访升 young 站上队首，百万页洪水从 old 尾逐出。把时间窗拧到 0，同一个扫描立刻变成 56078 页升 young 的洗劫——**「LRU 被扫描冲垮」不是宿命，是一个默认值为 1000 的旋钮**。

**表大于内存时，回表的债终于现形。** 覆盖 0.72 ms / 0 物理读，回表 57 ms / 377 物理读——80 倍时差、每行 1.26 页物理读。第一篇的「4 倍会变 40 倍」兑现为实测 80 倍。且回表拉进来的 300 多个聚簇页里 350 个落在 old 区拿不到晋升资格——**随机回表是缓存杀手，杀伤力连「进池」都到不了，更别提「驻留」**。覆盖索引的账，从此该用物理读来算。

**8.4 关掉了两位房客的默认开关。** change buffer：none vs all 实测插入快 20 倍、物理读省 90%（20472 → ~1800 总账），但合并风暴与 SSD 时代收窄的受益面让默认翻成 none（9.x 已正式弃用）。AHI：同一模式访问上万次才攒够建哈希的分数，实测开关无差异，默认翻成 OFF 是把 latch 争用的历史包袱放下。**缓冲池的默认配置哲学变了：从「宁滥勿缺」到「证据不足先不开」**——这也许是这一篇最值得带走的变化。
