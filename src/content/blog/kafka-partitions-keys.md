上一篇结尾留了一道除法：分区器对 key 做 murmur2 哈希，再对分区数取模。当时只有一句话，这道除法却管着每条消息落进哪根日志、谁和谁排在一起、多少人能同时干活。这一篇把它拆成三个问题：落点怎么算出来的，分区数钉死了什么，以及中途把分母改掉会发生什么。先交代结论：前两面是良性的，第三面是灾。

## 一、这道除法可以手算

公式一共三步：对 key 算 murmur2 哈希得到一个 32 位整数，`toPositive` 转正（`x & 0x7fffffff`），再对分区数取模。整个默认分区器就这一行逻辑，没有随机数，没有状态，也不用问 broker。所以落点可以提前手算。拿 15 个 key（旅程篇出过场的 u1/u2/u3，加上 order 与 city 系列）各发两条到 3 分区的 topic，手算结果和实际落点逐一对照：

```text
key        hash          手算   实测
u1         745337584     p1     p1
u2         1598843406    p0     p0
u3         1889425894    p1     p1
order-01   -89000877     p2     p2
...
city-gz    1362891687    p0     p0
```

15 个全中。每个 key 的两条消息都落同一分区，15 个 key 在三个分区上的分布是 5/5/5，murmur2 的均匀性在这个小样本上也立得住。旅程篇实测的 u1→p1、u2→p0 不是巧合，是这道除法的输出，当时只能观察，现在能算了。

换一种语言的客户端算出来还是同一个结果。用容器里的 Java console-producer 发一条 key=u2：

```text
$ echo "u2:from-java-cli" | kafka-console-producer.sh --topic kmap \
    --property parse.key=true --property key.separator=:

消费端看到：u2 → p0，与 kafkajs 的手算一致
```

这是把算法钉死成 murmur2 的实际价值：落点是 key 和分区数的纯函数，谁算都一样，服务端可以预演分片，事后也能对账。官方对顺序的承诺原文是 "any consumer of a given topic-partition will always read that partition's events in exactly the same order as they were written"，任何消费者读一个 topic-partition，读到的顺序就是写入顺序。注意承诺的单位：是 topic-partition，不是 topic。顺序的单位是分区，这句话是整篇的锚点，第二节会量它的边界。

无 key 的消息是另一回事。kafkajs 对无 key 消息做轮询，6 条在 3 个分区上均分 2/2/2；同样 6 条交给 Java 客户端，全进了 p0，它用的是粘性分区，一批攒满才换下一个（攒批上一篇拆过）。同一件事两种实现、两种结果，说明无 key 消息的落点是实现细节，不是承诺。想要靠得住的落点，就带 key。还有个后门：消息可以直接指定 `partition` 字段绕开分区器（kafkajs 的 `message.partition`、Java 的 `ProducerRecord` 构造器），落点从此归你管，加分区之后重算落点的活也归你管。

顺手记一个坑。kafkajs 里有两套 murmur2：default 版用 Long 库做 32 位回绕乘法，与 Java 的 `Utils.murmur2` 一致；legacy 版直接拿 JS 浮点数乘，乘积超过 2^53 就丢尾数。我最初拿 legacy 算预测，15 个 key 里 10 个和实测对不上，u2 被算成 p2，实际是 p0。producer 运行时用的是 default 版，所以收发消息不受影响，但想手算落点必须用对实现。CPython 浮点篇那道 2^53 的悬崖，这里咬到的是哈希算法。

## 二、分区数钉死两样东西

**第一样是顺序的范围。**同样 30 条消息（seq=1..30，key 轮换 u1/u2/u3），分别发进 1 分区和 3 分区的 topic，单个消费者从头读：

```text
【1 分区】到达顺序：
  1 2 3 4 5 6 …… 28 29 30        严格递增

【3 分区】到达顺序：
  2 3 5 6 8 9 …… 29 30 1 4 7 10 …… 25 28
  p0（10 条）：1 4 7 10 13 16 19 22 25 28    分区内有序
  p1（20 条）：2 3 5 6 8 9 …… 29 30         分区内有序
  p2：0 条
```

1 分区全程全序；3 分区各自内部有序，全局到达顺序交错。这就是第一节那句承诺的边界：分区内「与写入顺序完全一致」成立，跨分区什么都不保证。还有个附带发现：三个分区只用了两个，u1/u2/u3 全哈希进了 p0 和 p1，p2 从头到尾空着。分区数只设上限，用不用得满看 key 的分布。

**第二样是并行的上限。**一个分区在同一消费组里至多分给一个消费者（旅程篇提过一句，消费者组篇展开），所以 topic 有几个分区，同时就有几个人能干活。9000 条消息、每条处理 1ms，三种配置竞速：

```text
3 分区 × 3 个消费者：排空 6.4 秒    每人 3000 条，各管一个分区
3 分区 × 1 个消费者：排空 13.1 秒   一人 9000 条
1 分区 × 3 个消费者：排空 13.2 秒   一人 9000 条，另两人 0 条
```

第三行最冷：多出来的两个人一条消息都摸不到，建组的协商照跑，活还是一个人干。第一行的数字没到理想的三分之一，因为三个消费者挤在同一个 Node 进程里共享一个事件循环，拆成三个进程会更接近；方向没有疑问，加分区确实买到并行，不加分区加人买不到。生产端不是瓶颈：9000 条灌进 3 分区只花了 128ms，慢的从来是消化。

对照教具看立场。RabbitMQ 的并行是多个 worker 抢同一个队列：基础篇实验四里 3 个 worker 均分 1000 单（333/333/334），队列结构一动不动；代价是处理顺序被抢食打乱，快慢 worker 手里各囤一撮消息，实验八里不限流时慢消费者囤了 10 条。顺序与并行在队列世界里是消费端自己的修行，broker 不表态。Kafka 把这个交换摆上台面写进 topic 的结构里：**分区数同时是顺序的范围和并行的上限**，想要更多并行，就得接受更粗的顺序，一个旋钮管两件事。

这个旋钮还拧不回去。把 3 分区的 topic 改回 2 分区：

```text
$ kafka-topics.sh --alter --topic kgrow --partitions 2
ERROR org.apache.kafka.common.errors.InvalidPartitionsException:
The topic kgrow currently has 3 partition(s); 2 would not be an increase.
```

alter 命令的语义里根本没有「减」。道理不难想：减分区要决定哪些消息搬家、哪些作废，所有消费组已提交的位移集体失效。日志只追加、不回改（上一篇的结论），分区数只能跟着一起单向生长。

## 三、中途加一个分区

只能加，那加就是常态操作。现在兑现旅程篇预告的那场实测。2 分区的 topic，u1 到 u12 十二个 key 各发一条（seq=1），先纸面算出它们在 3 分区下的落点：

```text
u1    2分区→p0   3分区→p1   ← 注定搬家
u2    2分区→p0   3分区→p0
u5    2分区→p1   3分区→p2   ← 注定搬家
……
u12   2分区→p0   3分区→p2   ← 注定搬家

预测：12 个 key 里 9 个会搬家
```

加分区，再发同一批 key（seq=2），全量拉出 24 条对账：

```text
$ kafka-topics.sh --alter --topic kgrow --partitions 3
$ kafka-topics.sh --describe --topic kgrow
Topic: kgrow   PartitionCount: 3   ReplicationFactor: 1   …
```

- seq=1 的 12 条，**0 条挪动**。加分区不迁移数据，老消息永远躺在当初写入的那个分区里。
- seq=2 的 12 条，**9 个 key 搬家**，名单与纸面预测完全同一批：u1、u3、u5、u6、u7、u8、u10、u11、u12。
- u1 的历史从此劈成两段：seq=1 在 p0，seq=2 在 p1。业务眼里「同一个 u1」的两条相邻记录，物理上躺在两根互不相干的日志里。

劈开对消费者意味着什么？搭一个最小现场。1 分区的 topic，u5 写入 seq=1，落 p0；加一个分区，u5 写入 seq=2，按 %2 落 p1。两个消费者同组就位、各拿一个分区，p0 那位模拟存量积压，每条消息压 4 秒再处理：

```text
13:42:53.466  处理完成 seq=2（p1，新分区）
13:42:57.473  处理完成 seq=1（p0，旧分区）
```

后写的消息早了 4 秒被处理完。没有任何东西出错：每个分区内部有序，消费组健康，位移提交正常，但「u5 的 seq=1 先于 seq=2」这句话从此刻起不再成立。换成账户场景，先充值后消费的两条事件，消费那条先跑。4 秒的人为延迟不是作弊：旧分区里有存量、新分区从零开始，是加分区之后最常见的现实。

官方文档对这个操作写得相当重："messages with the same key may be routed to different partitions after the expansion, potentially affecting message ordering guarantees for existing keys"，同 key 的消息扩容后可能路由到不同分区，已有 key 的顺序保证随之受影响。后面还跟着一句更直白的："Kafka will not attempt to automatically redistribute existing data"，Kafka 不会试着替你重新分布已有数据。

还有一个更隐蔽的侧面：加完分区，存量 producer 不一定立刻看得见。分区数缓存在客户端的元数据里，kafkajs 的 `metadataMaxAge` 默认 300000ms，Java 客户端的 `metadata.max.age.ms` 同为 5 分钟。实测让 producer 保持连接不断开，加分区后立刻发一条：

```text
A（加分区前发）      → p0
B（加分区后立刻发，老连接） → p0    元数据里还只有 1 个分区
C（断开重连后发）     → p1
```

文档给这个现象起的名字叫 Metadata Propagation Delay。窗口期里，同一个 key 前后两条消息可能都留在旧分区，也可能一条旧一条新，破序不是一个干脆的瞬间，它带着一段不确定的过渡。

## 四、怎么跟这道除法相处

出路排一排。

**提前定好，别轻易动。**分区数的定法是倒推：要几个消费者同时干活，峰值吞吐要多少，按消费端的并行需求定下限，再留一点余量。别贪多：每个分区都是一整套段文件加索引（上一篇那堆文件家族按分区数乘份数），控制器要维护的元数据、故障时要选举的分区都按分区数涨（副本篇展开），建组协商也更贵，这次竞速实测单人建组 5 秒、三人先后入组连环 rebalance 花了 15 秒（消费者组篇细讲）。

**真要加，把它当成一次有顺序影响的变更。**挑低峰窗口，或者先停写、等旧分区排空再加，把历史劈开的过渡窗压到最小；下游扛不住停写，就让消费端自己重建顺序，消息里带业务时间戳或序列号，按它合并而不是按到达顺序处理。老 producer 那 5 分钟的元数据窗口也要算进方案里。

**落点规则可以定制。**分区器是可替换的（kafkajs 的 `createPartitioner`、Java 的 `partitioner.class`），文档公式里的 `hash(key) % number_of_partitions` 说的是默认实现。换成一致性哈希能不能少搬点家？拿教具对照：RabbitMQ 的 x-consistent-hash 交换机干的就是这件事，绑定键当权重，队列挂上哈希环。同样 30 个 key，环从 2 个队列变 3 个，重发一轮：

```text
一致性哈希（RabbitMQ）：搬家 11/30   ≈1/3，贴近理论值
取模（Kafka，%2 → %3）：搬家 17/30   ≈2/3
```

一致性哈希的搬家率确实低。但注意，搬走的那 11 个 key 历史照样劈开：旧消息在 q1，新消息在 q3，顺序照样破。一致性哈希把灾变小，没有变没，代价是环这个结构有状态、要维护。Kafka 的默认分区器无状态、均匀、可手算（第一节证过），只要分区数不变，映射就永远稳定；为一个本该提前定死的数字引入环结构，赌的还是罕见的扩容，不划算。

别的系统为「扩容要搬家」付的是真金白银，对照着看更清楚。Redis 集群篇拆过槽迁移：扩容时把键按槽真的搬去新家，迁移窗口里源节点用 ASK 重定向指路，搬完才改口 MOVED，数据动了，映射就不劈。MySQL 分区表篇的 REORGANIZE 同理，加分区时已有的行真的重排进新家。它们搬得动数据，因为行的坐标由存储引擎自己掌管，搬完即生效。Kafka 搬不动：消息的坐标是（分区, offset）二元组，握在无数消费组手里，位移早已提交出去，搬消息等于搬家不告诉任何人新地址，所有书签集体指错门。所以 Kafka 干脆不搬，改规则、劈历史、把警告写进文档，让做决定的人自己权衡。

三个问题的答案齐了：落点是 murmur2 对分区数取模，可手算，跨语言一致，无 key 则无任何承诺；分区数同时钉死顺序的范围与并行的上限，只增不减；加分区就是重哈希，9/12 的 key 搬家，历史劈开，顺序破，数据不迁移。

这篇从头到尾把「分区内全序」当好东西用，它其实标着价格：想要全局有序，只剩一个分区可用，第二节竞速里的并行收益当场清零。而且就算从不动分区，顺序也会漏：生产者重试会翻序，多个实例各发各的，跨分区合并本来就没有时序。下一篇把顺序保证四个字放上秤，看它的边界到底画在哪里。

（实验环境同前两篇：apache/kafka:4.3.1 KRaft 单容器，kafkajs 2.2.4；教具容器 rabbitmq:4-management 这轮也回来了，x-consistent-hash 插件默认没启用，先 enable 才跑得动对照。两个坑记一下：竞速想等「组稳了」再计时，别在消息处理函数里阻塞等待，rebalance 回收分区前要等在途 handler 跑完，我把建组硬生生卡到 65 秒，分配表全是过期数据；正确姿势是先 pause 分区、组稳了再 resume，顺带一提 pause 得在 run 之后调，先调会报 "Consumer group was not initialized"。另外 deleteTopics 删一个不存在的主题，kafkajs 会重试五轮十几秒才把错抛出来，脚本里别当它是快速失败。）
