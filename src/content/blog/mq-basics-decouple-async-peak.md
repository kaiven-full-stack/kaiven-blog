```text
10:00:00  下单服务一切正常，每单 30 毫秒收工。
10:00:01  积分服务开始抽风：每个请求 2 秒起步，还有 10% 直接 500。
10:00:02  下单接口的 RT 曲线一跃而起——每单 2029 毫秒。
10:00:05  运营开始收到投诉：用户点了下单，转圈三秒，偶尔还报错。
```

库存是好的，通知是好的，用户是好的，下单服务本身也是好的。但整条链路死了，因为下单在**同步等待**一个病了的下游。这是新系列的第一篇——MySQL 系列我们沿着一条 SQL 沉进 InnoDB 的存储现场，这个系列沿着一条消息的旅程走进消息队列的现场。起点不在消息队列里，而在它要治的那种病上。

先把病造出来，再谈药。

## 实验一：三个下游只有一个病了，为什么整个接口陪葬

用 Node 写一个最朴素的下单 handler，同步调用三个下游，各自 10ms。三个 10ms 串起来，每单 30ms，健康：

```js
async function placeOrder(order) {
  await callInventory();  // 10ms
  await callNotify();     // 10ms
  await callPoints();     // 10ms —— 病了之后：2000ms + 10% 失败
  return '下单成功';
}
```

然后让积分服务「病」了：每个请求睡 2 秒，10% 概率抛 500。跑十单：

```text
#01 ✓  2022ms
#02 ✗  2031ms  ← 积分服务 500
#03 ✓  2031ms
...
#10 ✓  2031ms
→ 9/10 成功 | 平均 2029ms/单

── 积分健康 × 3 单（对照）──
→ 3/3 成功 | 平均 30ms/单
```

**每单 RT 从 30ms 涨到 2029ms，翻了 68 倍，成功率掉到 9/10。**而下单代码一行没改，库存和通知也一点没慢。病是积分的，疼的是下单——因为同步调用是一根串联的锁链：链条的强度取决于最弱的一环，链条的耗时等于每一环的耗时之和。更糟的是那些看不见的成本：下单服务的连接和线程被 2 秒一个的请求占着，流量一大，本身健康的库存、通知调用也开始排队——**下游的病会顺着同步调用链一路传染**。

真实世界里的「积分服务病了」可以是任何东西：一次慢查询、一次 GC 停顿、一次依赖的依赖抖了一下。问题从来不是「下游会不会病」——会的，一定会——问题是**下游病了，你陪葬吗**？

## 药方：把「现在就要」和「必须做」拆开

回头看那笔 2029ms 的账：库存 10ms、通知 10ms、积分 2000ms。下单接口对积分的真实需求是什么？「这单的积分必须记上」。注意——**没说必须现在记上**。

- 库存必须现在扣，不然超卖；
- 通知最好现在发，用户在等确认页；
- 积分？晚几秒到账，用户根本感知不到。

「必须做」但不「现在就要」的事，天然适合异步化：下单接口发一条「订单已成立」的消息出去，就返回成功；积分服务自己从队列里取消息，按自己的节奏记账。消息队列（Message Queue，MQ）就是干这件事的中间人——生产者把消息丢给它，它替你存着，消费者什么时候来取、取多快，生产者不关心。

三个被写烂的词——解耦、异步、削峰——其实就是这个动作在三个方向上的收益。接下来每个词配一个实验，跑给你看。

## 实验二：异步——RT 与下游脱钩

环境是 RabbitMQ 4.x 的 Docker 容器（教具，不是主角；两段话的环境说明放在文末，想动手的读者再看）。把积分摘出调用链：下单只同步调库存和通知，然后往 `points` 队列发一条 JSON 消息。积分 worker 从队列消费——**注意它还病着，还是 2 秒一条**：

```text
── 异步下单 × 10 单（积分已摘出调用链，改为发消息）──
#01 ✓   21ms  （积分消息已入队，还没做）
#02 ✓   21ms  （积分消息已入队，还没做）
...
→ 10/10 成功 | 平均 21ms/单 | 总耗时 0.2s
```

每单 RT 从 2029ms 回到 **21ms**，即使积分 worker 还是 2 秒一条。30ms 变 21ms 的那点小改善来自少了一次同步调用；真正的大头是：**下单的响应时间从此与积分的耗时无关**。消息进队列出队是毫秒级的事，2 秒的病被留在了队列的另一头。

这就是异步的本钱：**RT 里只剩你真正要等的东西**。但账要记全——积分从「下单后 10ms 完成」变成「下单后平均 2 秒、排队长的时候更晚才完成」。你买到了快的下单，付的是**积分最终一致**：它不再和下单在一个瞬间完成，而是「早晚会完成」。对这个场景，值。

## 实验三：解耦——下游的生死不再决定上游的生死

异步解决「病了拖慢我」，解耦解决更狠的：**病了会不会弄死我**。

worker 还在消费（依旧 2 秒一条），先正常下一轮单，10/10 成功。然后 Ctrl-C 把 worker 杀掉——模拟积分服务整个挂了——再下一轮单：

```text
→ 10/10 成功 | 平均 21ms/单 | 总耗时 0.2s
```

下单照样全部成功。那 10 条积分消息去哪了？RabbitMQ 队列的深度涨到了 10：

```text
$ docker exec rabbitmq rabbitmqctl list_queues name messages
points   10
```

消息在队列里等。worker 重启，2 秒一条、10 条、约 20 秒排空，一条没丢：

```text
[worker-1] ✓ orderId=7（2000ms 处理完，已 ack）
[worker-1] ✓ orderId=8（2000ms 处完，已 ack）
...
points   0
```

（细节控会问：Ctrl-C 的瞬间 worker 手里可能还捏着一条收到但没处理完的消息，它会回到队列——为什么回了不会丢也不会乱？这是「ack 与重投」的地盘，第二篇专门拆，这篇先按下。）

对比实验一：同样是积分挂掉 20 秒，同步链的世界里下单成功率一路归零；队列的世界里下单毫无感觉，积分在恢复后把欠的账补上。**「订单已成立」这个事件从「积分函数的入参」变成了「积分服务的口粮」**——上游不再知道下游是谁、在不在、快不快，它只管把事实丢出去。哪天积分要重写、要停机维护、要灰度切流量，下单服务一行代码都不用动。

这就是解耦的实验形态：**下游的生死，不再决定上游的生死。**

顺带把「发布订阅」也跑了——解耦的自然延伸。一个 `order.events` 交换机（exchange），库存、积分、通知三家各自持有一个独立队列绑上去。发一个「订单已成立」事件：

```text
[库存] 收到 #1 订单已成立
[积分] 收到 #1 订单已成立
[通知] 收到 #1 订单已成立
...（5 个事件，三家各收 5 条）
```

**同一个事实，三家各自消费，互不知晓**。下游从「被调用」变成「订阅事实」，加第四个下游（比如风控）= 新开一个队列绑上去，上游零改动。反过来看 RabbitMQ 也有点对点玩法：两家消费者共享同一个队列竞争消费，5 条消息 A 拿 2 条、B 拿 3 条，一条只给一家——这正是实验四里多 worker 排空的原理。**发布订阅是一份事实多家消费，点对点是一堆活多家分摊**，同一个交换机，两种玩法，区别只在队列怎么开。

## 实验四：削峰——把峰值搬进队列

第三种病：下游不病，但**流量病**——秒杀、整点抢券，瞬时一万单，积分服务每秒只能消化 20 单。

先把消费者停掉（这次要看的是队列本身），瞬时灌 1000 单：

```text
── 削峰：1000 单瞬时灌入（此刻没有消费者）──
→ 灌入 1000 条用时 13ms（≈76000 单/秒）
→ 最慢一单的入队等待 0.7ms
```

1000 条消息 13 毫秒全部入队，**最慢一单的入队等待 0.7ms**——上游没有任何一单被下游的消化速率拖住。Management UI 的 points 队列页上，深度曲线此刻是一根 1000 的尖峰。如果这是同步链，实验一已经告诉你答案了：第 N 单要等前面所有单的 2 秒排完，RT 曲线直接上天，连接池先爆。

现在开一个 worker（这次病好了，50ms 一条），看它按自己的节奏消化：**1000 条，单 worker 用了 52 秒**。再开两个 worker（三个共享队列竞争消费）：

```text
TRIPLE-DRAIN: 18s split=334/333/333
```

**18 秒排空，三条腿均分 334/333/333。**流量峰值没有消失——它被搬进了队列，摊平成下游消化得起的平均速率。上游瞬间放行、下游平稳干活，中间的缓冲垫就是削峰的全部秘密。

实验四还顺手暴露了一个之前藏着的性质：同一个队列的多个消费者是**竞争**关系（点对点），所以加 worker 才能横向扩。52→18 秒不是三倍速（有调度和衔接开销），但方向是对的：**消化速率不够，加消费者就行，上游无感**。

另外注意一个容易忽视的事实：削峰削掉的峰值不是「消失」了，是**排队**了。排在第 1000 位的那条消息，等到自己被处理时已是 18 秒之后（单 worker 则是 52 秒）。下游限速 20 单/秒的世界里，一万单的峰值注定要 500 秒才能消化完——MQ 改变不了这个除法，它只是让你**不用把 500 秒摊到用户的响应时间上**。

## 推与拉：一个伏笔

这篇里还有个没展开的机制问题：消息怎么从队列到消费者？RabbitMQ 的答案是**推**——broker 主动把消息送到消费者的回调里，节奏由 broker 定，消费者唯一的阀门是 prefetch（「在等我 ack 之前，最多推给我几条」，第二篇细讲）。

Kafka 的答案反过来：**拉**——消费者主动来 poll，自己决定节奏，落下的进度自己记账（位移）。推的好处是实时、省轮询；拉的好处是消费者按自己的能力消费、批量拉取摊薄开销，进度这个概念也自然浮出水面。

两家的分歧先记下，等到 Kafka 的第一篇现场对照。你还会发现那篇里队列的画风大变：消息**不再被消费掉**，消费只是记账，删除按时间/大小截断——同一个词「队列」，两个世界。

## 什么时候不该用：一张账单

解耦、异步、削峰听起来无所不能，但每一项收益都对应一张账单，只是这篇文章的前三个实验一直在替你付账：

1. **会排队、会延迟。**异步的收益 = 下游耗时从 RT 里消失；代价 = 下游完成时间从「几十毫秒后」变成「队列积压排空之后」。积分晚几秒无所谓，**支付扣款晚几秒、库存扣减晚几秒，就是事故**。「必须现在就要结果」的调用，老老实实同步调——异步化之前先问：这个下游的延迟，业务真的无感吗？
2. **最终一致，不是立等可取。**下单返回成功 ≠ 积分已记账。用户下一步动作如果依赖这个「 eventual 状态」（下单后立刻查积分余额），就会撞上不一致窗口。
3. **消息会丢、会重、会乱序。**实验三的「一条没丢」有前提：队列是持久化的、消息落了盘、worker 妥善 ack。这些前提每个都是一整篇的内容——第二篇就拆「没 ack 会怎样」。重复与乱序同理，都是第二篇之后的债。
4. **你多了一个要养的系统。**broker 自己也是个服务：它会挂（实验三里「上游无感」的前提是 broker 没挂）、它要运维、要监控积压、要容量规划。队列深度本身就是一个新的健康指标——积压 10 条是正常波动，积压 1000 万条是下游死了没人发现。

所以三种「看起来该用」其实不该的场景：

- **把 MQ 当 RPC 用**：发一条消息，眼巴巴等消费者处理完回一条。你付了排队延迟和一套 broker 运维，买到的却是同步调用的语义——直接调函数不好吗？
- **峰值本来就扛得住**：日均流量平得很，没有秒杀没有整点尖峰。削峰是给峰值买保险，保费是排队延迟和最终一致——没有峰值，保单白买。
- **分布式单体里塞 MQ**：所有服务还是拧成一团一起发版，中间只是多了个「异步的」锁链。爆炸没有消失，只是从「同步超时」变成「积压告警」，还更难查了。

一句话：**MQ 买的是「下游的病不再传染上游」，卖的是「下游完成的事，从这一刻起变成早晚会完成的」。**前者是你的刚需吗？后者你的业务咽得下吗？两个问题都有答案，才知道该不该上。

## 环境：两段话的复现说明

教具是 RabbitMQ 4.x（Docker 官方 `rabbitmq:4-management` 镜像），脚本用 Node + amqplib。一条命令起容器（自定义了账号密码——默认的 `guest` 只允许 broker 自己眼中的 localhost 连接，端口映射过来的连接会被拒）：

```bash
docker run -d --name rabbitmq -p 5672:5672 -p 15672:15672 \
  -e RABBITMQ_DEFAULT_USER=kaiven -e RABBITMQ_DEFAULT_PASS=xxx \
  rabbitmq:4-management
```

浏览器打开 `localhost:15672` 登录就是 Management UI。第一个惊喜给的是我自己的第一版脚本：实验二的 `points` 队列我在脚本里写的是「非持久化队列」，**RabbitMQ 4.x 直接拒绝了这个声明，连接当场被断**——4.x 起「非持久化 + 非独占」队列默认禁用（`transient_nonexcl_queues` 废弃）。修法是把队列声明成 durable（实验数据里的 messages-in-queue 落盘语义由此而来）。这算教具给的第一课：**不同 MQ 对「消息放内存还是磁盘」的默认答案不一样，而默认值就是它们的世界观。**——这一课在 Kafka 那边会以完全不同的方式再上一遍：它连「删除」的定义都不一样。

所有脚本（下单、worker、灌压）几十行一个，仓库外维护，思路都在正文里，随手就能复刻。

---

三单 30ms 到 2029ms 的崩溃、21ms 的收复、10/10 的死里逃生、52 秒到 18 秒的排空——四个实验讲完了一个动作的三种收益。但有一个问题被小心地绕开了：实验三的「一条没丢」，前提是 worker 处理完每条消息都认真回了一个 ack；实验二到四的消费者也都是乖学生，处理完就 ack，假装世界很完美。

那如果消息处理到一半，消费者崩了呢？如果一条消息天生就是毒的，谁处理谁崩呢？如果消息被投递了两次，你的账本会记两笔吗？——下一篇，投递语义：at-least-once 为什么是常态，幂等为什么是消费端的必修课。到时候队列不再假装完美，我们也不得不在崩溃现场数账。
